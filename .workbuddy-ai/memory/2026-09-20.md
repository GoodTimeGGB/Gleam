### 一、提示词前缀缓存友好化（P0）

**理论**：服务端前缀缓存（KV cache 复用）要求**逐字节相同的最长公共前缀**，命中部分按折扣计价。
不是"意思一样"，是逐字节——一个字符不同，从该处往后全部未命中。

**原布局的问题**：`buildSystemPrompt` 把最长的静态块（输出格式 + 规划规则 + 验收指南，一千多字）
排在**最后**，而工具 schema 段在最前、且菜单模式下按目标筛选 →
第一个易变段出现在第一百字左右，公共前缀几乎为零，缓存形同虚设。

**新布局**：稳定段（身份 → 输出格式/规则/验收指南 → 角色知识 → 验收重点 → 产出格式 → 风格 →
编程准则 → 能力菜单 → 定时任务）+ 易变段（筛出的 schema → 工作目录 → 摘要 → 记忆 → 历史 → 反馈）。

关键拆分：**能力菜单（只依赖注册表，稳定）** 与 **完整 schema（按目标筛选，易变）** 分开，
不再把稳定内容拖进易变区。反思器同样处理（`reflectorSystemPrompt`）。

**易被忽略的一步**：格式约束前移后离生成点远了两千字，末尾必须补一行 `## 输出提醒`
（排在易变段之后，不损缓存前缀，却把"只输出 JSON"推回生成点）。

**度量**：`llm.StablePrefixLen` / `SplitCacheBoundary`（按字符切分，不切断多字节字符）。

### 二、缓存命中量化（P0）

- 四套协议分别解析：OpenAI/GLM `prompt_tokens_details.cached_tokens`、DeepSeek `prompt_cache_hit_tokens`、
  Anthropic `cache_read_input_tokens`、Responses `input_tokens_details.cached_tokens`
- **流式必须主动要 usage**：规划走流式，不主动要就永远只能估算，而**估算值里没有"缓存"这一项**，
  命中率永远显示不出来。故流式带 `stream_options.include_usage`。
  该字段是 OpenAI 扩展，个别厂商直接 400 → **被拒一次自动退回重试并记住不再发**（不能为拿准数字把主链路弄挂）
- **Anthropic 是 opt-in**：不标 `cache_control` 就完全不缓存。系统提示词估算 > 1024 token 时
  转内容块数组并挂 `{type:"ephemeral"}`
- **口径对齐**：Anthropic 的 `input_tokens` 不含缓存部分，总输入按 `input_tokens + cache_read + cache_creation` 计，
  与 OpenAI 的 `prompt_tokens`（本身含 cached）一致；命中量只取 `cache_read`
- `TaskUsage` 增 `CachedTokens` / `CachedCalls`；任务卡悬浮显示命中率
- **沉默比撒谎好**：厂商不返回该字段时不显示任何百分比——"命中率 0%"会被误读成布局有问题

### 三、场景模板（P1）

文章原话：**"把不同场景的差异沉淀为 Agent Template，而不是为每个场景修改底层 Runtime"**。

`ExpertRole` 从"人设 + 验收重点"升级为五字段模板：
`SystemPrompt` / `AcceptanceFocus` / `OutputFormat` / `Tools` / `ModelTier`。

- `Tools` → `Planner.RoleTools`：菜单模式下强制附 schema，且排在按目标快筛结果**之前**；
  与 `ForceTools`（上次用过的）**分开存**，提示词里也分开说，因为理由不同
- `OutputFormat` → 注入稳定段。"写份报告"在分析师那里是表 + 口径，在 PM 那里是"谁、什么时候、交付什么"
- `ModelTier` → `llm.tiers` 档位表 + `Agent.TierLLM`，内置 economy/coding/office/reasoning。
  **三层回退**（角色未声明 / 档位未配置 / 档位即主模型）都安全回退——档位是"可以挑"不是"必须挑"
- 同一场景内规划/反思/对话用同一客户端；mock 会话下档位失效，避免离线自测打真实网络
- **边界**：模板作用于工作/编程模式（规划管线）；对话模式只取模型档位——
  把"优先用 file.*"这类规划导向约束塞进直答路径只会互相打架

**预算冲突的明确处理**：`MaxToolSchemas` 是用户显式上限，模板不能顶穿；角色工具在预算内优先占
（`reply` 始终占一席），装不下就是装不下。默认 12 足够放下任何角色 ≤5 个核心工具。

### 本机踩坑（已写进 skill）

- **本仓库全部是 LF 行尾**（此前记录的"CRLF"是误判，已在 2026-09-18 日志加勘误）。
  `gofmt -w` 可能连带改掉行尾，改完必须核：`python -c "raw=open(f,'rb').read(); print(raw.count(b'\r\n'))"`
- `gofmt -l` 在**改动结构体字段/常量对齐列**后会报警（不是行尾问题）。核格式时先 `tr -d '\r'` 归一化
- `NewGLM(..., timeout time.Duration)` 最后一个是 `time.Duration`，传字面量 `5` = 5 纳秒，
  测试以 "context deadline exceeded" 失败
- 前缀缓存的公共前缀**包含段落标题**：两边都有 `## 上下文` 时标题本身在公共前缀里，
  只有标题下的取值不同。断言要针对**取值**，不要针对标题
- 测试里不要复刻生产代码的拼装逻辑（如自己再拼一遍系统提示词）——那样测试改了也不会红。
  正解是把拼装抽成函数（`reflectorSystemPrompt`）让测试调真的那个

## 就绪体检：把「自建九坑」做成可执行自检

文章（Qoder Agent SDK 分享）里最后一处可迁移的东西：它列的九个坑 + 那句结论
"几个坑叠在一起，结果就是 demo 做了很多，稳定进入生产的 Agent 很少"。
静态清单看一遍就忘、没法随版本回归、也没法在自己这套系统上验证踩没踩，
所以做成**一次可执行体检**，不是第二份清单。

### 九项 → 真实证据来源（这是这项功能的全部价值所在）

| # | 坑 | 证据 |
|---|---|---|
| 1 | Runtime 重复建设 | 工具注册表 / 子系统装配 / 工具 schema 完整度（裸工具=模型猜参数） |
| 2 | 只会聊不会交付 | 工具权限分布 / 验收门禁 / 结构化结果 |
| 3 | 模型与能力锁定 | 厂商目录 / 协议集合 / `llm.tiers` 档位表 |
| 4 | 权限与审计割裂 | 门控覆盖数 / 门面视图条数 / 审计留痕 / **审批通道** |
| 5 | 最佳实践不可复制 | 场景模板五要素完整度 / 技能数与复用次数 / 可安装生态 |
| 6 | 体验与业务脱节 | 角色数 / 工作区 / 微光空间 / 历史会话 |
| 7 | 缓存不可控 | **实测**提示词公共前缀 + 用量归集里的缓存命中 |
| 8 | 缺少健康迭代架构 | 成长日志（任务数 / 平均分 / 连续活跃 / 等级） |
| 9 | 可扩展架构与压缩记忆 | 记忆条数 / 短期窗口 / 压缩开关与节省量 / 扩展点计数 |

### 踩过并修正的两个坑（都有测试固定）

1. **`checkDelivery` 空指针**：体检在门控缺席（`Gate == nil`）时直接 deref 崩了。
   加 `effectivePermissionOf` 兜底：门控在就用门控，缺席退回工具自身声明。
   教训：**体检代码本身不能把引擎跑挂**——它最该在"装配不全"时可用。
2. **缓存项只看占比 → 错判**。真实环境（21 个内置工具）下稳定段 2448 字符、布局完全正确，
   却因按目标筛出的 schema 尾巴长、占比仅 46% 被判「待改进」。
   **占比低不等于布局坏**。改成三级判定，顺序有意为之：
   1) 布局对不对（稳定段标志小节 `stablePromptMarkers` 是否全落在公共前缀内；不对=不合格）
   2) 稳定段够不够大（≥ `CacheFriendlyMinChars`；不够=待改进）
   3) 占比高不高（≥ 25%；偏低=待改进）
   抽成纯函数 `cacheStatus(layoutOK, stable, ratio)` 单独测优先级。

### 两个设计决定

- **样本同时变目标和 cwd**：`measurePromptPrefix` 用两个不同目标 **+ 两个不同工作目录**。
  只变目标的话，若有人把工作目录挪到提示词前部，两份样本 cwd 相同、公共前缀照样穿过去，检查就漏了。
- **CLI 版不能用 `NopNotifier`**：最初硬传它，第 4 项永远报"未接入审批通道"。
  体检结论必须反映真实运行环境 → 改用与 `gleam goal` 一致的 `newConsoleNotifier()`，
  并支持 `--config/--workspace/--data-dir/--mock-llm`。

任何编辑器 / IDE 都能接，**不绑定任何具体宿主**。对外统称「编辑器插件 / 宿主」。
ZCode 只应出现在「本项目由什么搭建」的语境里。

### 踩坑：设计文档是 CRLF，不是 LF

- 全仓库文本多为 **LF**，但 `Gleam 技术设计文档.md` 是**统一 CRLF**（768/768）。
- 我用 Python 脚本按行号替换时用 `"\n".join(lines)` 写回，**新写入的行成了裸 LF**，
  把文件搞成 MIXED（757 CRLF / 11 裸 LF）。
- 修复：把所有行补齐 `\r`，恢复 768/768 统一 CRLF。
- **教训（重要）**：改文件前先**量行尾**（Python 数 `\r\n` 字节），
  不要相信「全仓库 LF」这种整体印象；`newline=""` 读、按行替换后要显式保住 `\r`。
- 顺手把 `website/style.css` 末行一处游离 CRLF 规范为 LF（其余 741 行本就是 LF）。

### 脚本踩坑：整文件残留断言不能放在单行替换之后

第一版脚本对 `cmd/gleam/main.go` 改完第 6 行就断言"整文件无 ZCode 残留"，
而第 106 行还在 → 断言失败 → **整个文件没写盘**。
正确做法：**先把一个文件的全部行改完，再做残留断言，最后写盘**。

## 文章研判：《模型变强之后，Skill 和 Prompt 该做减法了》

来源：七牛开发者，2026-09-20。属**二手综述**（转述 OpenAI / Anthropic / Mistral / Google 的说法），
无原创工程数据。核心主张：模型变强后，为弱模型准备的规则、每次加载但用不到的资料、

### 三条结论

1. **Gleam 已经做对了文章里大半的事**：验收标准（＝完成条件，且要求"可判定"）✓；
   能力菜单 = 工具层的渐进式展开 ✓；版本化技能 ✓。文章的增量价值集中在**减法 + 评测 + 版本追溯**。
2. **最具体的减法候选：`## 定时/周期任务` 734 字节恒定加载**（只要注册表里有
   `schedule.create` 就注入，与本次任务是否涉及定时无关）——正是文章说的
   "每次任务都会加载但多数时候用不到的资料"。第一刀：压成一两行意图指针，
   细节移到 `schedule.create` 的工具描述里，只在选中该工具时才加载。
3. **但 Gleam 有个文章不知道的约束：稳定段是被前缀缓存命中的**，那 734 字节的
   *token 成本*已经被折扣了。所以减法的收益不是省钱，而是**减少注意力稀释与指令冲突**——
   这意味着**没法用"省了多少 token"来论证，只能靠评测验证**。评测是前提，不是可选项。

### 关键设计约束（本次推导，之前没记过）

- **规则开关只能挂在「稳定维度」上**（模型档位 / 角色 / 任务模式），
  **绝不能挂在「本次任务」上**——否则稳定段逐任务变化，前缀缓存全碎。
  规则集按档位整体切分是可以的（缓存本来就是按档位分的）。
- 文章主张"旧规则会害模型重复测试/过度验证"，Gleam 里对应的具体条款是
  `promptCodeMode` 第 3 条「涉及代码修改后必须安排验证步骤（构建/测试/运行）并检查输出」
  ——**与 OpenAI 举的例子几乎逐字相同**。删它是否有害，目前**无法回答**（没有评测）。

### 工程事实（值得长期记住）

- **规划器系统提示词里根本没有「用户目标」**。目标走独立 user message。
  所以拿两个不同目标去比系统提示词的公共前缀，结果**必然 100% 相同**（我一开始就被这个骗了）。

  （`stable,_,_ := llm.SplitCacheBoundary(a,b)` 取 `len(stable)`）。

### 设计要点（值得长期记住）

- **范围只能落在稳定维度上**（模式 / 档位 / 角色），由签名兜住：`renderRules` 拿不到 `goal`，
  想按目标开关也开关不了。缓存本来就是按这些维度分的，按它们切规则等于"每类任务各缓存一份"。
- **同一 ID 可注册多条，先匹配到的生效**（变体在前、兜底在后）——这就是条件化，调用方不必写 if。
  兜底版排到变体前面会让变体永远轮不到（死代码且不报错），有测试钉顺序。
- **判据用「生效档位」而非角色「声明」的档位**：声明只说明这个场景**建议**用哪一档，
  没配时角色照样跑在主模型上；拿声明档位切规则会切出"跑着主模型、却按强模型的口径删规则"的错配。
- **档位名描述的是用途不是能力**（economy 低难度 / 编码强 / 办公写作强 / 推理强），
  所以不能从档位名猜强弱。判据换成"用户有没有为这一档单独配模型"——那是他能直接表达的信号。
- **条件化的底线是"换措辞，不是删底线"**：变体保留"要验证"，只去掉"反复"的推力。
  Gleam 里没有别的机制保证代码改完会被验证。

### 资产化的第一要求是"不改一个字"——这次唯一的真 bug 就是它抓出来的

重构前先把 5 个 (角色, 模式) 组合的 `buildSystemPrompt` 原样导出，重构后逐字节比：
**21356 字节完全一致**，`gleam eval` 提示词合计 82964 也一字不差。

比对当场抓出一个真 bug：`code.verify` 的**兜底版漏了 `Modes: []string{"code"}`**，
于是**工作模式的提示词里凭空多出一条「涉及代码修改后必须安排验证步骤」**。
规则表看起来毫无问题、规则自身的测试全绿——只有逐字节比对能发现。
教训：**兜底兜的是档位，不是模式**；加变体时每个维度都要写清楚。

### 效果（要说实话）

  economy 与未模拟相同（都走强制版）。

### 工程事实（新增）

- **`--tier` 是量测开关不是模型开关**：只改提示词构建看到的档位，不切换客户端。
  它同样改变提示词，所以 `Compare` 加了与"跨深度"同款的拦截——跨档位比直接报错，
  而不是把措辞差异报成一片回归。
- **`gofmt -l .` 在整仓库上会报 25 个文件**（不是"只有 std.go"）：两类成因——
  文件头 **UTF-8 BOM**（growth/auth 等一批）与结构体 tag 对齐列不同；`cmd/gleam/main.go` 是 import 排序。
  **判断"是不是我弄坏的"要只对自己改过的文件跑 `gofmt -l`**；本次 agent / eval / cmd/gleam/eval.go 都干净。
- **设计文档插入段落必须转 CRLF 再写**：脚本里的守卫（写入前断言"无裸 LF"）当场拦下过一次——
  我写的插入段是 `\n`，直接写会把 CRLF 文件变 MIXED。
- **逐字节比对的姿势**：临时导出测试先跑一份 before 存 `$TEMP` → 改代码 → 再导出一份 after →
  用 Python `difflib` 比。比人眼可靠，且能区分"只有空白差异"与"真的改了字"。
- **体积守卫里顺手 `t.Logf` 分段体积**，实测数字就从 `go test -v` 里直接拿到，不用另写脚本。

### 关键决策与踩到的坑

- **指纹从内容派生，不手写版本号**：手写会忘改；`Scope` 也要进指纹——同一句话换个适用范围，
  行为就变了，不算同一版。
- **指纹与 ID 列表互补**：加一条只对 code 模式生效的规则 → work 模式 ID 列表一字不变、但指纹变；
  改一句措辞 → ID 不变、指纹也变。两者都得看。
- **对话模式留空**（`ActiveRuleIDs` 里就判断，不放调用方）：它直连模型、不经规划，
  一条规则都没用上；记成"用了契约段三条"是撒谎，会让翻日志的人往错方向排查。
  RunGoal / 评测 / `gleam rules` 三处必须得出同一结论，所以判断放在一处。
- **规则集变化只报、不卡门禁**：改规则是正常动作，卡它会逼人摘掉 `--strict`，门禁整体失效；
  但回归报告里必须可见——**有回归时第一条该怀疑的是规则改了，不是代码改坏了**。
- **`gleam rules` 不装配运行时**：规则表是编译期常量；排障时往往正是配置/模型坏了才要查规则。
  用 `--task-mode` 而不是 `--mode`——后者在 `gleam goal` 里是执行模式，同名不同义。
- **⚠ 变异验证逼出来的边界：ID 列表区分不了变体。** 把 `ActiveRuleIDs` 改成忽略档位，
  **全部测试仍然绿**——`code.verify` 两个变体共用同一个 ID。**测试绿 ≠ 行为被守住**，
  动手前先问"这个断言看不看得见它"。改成两条可观测的变异（忽略模式 / 重复记账变体）后全响，
  并把这条边界写成显式断言 `TestActiveRuleIDs_CannotDistinguishVariants` 钉住。
- **⚠ 变异脚本把 4 个 Go 文件整份改成了 CRLF**（`io.open(path, encoding='utf-8')` 读写，
  Windows 下读翻 `

  **还原 ≠ 原样**：临时脚本收尾必须对所有碰过的文件跑行尾 + gofmt 复核（已写进 release-verify 技能）。
