### 本批关键设计判断

1. **看门狗必须放 goroutine**：`scanner.Scan()` 阻塞期间主循环拿不到控制权，计时器到期也无法响应 → 读取放独立 goroutine，主循环 `select` 计时器与行通道；读完 `close(lines)` 自然退出，`select ctx.Done()` 防泄漏。
2. **重置计时器要先停表排空再 Reset**：`timer.Stop()` 返回 false 时管道里可能残留到期信号，必须 `select { case <-timer.C: default: }` 排空，否则上一次的到期会被误读成本次超时。
3. **`onLine` 返回 bool 而非让调用方 break**：Go 闭包不能 break 外层循环 → 用「返回 false = 处理者要求停止」表达，`[DONE]`/终态事件统一映射为 false。语义从「跳转」变成「请求停止」，超时也因此能区分「正常结束」与「被处理者叫停」。
4. **边界只有一处实现才叫纵深防御**：`within`/resolve 从 file 包提升到 toolutil → 「两条路径各写一份边界，就会出现『文件工具挡住了、shell 绕过去了』这种缝」。`filepath.Rel` 而非字符串前缀（`/ws2` 不该被当成 `/ws` 的子路径，有测试守着）。
5. **失败要朝安全方向失败**：`ResolveInRoots` 在 roots 为空时一律拒绝 —— 「没配边界就放行，等于把『忘了配置』变成一次越权」。
6. **凭证隔离是「拿开凭证」不是「清空环境」**：保留其余全部变量，清空会让命令跑在陌生环境里、排查成本远高于收益；只拦几乎确定是凭证的模式（`TOKENIZER_PATH` 不该被判为凭证，有测试守着）。
7. **审计追加而非重写**：JSONL + `O_APPEND` —— 「审计的价值在于『发生过什么』，重写会把它变成『当前状态』，且崩溃时丢全部」。**只读不记**（无副作用，记下来只是噪音，会把真事件淹掉），判据是 `dec.Risk != "low"`。
8. **等待审批「进行中」就落盘、有结果即摘除**：唯一能观察到「审批进行中」的时点是在 Notifier 回调里 → 测试夹具 `probingNotifier` 在 `OnApproval` 里探查 `PendingApprovals()` 与文件内容，证明「审批期间就落了盘」而不是「结束后补写」。

### 成本半边：实测数据（内置 23 个工具，空载，`llm.StablePrefixLen`）

**关键洞察（与清单假设不同）**：清单把「工具菜单关键词筛选」定性为「为旧模型弱点加的补丁」，
但它的真实性质是**提示词体积 × 缓存前缀的权衡**，而且方向可能反了——
`toolSchemaSection(goal)` 是**第一个易变段**（planner.go:536 注释「易变段」），
它按目标筛选 schema，于是可缓存前缀被**截在它之前**。全量注入时 schema 段与目标无关、
整段稳定，前缀从 49.6% 涨到 100%。

按缓存读价 d 折算的盈亏平衡：`2452 + 2409d = 6833d` → **d ≈ 0.554**。
即缓存读价低于全价的 55% 时，全量注入的**计费**反而更低（d=0.25 时低约 44%）。
唯一反转条件是**缓存命中率低**（桌面端使用零散、TTL 通常 5 分钟）——命中率≈0 时菜单模式省 29%。

### 顺带查到的两个事实（都不是阻断项，但值得记）

1. **`max_steps: 0` 关不掉上限**：`planner.go:635-641` 有一份 `maxSteps = 12` 兜底，

   `MaxTokensPerTask` / `StuckThreshold` / `MaxOutputRunes` / `MaxToolSchemas`）都写明「0 表示不限」，
   只有 `MaxSteps` 例外。这是「同一个常量写两份」的老形态（与 P5-1 的 within 同源）。
   **但它不是实验阻断项**——要测「不设上限」直接配 `max_steps: 1000` 即可，无需改语义。
2. **步数期望的弱信号**：内置 16 条用例里只有 4 条带步数区间，最大期望是 10（`code-add-test`，
   holdout 层）。上限 12 只比最高期望高 2 —— 说明作者写期望时观察到过接近 10 步的计划，
   上限不像纯死重。但样本太小（4 条），不足以支撑结论。

## 减法实验实跑完成（同日第六批）：工具菜单无影响、步数上限从未触发

用户给了 key 与模型名 `deepseek-flash`，质量那半边补上了。全部实验文件用后即删，数字在此留档。

### 实验设置（可复现）

```

gleam eval --depth plan --config <实验配置> --data-dir <临时目录> --workspace <项目>/dist --json
```
**关键技巧**：用 `--data-dir <临时目录>` 让 `LoadOverlay` 找不到 `settings.yaml`，否则
**覆盖层会在 `applyEnv` 之后生效、把 `GLEAM_LLM_MODEL` 顶掉**（`config.Load` 里先 applyEnv，
`buildRuntime` 后加载覆盖层）——想用环境变量改模型就必须绕开覆盖层。

### 结论一：拆掉工具菜单，选择准确率**测不出差异**

| 对比 | 配对 | 工具集不同的用例数（满分 16） |
| --- | --- | --- |
| 菜单×菜单（**噪声基线**，4 次运行两两配对） | 6 | 均值 **3.00**（2..4） |
| 全量×全量（**噪声基线**，3 次运行两两配对） | 3 | 均值 **5.67**（4..7） |
| 菜单×全量（**处理效应**） | 12 | 均值 **4.83**（3..7） |

**处理效应落在两条噪声基线之间**——即「菜单 vs 全量」的差异**小于同配置重跑的差异**。
逐用例检查：**没有任何一条用例的工具集在两组间完全无重叠**（即不存在稳定差异）。
组内变异度：菜单 1.38 种/用例、全量 1.56 种/用例。

- 温度 0 **也没能消除噪声**（A0 16/16、A0b 15/16），provider 侧不保证确定性 →
  这类对比**必须靠重复采样量噪声基线**，单轮 16 条得出的任何差异都不可信。
- 提示词成本确认：**83994 → 109758 字符（+30.7%）**，与离线量测的 +30.9% 吻合。

**一个稳定机制（7/7 一致）**：`work-analyze-sales` 里全量组 3/3 都用了 `file.search`，
菜单组 4/4 都没用。原因是菜单模式会明确告诉模型「只能使用上面附了 schema 的工具；
菜单里的其他工具本次不可用」——**菜单把 top-12 之外的工具从"可用"降级为"知道但不可用"**。
全量注入解除了这道门。该用例既没 want 也没 not_want `file.search`，两边都通过。

### 结论二：`MaxSteps = 12` **从未触发过一次**

- 16 条评测用例 × 8 次运行：最大步数 **7**（各次 max：6/4/7/5/7/5/5/5）。
- 6 条**故意宽泛**的目标 × 3 次运行：最大步数 **10**（`broad-refactor`）。
- 146 次规划观测里，**没有任何一次报「步骤数超过上限」**。
- 判据「不设上限时步数分布自然收敛」→ **成立**（自然收敛在 1~10 步）。

但**余量只有 2 步**（10 vs 12），所以「拆」的形态应该是**抬高上限**而不是取消上限。
更值得记的是：**真正的硬约束不是 `MaxSteps`，而是输出 token 预算**——
宽泛目标在 `max_tokens: 4096`（生产默认值）下会产出**未闭合的 JSON**（`broad-workspace`
报「JSON 对象未闭合」、0 步）；抬到 16000 后同一条变成 **8 步通过**。
即计划爆炸会先被输出预算截断，`MaxSteps=12` 是叠在上面的第二道闸。

### 顺带发现

- **`max_tokens` 键名是复数**（`llm.max_tokens`），`configs/config.yaml` 与 `settings.yaml` 都是 4096。
- 宽泛目标下还有一类失败与上限无关：模型输出**语法错误**的 JSON
  （`invalid character ':' after array element`），`extractJSON` 宽容解析也救不回来。
- 失败用例的 `min_steps: 1` 在报错时显示成「步数在 1..0 之间」，是 `max_steps` 缺省 0 的
  显示口径问题（不影响判定，但读报告时会困惑）。

### 建议（等用户拍板）

1. **工具菜单**：无证据表明拆掉会伤选择准确率，且计费大概率更省（离线量测：缓存读价 <55% 时全量更便宜）。
   但既然差异测不出，**"拆"的收益主要是少一层代码**，不是准确率——可拆，但不是必须。
2. **`MaxSteps`**：判据成立，可抬不可废。建议 `12 → 32`（远高于观测到的 10，仍能挡住真正的失控），
   并**同时改掉 `planner.go:637` 那份重复的 12**，否则又是两份边界。
3. 若要更硬的证据，需要 `temperature` 可控的模型或 ≥5 次/配置的重复采样——本次 3~4 次仍偏少。

### 关键发现

1. **验收旁路是两条独立路径，只堵一处等于没堵**：`acceptanceSatisfied` 管"循环要不要继续"，
   `applyAcceptanceVerdict` 管"对外怎么声称"。只改前者 → 循环不早退 → 走到最后一次尝试 →
   `statusOfExec` 仍判 `GoalSuccess`。
2. **85 分是同一个洞的第二条路**：项目自己的规则是"有验收标准时分数一律由 checks 算"
   （`scoreFromChecks` 对空 checks 返回 0），给 85 既违背规则、又恰好越过 `DoneThreshold=80`。
   → 分数必须同时改成 0。
3. **「不要卡死」的诉求改由状态层满足**：落 `GoalPartial`（步骤都成功了，不必说失败）+
   `Error` 写明"验收未能核对"，而不是靠放行。`Failed` 不会被 `applyAcceptanceVerdict` 翻案
   （它只纠正"被误判为成功"的结论），所以 `Partial` 是唯一正确落点。
4. **不可归因 ≠ 证明无差异** → 推翻拆除决定。实测处理效应 4.83 落在噪声基线 3.00/5.67 **之间**，
   而判据原文写的是"选择准确率不下降"。拿不可归因的证据删一个用户可见的安全阀（设置页
   `max_tool_schemas`）是草率不是精简。叠加两条反证：内置工具 23 个已越过资料所述"约 20 个
   活跃工具表现下降"的门槛；删除面牵到 web 设置页、成本看板 `tool_pick` 归因、约 30 处测试
   → 属**产品变更而非内部重构**。**正确顺序：先补可重复性指标，再用重复采样实测判定。**
5. **出网有三条路径**：`httputil.postJSONOnce`（非流式）、`openStreamOnce`（流式）、
   `glm.go` 的 `do()`（GLM 自走 HTTP）。**只给非流式留痕会留下安静的盲区——对话模式走的就是流式。**
   用包级钩子（`llm.SetEgressHook`）而非给三个客户端各加字段：出网路径已收敛、装配点只有一处，
   逐层传参是管道工程且以后新增协议必然漏掉一个。
6. **边界写在签名上**：`RecordEgress(kind, host, nbytes)` / `EgressFunc(host, nbytes)` ——
   调用方手里**根本没有正文可传**，也就不可能不小心把它写进审计。把请求正文写进 `audit.jsonl`
   等于把风险从"网络"搬到"磁盘上的日志"。
7. **`denied` ≠ `egress`**：`web.fetch` 的留痕放在 `guardURL` 之后、发包之前。被拦下的请求
   根本没出网，混在一起审计就会把"发给了谁"变成"想发给谁"。
8. **审计过滤要先全读再筛**：先取最近 50 条再筛，稀疏的出网记录会被别的留痕整个盖掉，
   看起来像"什么都没出网"——**一个查不出问题的审计比没有审计更危险**。

### 本批新踩的坑

1. **变异脚本的 stdout 块缓冲**：`> _mut_all_out.txt` 时 Python 输出全卡在缓冲区，
   跑着的时候文件一直是 **0 字节**，看起来像"脚本根本没启动"（实际在跑，python + go 进程都在）。
   → 必须 `python -u`。
2. **变异体必须"能编译"**：M7（`&rate` → `nil` 让 `rate` 未使用）、M9（去掉
   `config.DefaultMaxSteps` 让 import 未使用）只拿到 `FAIL ... [build failed]`。
   **编译红只能证明"这行是承重的"，不能证明"测试断言抓得住这个行为"**。判据：必须出现 `--- FAIL`。
   已用能编译的变异体补验三处 → 全部断言红。
3. **`consume(bak(p))` 双重套用**：助手内部已含 `bak(p)`，我又套了一层 → 去找
   `xxx.probe.bak.probe.bak` → `os.replace` 抛 `FileNotFoundError`，**且发生在恢复路径上**。
4. **多参数 `rm` 被 SIGTERM 拦截**（第四批记过，本批又踩）：`rm -f a b c d` 整条被杀、
   只生效前几个。用 `for` 循环、每轮 ≤4 个、删完 `find` 回读确认。

## 第九批 · 减法实验实测判定（同日第九批）：能力菜单保留

### 做了什么

用第八批刚落地的 `gleam eval --repeat N`，把「能力菜单该不该拆」这条悬着的判定做掉。

实验：两个数据目录只差 `agent.max_tool_schemas`（12=菜单 / 0=全量），
两边各跑 `--depth plan --repeat 3`，16 条用例，**跑两轮互相独立**。
`max_tokens` 抬到 16000（消掉"JSON 截断"这个已知混淆项）。

### 结果

| 轮次 | 臂 | 通过 | 提示词 | 一致率 | 不稳 |
|---|---|---|---|---|---|
| 第1轮 | 菜单(12) | 16/16 | 83,482 | 69% | 5 |
| 第1轮 | 全量(0) | 16/16 | 109,246 | 50% | 8 |
| 第2轮 | 菜单(12) | 16/16 | 83,482 | 38% | 10 |
| 第2轮 | 全量(0) | 15/16 | 109,246 | 44% | 9 |

### 三个关键发现

1. **可归因差异两轮都是 0 条**：在两臂都稳的范围内，工具集/步数/通过与否完全一致；
   合并口径（两轮都稳）也是 5/16 对 5/16。
2. **成本收益是确定的**：提示词小 **24%**（83,482 vs 109,246），两轮**一模一样**——算术而非统计。
   → 判定**保留**。结论与原先假设相反：不是"拆掉也没事"，而是**拆掉纯亏**
   （拿确定的 24% 提示词收益换一个测不出来的质量改善）。比"不可归因所以保守不拆"更强。
3. **可重复性指标自己也需要噪声基线**（本批最重要的方法论）：
   第1轮 69% vs 50%（差 19pp）看着像"菜单更稳"，第2轮 **38% vs 44%，符号反了**，合并后相同。
   逐条看原因清楚：**用例自身的稳定性是稳定的**（`file-write`/`file-list`/`work-analyze-sales`/
   `code-add-test` 四格全抖；`schedule-weekday-report`/`schedule-list`/`web-fetch` 三格全稳），
   会变的只是"这次抖几条"，而 16×3 下这个计数有 **±2~3 条**误差。
   → **要比较两个配置的稳定性，一轮 16×3 不够，至少两轮独立测量看方向是否一致。**

### 另一个值得记住的事实

`deepseek-v4.1-flash`（temperature 0.3）逐次一致性只有 **31%~69%**——大多数用例单跑一次
接近掷硬币。**通过率必须配合可重复性一起读**，否则会把噪声当结论。

### 顺带发现的坑：配置覆盖层把默认值钉死

改 `DefaultMaxSteps` 12→32 后本机**没生效**——`~/.gleam/settings.yaml` 有 `agent: max_steps: 12`。

- 根因：`SaveOverlay` 是**全量快照**（不管用户动没动过都写）；MCP 空列表与 `tiers` 空表
  更是**故意要写**（覆盖 `config.yaml` / 表达清空）→ 这是"覆盖层权威"的有意设计，不是疏忽。
  加载侧又是"覆盖层赢" → **一旦保存过设置，所有默认值被钉死，之后改任何默认值都不生效**。
- **没有改成"只写非默认字段"**：需要一张例外清单（`tiers`/`mcp`/`workspace` 的零值都带
  "清空/覆盖"语义，不能省），清单本身比这个坑更脆 → 属"臃肿"。
- 落点：把坑写进 `SaveOverlay` 注释 + 立操作纪律「**改默认值后要确认已有安装的
  settings.yaml 有没有把旧值写进去**」。
- 顺带回填：`config.go` 注释里"当前内置 21 个"→ `gleam tools` 实测 **23** 个。

## 第十批 · 复核 P0-1 波及面 + 对话自检失败路径补漏（同日第十批）

### 复核：P0-1 的三条路径全部干净

- **工作模式**：`Verdict:"replan"` 与 `Score:0` 是同一信号的两种表达，在
  `(Verdict=="done" || Score>=80) && acceptanceSatisfied(...)` 这**一个**门里只判一次，
  不会双重触发；最后一次尝试时由 `finalize` **首行**的 `applyAcceptanceVerdict`
  把 `GoalSuccess` 校正成 `GoalPartial`——在写成长统计之前，不会被当成成功记档。
- **技能路径**：`plan.Acceptance` 恒空 → `applyAcceptanceVerdict` 直接 return。
- **对话模式**：`applyChatCheck` 在 `len(checks)==0` 时提前 return，新分支不可达。

### 补漏：对话自检"跑了但没跑成"时静默保留满分

**问题**：对话模式核对调用失败 / 输出读不出来时，结果仍是 `Score: 100`——
"干活的自己报满分"正是这个功能要消灭的东西，却在自己的失败路径上复现了一遍。
根因：**"不值得核对"（开关关、闲聊）与"核对了但没成功"被压成同一个 `ok=false`**。

**修法**：拆成三态 `chatCheckSkipped` / `chatCheckDone` / `chatCheckUnusable`；
只有 `Unusable` 会发提示「对话自检未能完成，本次回答未经核对」。

**关键判断：不能改分数。** 一度想照 P0-1 的做法把分数改成 0，查了前端才发现
`scoreRing()` 会把 `<40` 渲染成**红色的"完成度 0/100"**，还有 toast 与成长均分——
那是在**往反方向说谎**（回答可能很好，只是没核对）。所以能做的只有
"让没核对过这件事本身可见"。

**为什么不像工作模式那样落"部分完成"**：差别不在"有没有放行"，而在**有没有先前的承诺**。
工作模式的标准是规划器**动手前**定下的 → 核对不了就不该声称完成；
对话模式的标准是核对者**事后**提炼的 → 核对器一挂等于标准从未存在，放行与
"没有验收标准就放行"是同一条规则。
**同一个 fail-open 动作，在有承诺的地方是漏洞，在没有承诺的地方是常识。**

### 一条重要的判断纪律（本批最大的收获）

**"有意的 fail-open"与"意外的 fail-open"要分开处理**：
- 前者（对话自检）有测试锁定（`TestChatSelfCheck_FailureKeepsOldBehavior` 明确断言
  "失败时保持成功/满分"）→ 说明它是设计选择 → **改口径 / 补可见性，不推翻设计**。
- 后者（P0-1 工作模式）没有测试锁定、且效果是让整道闸失效 → **改代码**。
判据：**先去看有没有测试把当前行为锁成契约**。有 → 尊重它；没有 → 再判断是漏洞还是设计。

### 验证

- 新增 2 条测试、改写 2 条（把 `ok=false` 的断言细化为各自的结局）。
- **4 处变异全部捕获**（去掉 Unusable 分支 / 解析失败归 skipped / 调用失败归 skipped /

## 第十一批 · e2e 脚手架从"必然报红"改成"能跑"（同日第十一批）

收尾第十批时发现全量测试里 e2e 5 条恒红，追下去不是回归，是**脚手架缺陷**。

- **根因**：`internal/e2e` 的 `buildBinary` 在 `GOCACHE` 未设置时**每次新建一个临时缓存目录**
  → 每次都是冷编译 → 本机冷编译超过它内部 2 分钟预算 → 5 条全部「构建超时」。
  即**只要没显式导出 `GOCACHE`，整套 e2e 必然报红**。一个永远报红的测试比没有测试更糟：
  它会训练人忽略红色，真回归也被一起忽略。
- **修法**：`GOCACHE` 未设置时回退到 `go env GOCACHE`（标准缓存，显式设置仍优先）；
  构建预算 2 分钟 → 5 分钟（预算只是"编译卡死"的兜底，不是性能指标）；超时信息补预热提示。
- **对照验证**：修复前 `unset GOCACHE && go test ./...` → e2e 5 条超时、exit=1、2m39s；
  修复后同一条命令 → **26 包全 ok、exit=0、32s**。热缓存下单跑 e2e/webui = ok 14.6s / ok (cached)。
- **顺带清理**：`pack/CHANGELOG.md` 每批前插时都带了一次 H1 与 `## 日期`，累积出 3 个重复标题 +
  3 个同日分节 → 合并为 1 标题 + 1 个 `## 2026-09-21`（8 个小节）。体量 36767 → 37419 字符。
- **设计文档**：§4.6.16 新增「（5）端到端测试脚手架从"必然报红"改成"能跑"」；
  §4.6.5.1 里把对话自检三态拆分误写成「第八批」，已改回「第十批」。
- **顺带：全仓通过 gofmt**。`gofmt -l internal/ pkg/ cmd/` 原本有 **28 个文件**不合格
  （真实缩进漂移，非行尾符）；其中 7 个文件头带 UTF-8 BOM。`gofmt -w` 一把过（+148/-145 行），
  **先备份再改**（无版本控制），改完做「去空白后逐字节比对」→ 9 个不等，查明只有两类：
  **BOM 移除**（7 个）与 **import 重排**（`scheduler/cron.go`、`cmd/gleam/main.go`）。
  验证：`gofmt -l` 空、全量 26 包 ok、`go vet ./...` 零输出。CHANGELOG 36767 → 38157 字符。
- **官网**：「工程质量」分组补 1 张卡「测试门禁自己也得可信」→ **40 卡片 / 6 分组**，

  靠标签计数立刻发现并补回。**改 HTML 后必须数标签，不能只看局部**。）

**教训**：**"测试失败"先分三类——代码回归 / 环境缺陷 / 脚手架缺陷**。e2e 的红色最初被当成

## 第十二批 · P4-2a 验收确定性层：把产物核对从自述里拿回来（同日第十二批）

- **问题**：反思器看到的每步只有**截断 300 字的工具自述**，"说写了其实没写""写到别的路径去了"
  "只写进去一半"它看不出来——它拿到的文字说成功，就只能按成功判。这是"干活的自己给自己打分"
  的另一种形态：不是分数自评，而是**事实自述**。
- **同形状的第二个洞**：`statusOfExec` 只看步骤计数，而 `acceptanceSatisfied` 在**没有验收标准时
  直接放行** → 一个没有验收标准的任务，只要每步都报成功，哪怕说好的文件根本不在，
  也会以「已完成」收尾。与 P0-1 同一个形状。
- **做法**：新增 `internal/agent/artifact.go`，对 `file.write` / `file.mkdir` / `file.move` /
  `file.delete` 做事后核对（存在性 + 长度；move 的**两端**都查）。事实两个去处：喂给语义层
  （digest 末尾加「产物核对（代码实测）」段，把自述换成实测）+ 当硬闸门
  （`Evaluate` 一票否决 / `completionReached` 独立判 / `applyAcceptanceVerdict` 校正状态，**三处都堵**）。
- **关键取舍**：**按路径收敛、后写覆盖先写**（否则"写完又删"会被误报成产物丢失，而假警报会让
  这道闸很快被当成噪音关掉）；长度校验最值钱；**宁可不判不可错判**；**闸门不看有没有验收标准**
  （判的是现实不是承诺）；**不改分数**（只改结论——`Score` 的口径是"验收标准通过比例"，
  塞合成条目进去会把口径弄脏）。
- **完成判定抽成 `completionReached`**：原先是一个长条件，少写一句看不出来；拆开后三条守卫
  （分数/verdict、验收标准、产物核对）各自可测。**不能只压 verdict**——第一句是
  `verdict=="done" || score>=阈值`，压成 replan 后**分数达标的半边仍会放行**。
- **验证**：新增 `artifact_test.go` 15 条；**8 处变异全部会响**（连跑两次结果一致）；全量 26 包 ok。
- **P4-2 的另一半未做**：换用与执行者**不同档位**的核对模型，以及"格式合法"这类更深的确定性判定。

**本批最贵的教训（脚本，已写进技能）**：变异脚本的恢复路径**不能碰 `os.remove`**——本环境
safe-delete 垫片把它劫持成"移入回收站"，无桌面会话时抛 `SHFileOperationW 失败: 0x2`，
崩在 `finally` 里，**整个验证带伤运行**。症状是某几处变异莫名"未被捕获"、两次结果还不一致，
极易被误判成"守卫不承重"从而去改代码。修法：**恢复用内存里的原字节**、快照只在开头写一次、
结尾用 shell 的 `for` 循环清理，**Python 全程不删任何文件**；写文件一律 `with + flush + fsync`
并回读确认变异已落盘。**判据：结果不稳定就是脚本的问题，先别改测试。**

### 第十三批 · 收尾核对抓回一次格式门禁回归（CRLF）

- **现象**：P4-2a 收尾跑最终核对，`gofmt -l` 报 4 个文件不合格——
  正是本批用 Python **文本模式**改过的 4 个测试文件
  （`acceptance_test.go` / `outcome_test.go` / `promptcache_test.go` / `reflector_test.go`）。
  刚在第十一批把全仓格式统一，自己又打翻了。
- **根因**：为 `buildDigest` 补第 5 个参数时用 `open(p,'w').write(s)` 批量写回。
  Windows 下文本模式写会把 `\n` 翻成 `\r\n`（已实测：`open(p,'w')` → `\r\n`，`open(p,'wb')` → `\n`）。
  正确写法：`open(p,'wb')` 自己编码，或 `open(p,'w', encoding='utf-8', newline='')`。
- **判定过程又踩一坑**：先用 `grep -c $'\r'` 判行尾，得出"8 个文件全 CRLF"的**错误**结论；
  换 `od -c` 才看清只有 4 个真是 CRLF（`artifact.go` 是 `\n`）。
  **本机 Git Bash 的 `grep -c $'\r'` 是假阳性**——这条技能里早写过，仍栽了第二次。
- **修法**：`gofmt -w` 那 4 个文件，并用 `tr -d '\r' < f > f.check` + `cmp` 证明
  **只动了行尾、没动内容**（4 个全部一致）。复核：`gofmt -l` 空、残留空、
  `go test -count=1 ./internal/agent/...` 全绿。
- **技能同步**（`gleam-release-verify`）：① 旧的"仓库有 25 个历史漂移文件、别全仓 `gofmt -w`"
  **已过时且现在有害**（会把人劝退），改为"2026-09-21 起清零，`gofmt -l` 有输出一律算自己的问题"；
  ② 示例代码里那个 `os.remove(f+'.lf')` 换成 shell 清理（safe-delete 垫片会崩）；
  ③ "Python 文本模式"规则从"变异脚本"扩到**任何写仓库文件的场合**，并补上"只动行尾"的 `cmp` 证明法。
  `gleam-external-source-mining` 同步一句。

### 第十四批 · P4-2b 独立验收者：验收换档位 + 格式合法

- **① 验收换档位**：原先 `reflector := &Reflector{LLM: mainLLM}`，注释还写着"规划、反思、对话都走这个客户端"
  ——"独立验收"只体现在"独立调用 + 独立上下文"上，**干活的模型仍在给自己打分**。
  改为走 `VerifyLLM(role)`：默认点名 `reasoning` 档（`DefaultVerifyTier`）。
  抽出 `tierLLM(tier)`（按档位名取客户端），`TierLLM(role)` 变成它"先由角色解析档位"的包装。
- **判据只有一条：模型 ID 不同**（不是"档位名不同"）。两个档位名指向同一个模型不构成独立，照旧回退。
- **换不成要如实回退，不许随便挑一个顶上**：刻意**不**去挑 economy/coding 档或主模型——
  拿一个没有理由信任的弱模型去判强模型的产出，只会得到"看起来独立"的橡皮图章，**比同源自评更难发现**。
  已知限制：`analyst` 这类角色自己就声明 `reasoning` 档 → 换不成、走回退（内置 7 个角色里 5 个能换成）。
  这条写进代码注释与就绪诊断。
- **回退不是错误，但不能假装独立**：新增 `VerifyModel`（只算名字、不建客户端），
  就绪体检据此明说"独立验收生效"还是"与执行者同源"——**把承诺变成可核对的事实**。
- **② 格式合法**：确定性层补上唯一一处读内容的例外——`.json` 能不能解析。
  取舍全在防假警报：只认扩展名（**csv 刻意不查**，列数不齐也可能是合法数据）、只查覆盖写
  （追加写可能只是往尾部贴一段）、放宽一档（**JSONL 常被写成 `.json`**，逐行合法也算通过）、
  顺手容忍 BOM。
- **两处清理**：删掉已无人使用的 `mainLLM`；`applyAcceptanceVerdict` 的收尾文案
  "代码实测没找到说好的产物" → "代码实测对不上"（产物可能**在**，只是坏的）。
- **关键手法：接线断言**。`VerifyLLM` 自己正确 ≠ 被接进主循环。所以造两个假客户端，
  执行者那个的反思脚本故意给低分（`score=10/replan`）、验收那个给高分，断言最终成功且

## 第十五批 · 交付侧一次性口径：首次验收通过率 / 返工轮数（#59 / P5）

**为什么现在做**：#59 此前被有意排期，理由是价值依赖两个前置——① P1-1 可重复性（说明噪声多大）、
② 稳定的验收判定层。P4-2a/P4-2b 落地后两个前置齐了，才动笔。

**落地内容**：

- `GoalResult` 加 `FirstPass`（第一轮尝试就走完流程并通过完成判定）与 `Reworks`
  （反思判未达标后**真正重新执行**的轮数）。与 `StepResult.Retried` 的区别在层级：
  那个是步骤级，回答不了"整个目标返工了几轮"。
- **规划校验失败导致的重规划不算返工**（一步都没执行，谈不上重做），
  但会让 `FirstPass` 落成 false（"首次尝试"包含"计划第一次就可用"）。
- **循环内部的事实不让外面猜**：新增 `goalProgress`（`attempts`/`reworks`/`firstRound`），
  循环写、`RunGoal` 读并 `stamp`。从结果反推不出来——重做三轮才成与一次做对，status/score 一样。
  `stamp` 两条守卫：只在进过循环时写（对话模式没"轮"，无条件写会覆盖对话管线的结论）、
  要求最终状态是成功（完成判定通过后 `applyAcceptanceVerdict` 仍可能校正成"部分完成"）。
- **分母不共用**：`FirstPassRate` 只算**记过这个口径的完成任务**（成长记录里单记一个 `Delivery` 布尔，
  而不是靠"FirstPass 是不是零值"去猜——零值既可能是没通过，也可能是没这项）。
  `ReworksTotal` 则含中断任务中断前已发生的返工（那笔钱真花了）。
- **一处刻意不做**：工作模式规划屡败回落直聊的任务留在分母里（`Delivery=true`/`FirstPass=false`）——
  把最差的从分母里摘出去是在把比率改成好看的样子。
- CLI：`gleam doctor` 用户信号块加两行（分母写在行内，不借上一句的"完成 + 中断"）；
  `gleam replay` 单任务加一行，**一次通过 / 返工 N 轮 / 没走到验收三种情形都要分得开**。
  顺带把 doctor 那段抽成 `userSignalReport(growth.Stats) string`（段里两个不同分母，
  而分母写错在终端上看起来一模一样，只有断言文本能发现）。

**验证**：新增 `internal/agent/delivery_test.go` 9 条、`growth/delivery_test.go` 3 条、
`cmd/gleam` 下 doctor 3 条 + replay 1 条；**16 处变异全部会响**；`gofmt -l` 空、`go vet` 零输出、
全量 `-count=1` 26 包 ok。

**两处 CLI 是冒烟验证的，不是单测**（调用点在 cobra 命令里，抽不动）：造 6 条完成记录 + 1 条中断，
`gleam doctor` 实跑输出 `首次验收通过率 50%（3/6，仅工作模式）` / `累计返工 4 轮（含中断前已发生的）`；
`gleam replay` 用三个任务文件分别得到"返工 2 轮（非一次通过）"/"返工 0 轮（一次通过）"/**不印**。
**这是本批唯一没有单测覆盖的落点**——将来若重构 doctor 的输出组装，记得把调用点也纳入验证。

**文档**：设计文档新增 §4.6.20；CHANGELOG 42086 → 44321 字符（该日期节 12 个小节）；
官网工程质量补 2 张卡（45 卡片 / 6 分组，标签 45:45、135:135、7:7）；README 追加一句；
审计清单"落地进度"补 P5。

**这批最该记住的一条**：**"新写一个判定"和"把它接上线"在这套代码里始终是两件事。**
`stamp` 正确、`growth.Stats` 汇总正确，但中间"写进成长记录"少接一根线，统计的分母就永远是空的——
而所有单元测试照样全绿。所以加了**接线断言**：端到端跑一遍，去读真正落盘的那条记录。
与 P4-2b 的 `VerifyLLM` 是同一个坑，**同一个坑第二次栽**。

**两个新坑（已写进技能）**：

1. **SIGTERM 默认直接终止进程，`finally` 不会执行** → 变异脚本会把源码留在变异态
   （P4-2b 就栽在这）。修法：注册 SIGTERM/SIGINT 处理器转成异常，走 `finally` 还原；
   并加开跑前的**锚点预检**（命中数不为 1 就别开跑，免得跑到一半才发现锚点写错）。
2. **判"变异是否残留"不能用 `new in text`**：`new` 常常是 `old` 的前缀或子串
   （例如 `res.FirstPass = p.firstRound` 是 `... && res.Status == types.GoalSuccess` 的前缀），
   会报三处假阳性。**要判"原文锚点是否仍恰好命中 1 次"**，那才是真判据。

## 第十六批 · 任务绑定配置快照（P2-1）

**动机**：事后留痕回答不了"是什么"。`RuleSetVersion` 只在产出时事后留痕、不绑定任务；
一个跑五分钟的任务中途改了模型或档位，前半段和后半段就不是同一套配置——而"配置变了"与
"模型发挥不稳"在数据里长得一模一样。

**做法**：`types.ConfigSnapshot` + `GoalResult.ConfigSnapshot`；`config.Snapshot()` 提供取值
（`Tiers` 深拷贝）；`RunGoal` 在**进循环之前**取一次（收尾时取，记下的是一个从未完整生效过的配置）。
只记影响行为的关键项：全量会把 API Key 明文写进 `tasks/<id>.json`，且改一个无关字段也算"配置变了"；
路径类字段不记（属于"这次在哪跑"，不属于"用什么跑"）。`gleam replay --rerun` 优先吃快照，
旧任务没有该字段时回退当前配置，但**印一行说明走的是哪一条**。

**接线断言（第三次同一个坑）**：`resolveRerunParams` 写对、组装执行器时却传 `nil` 或活配置，
单测照样全绿。所以把组装抽成 `rerunExecutor(g, live, reg, gate)`，让"用快照"这根线本身可被测试钉住。

**验证**：新增 5 + 2 + 6 条测试；**15 处变异全部捕获、无残留**（其中 2 处遇环境错误自动重试后才捕获——
变异脚本的重试逻辑第二次在承重）。端到端冒烟两个任务文件：带快照 → `参数取自任务启动时的快照`；
旧任务 → `参数回退当前配置（该任务没有快照）——差异里混着配置变化，不能全归给环境`。

**两个新坑**：

1. **CHANGELOG 结构检查必须行首锚定**：`count("## 2026-09-21")` 会命中正文里提到该标题的一句，
   报出"日期节 2 个"这种假警报。真判据是 `(?m)^## `。这次它又咬了一次（把"该节 13 个小节"误报成 5）。
2. **布尔字段的"漏拷"测不出来**：`DedupeCalls` 默认值就是 true、`ReflectEachStep` 默认 false，
   而 false 恰好等于"字段没被拷贝"的零值——只拿 false 断言，漏拷一处照样通过。
   必须有一个显式设 `true` 的用例把两件事分开。

## 第十七批 · 审计的四种用法（批次 A，P0-1）

**来源**：《控制权往哪里移：AI Coding 的工程演变》（Ethan Jiang，32 页）。第三份对照清单
`AI Coding 工程演变对照与升级清单.md` 里的 P0-1。这一条是资料独有的判据：同一份
append-only 记录支撑**回放 / 恢复 / 分叉 / 并行比较**四种问法。

**此前的两个缺口**：① 用法只有一种（`gleam replay` 只能排给人看）；② **前置不成立**——
任务记录是**跑完之后写一次的终态快照**，进程若在运行中退出那次运行什么都没有；
而 `--rerun` 会**真实调用工具**（20 步任务第 17 步失败，从头重跑 = 前 16 步副作用再做一遍）。
**用法是果，日志是因**：只加 `--from` 而不补运行中落盘，"恢复"在最需要它的场合恰好没有凭据。

**做法**：
- `internal/agent/runlog.go`：`runs/<taskID>.jsonl`，执行器新增 `Sink` 每步回调。**JSONL 而非数组**
  （追加 O(1)、崩了只坏半行）；**半行跳过而非整份拒绝**；**正常结束就删**（`runs/` 只留没跑完的运行）；
  **不安全 taskID 宁可不记**（净化会让 `a/b` 与 `a_b` 撞同一文件）；**文件不存在不算错误**
  （日志正常结束就删，不存在是预期状态）。`DiscardRunLog` 必须在**写盘成功之后**。
- `types.StepResult.Carried` + `Executor.Carried`：命中的步骤预置结果、**先于所有 goroutine** 放行下游。
  **`Carried` ≠ `Deduped`**：一个省副作用，一个省调用；回放要回答的第一个问题就是"这一步执行了没有"。
  **缺一条历史结果就拒绝**（顺手跑一遍 = 把恢复悄悄变成重跑）。沿用步数必须印。
- `types.ReplayRecord` + `cmd/gleam/replay.go` 重写：`--from` / `--tool` / `--args` / `--diff`。
  产物落 `replays/` **不进 `tasks/`**（后者是质量统计的分母来源）。计数只有 `countSteps` 一份实现，
  比较只有 `renderDiff` 一份实现。
- **接线断言（第四次）**：回放记录跑完才写，所以 Sink 的接线写在调用点的话单测照样全绿——
  改接在 `rerunExecutor`（组装执行器处），并加 `TestRerunExecutor_WiresRunLogSink`。

**实现中测试抓到的两个真问题**：
1. 预置循环 `close(finished[i])` 之后**没有 `e.record`**，沿用的步骤不进运行日志 →
   终态记录与从日志重建的视图会给出不同的「沿用」计数。
2. 冒烟脚本里任务记录写的是**相对**"绝对路径"（`cygpath -m` 对相对路径不补全）→ 被工具再按工作区
   解析一次，路径拼两遍 `ws/ws/c.txt`，症状看起来像"文件不存在"。**更坏的是**：这使"a.txt 没被创建"
   这条断言**碰巧通过**——路径本来就是坏的，跟沿用无关。补强断言（先证 s3 真的执行了）才暴露出来。

**验证**：新增 28 条测试（runlog 10 / executor carried 6 / replay_audit 11 / 跨实现对照 1）。
**19 处变异全部捕获**（脚本 `scripts/mutation/batch-a-audit.py`，**不再跑完即删**）。
端到端冒烟 `scripts/smoke-replay.sh` **33 条断言全过**，走真实二进制。

**四个新坑（都是环境/纪律层面的，值得记）**：
1. **断言顺序必须先正后反**：先证明"命令跑起来了、第三步真的执行了"，再证明"前两步没被重做"。
   反过来写，否定断言会在命令压根没跑起来时也成立——**用错误的理由通过比直接失败更坏**。
2. **本机删除操作会挂起**：`rm -rf` / `rmdir` / `find -delete` 都经过一层安全删除策略，
   可能被挂起等待确认（脚本里表现为莫名的 SIGTERM）。**脚本一律不清理临时目录**，
   改用系统临时目录由操作系统回收（每次 `mktemp` 都是新目录，重复运行天然干净）。
3. **`cygpath -m` 对相对路径不补全**：传给 Windows 二进制的路径要先用绝对路径再转换；
   任务记录里也必须写绝对路径。
4. **工具超时会伪装成 SIGTERM**：`go build` 在环境抖动时很慢，脚本总耗时超过工具默认超时
   会被杀成 SIGTERM，看起来像脚本有 bug。跑长脚本要给足超时或放后台。

**补正与追加（变异跑完之后）**：实际是 **20 处变异全部捕获**（无一存活、无一无效）。
变异脚本本身踩的坑比被验证的代码更值得记——**其中三条会让验证给出一个假的满分**：

1. **`|` 被 `cmd.exe` 当管道**：`subprocess.run(shell=True)` 在 Windows 上走 cmd.exe，而 cmd 不认单引号，
   于是 `go test -run 'A|B'` 的 `|` 成了管道，命令**压根没跑起来**——而"失败"被记成"捕获"。
   报错看起来像测试在报错，实际是 shell 在报错。**最隐蔽的假阳性。** 目标命令一律不含 `|`。
2. **不能编译的变异证明不了任何事**：有一处改法留下一句不可达代码，整包编译失败却照样记成"捕获"。
   骨架现在识别 `[build failed]`/`missing return` 等标志，单列为**无效变异**。
3. **被强杀会留下改了一半的仓库**：后台执行被沙箱拦在 Go 构建缓存上，进程被掐掉，
   信号处理器没机会跑，`executor.go` 停在一个被删掉 `close` 的状态上。更坏的是**下一次运行时
   另一条变异的锚点仍然匹配**，变异被应用到不干净的文件上，结果毫无意义。
   现在骨架做三件事：启动时对**全部**变异的**全部**锚点预检、备份同时写磁盘（下次启动自动还原）、
   还原后复核锚点回到恰好一次。**先确认起点干净，再谈结果。**
4. **死等类变异会让 `go test` 挂满默认的 10 分钟**（「沿用步骤不放行下游」的正确症状就是死等）。
   目标命令统一带 `-timeout 90s`，死等于是变成 90 秒后的 panic。
5. **不要用后台跑变异**：后台沙箱会拦构建缓存写入，而拦截看起来就像"测试失败"。
   骨架加了 `a-b` 范围参数，**每段 5 条在前台跑完**。

技能已存：`~/.workbuddy-ai/skills/go-mutation-verify/SKILL.md`（跨项目复用这套流程与环境坑）。
