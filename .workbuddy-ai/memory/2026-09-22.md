## 第十九批 · 批次 C：后台任务的结果必须送达（Qoder Cloud Agents 文章）

### 关键取证：`step.ID` 是不可信输入

`step.ID` 直接来自模型输出的计划 JSON，而计划校验只查「非空」「不重复」（`planner.go:582`），**没有路径安全**。所以 `"id": "../../../x"` 能一路走到落盘——而这是**写**。负例控制时关掉第 1 道，**第 2 道独立兜住了越界**，这就是两道都要留的意义。

### 落地时测试逼出来的三个问题

1. **落盘名跟着「引用方」而不是「内容来源」走 → 互相覆盖。** 一步可以引用多个来源（`{ref:s1}` 与 `{ref:s2}` 同在一个步骤参数里），第二次落盘覆盖第一次，**两个路径指向同一段内容**——比不给路径更坏。改成跟 `splitRef(ref)` 的来源 ID 走。
2. **提示语把预算撑破。** 先分配首尾再追加提示语（含一条可能很长的路径），结果比预算长出那一段。**假上限比没有上限更坏**（调用方按它分配上下文，却在某批任务上悄悄超出 → 表现为"偶发"溢出）。改成**先算提示语、再按剩余预算分配首尾**；剩余不足 `truncNoteMinBody=80` 退回纯截断。
3. **落盘失败必须说出来 + 给退路。** 装作成功会让模型反复重试同一个引用，而真正原因（没配数据目录/磁盘满/权限）一次都没被说出来。

**小预算不落盘**：`budget < spillMinBudget(160)` 纯截断——提示语含路径占几十上百字，预算太小时会把正文挤没；而"落了盘但提示语放不下路径"等于没落。

## 第二十一批 · 补漏：shell.exec 的孤儿孙进程会把 Wait 拖到包超时

**症状**：`bash scripts/verify.sh` 第 4 层失败——`go test ./...` 跑到 `internal/tools/shell` 卡满 **302s** 包超时（栈停在 `io.Copy` → `bytes.Buffer.ReadFrom`），而**单跑该包 10s 通过**；复现一次全量又是 27 包全绿。即**偶发**。

### 根因（三个条件叠加）

1. `Stdout`/`Stderr` 是 `bytes.Buffer`（不是 `*os.File`）时，`os/exec` 会另起 goroutine 把管道内容拷进 buffer，而 `Wait` **要等这些 goroutine 结束**；
2. 管道写端只要还有**任何**进程持有，拷贝就永远不返回；
3. `exec.CommandContext` 在 Windows 上只杀**直接子进程**——外层 shell 起的孙进程会存活，继续持有继承来的管道句柄。

于是「命令超时」这条正常路径在某些时序下变成「整个测试包挂到超时」。

**全仓只有 `internal/tools/shell/shell.go` 是「context 超时 + bytes.Buffer 接管道」这个组合**（其余用 `.Output()` 或 `.Run()` 不接管道）——所以修复面很小。

### 修法

- `cmd.WaitDelay = 5 * time.Second`（Go 1.20+）：进程退出后等管道关闭的上限，到点 `Wait` 返回 `exec.ErrWaitDelay`。
- 新增分支处理 `errors.Is(err, exec.ErrWaitDelay)`：**不能**走原来的 `default: 命令执行失败`（那条会误报"命令失败"，而命令其实结束了）。结果里带 `output_incomplete: true` + 一句说明——stdout/stderr 很可能只拷到一半，当完整输出用就是**静默截断**。

### 为什么要为一次偶发失败动代码

一个偶发失败的闸门很快就会被忽略，而忽略之后它连"哪一条失败了"都不再提供。这与 `verify.sh` 建立时抓出的三个问题（`set -e` 豁免 `A && B`、trap 污染退出码、`go run` 不稳）是同一类：**闸门的可信度就是它的全部价值**。

### 测试与负例控制

- 新增 `internal/tools/shell/orphan_test.go`：`orphanHolder()` 造「自己立刻结束、但留下活 30 秒的孙进程」的命令（Windows 用后台 ping，Unix 用 `sleep 30 & echo done`）。
- `TestShell_OrphanChildDoesNotHangWait`：断言耗时远小于 30 秒（**实测 5.64s**）+ 断言 `output_incomplete: true`。
- `TestShell_NormalCommandNotMarkedIncomplete`：反向控制——正常命令**不能**被标记为不完整（永远亮着的告警等于没有告警）。
- **负例控制**：`WaitDelay = 0` → 耗时 **31.38s** 且 `RC=1`。

### 踩到的坑：`set -e` 下的裸赋值

`go_retry` 第一版写成 `out=$(cmd); rc=$?`。这在 `set -e` 下**直接退出脚本**——赋值语句的退出码就是命令替换的退出码，`set -e` 立刻生效，重试逻辑一次都跑不到。症状极具误导性：脚本在第 N 行静默结束，看起来像构建失败。

`smoke.sh` 是 `set -uo pipefail`（无 `-e`）所以没事，`smoke-replay.sh` 是 `set -euo pipefail` 所以必然中招。

修法：取退出码写成 `out=$(...) && rc=0 || rc=$?`——`&&`/`||` 列表里 `set -e` 不生效。

### 闸门自检（第 0 步，不占层号）

- **`scripts/lib/gonoise_probe.sh`**（新建）：三段式探针，`<1s`、不碰 Go 工具链。
  ① 噪声一次后成功 → 必须 `rc=0`、命令调 **2** 次、**且必须打印**（静默重试等于把抖动藏起来）；
  ② 真实失败（无噪声签名）→ 必须 `rc=1`、命令**只调 1 次**（确定性失败不该被重试掩盖）；
  ③ 噪声两次 → 必须 `rc=1`、调 2 次（不无限重试）。
- `verify.sh` 在函数定义之后、第 1 层之前跑它，失败即 exit。
- 单独验证过 `set -e` 下的两种行为：真实失败 → 脚本终止（后续行不打印）；噪声后成功 → 继续执行（`calls=2`）。

### 探针自己踩的坑（写进脚本注释了）

探针第一版用**变量**计数，三例全误报「命令没被调用」。原因：`ERR=$( { go_retry …; } 2>&1 )` 与 `go_retry` 内部的 `out=$(...)` **都是子 shell**，变量在子 shell 里加完就随子 shell 消失。改成**文件计数**。这与 `set -e` 那个坑同源：**子 shell 边界**是这个函数最容易出错的地方。

### 顺带修正 CHANGELOG 的结构错位

批次 C / P2-2 / 补漏三节此前被**追加在 `pack/CHANGELOG.md` 文件末尾**，而末尾那节的日期是 `## 2026-09-07` —— 于是三节最新工作挂在了最旧的日期下。已按日期归位到 `## 2026-09-22`（顺序：批次 B → 批次 C → P2-2 → 补漏 → 本批），本批新节一并写入。88334 → 90682 字节。

改 GBK 文件踩到的三个坑（都记在脚本注释里，脚本已删）：

1. **文件是 CRLF**。锚点 `## 2026-09-21\n` 永远匹配不上（实际是 `\r\n`）→ 先归一化成 LF 处理，写回时再 `\n → \r\n`。写回后断言 `raw.count(b"\r\n") == raw.count(b"\n")` 防孤立 CR。
2. **别把「标记在文件末尾」当成「插入点在文件末尾」**。被误挂的三节确实在末尾，但 `head = txt[:标记位置]` 已经包含了 `2026-09-21` 及其后所有日期节，于是「接在 head 后面」等于插到了最旧的日期之后。正确做法是**按两处切成三段**（A=目标日期节 / B=其余日期节 / C=被误挂的三节），重排成 A+C+新节+B。
3. **断言要挑不会自我干扰的**。三次写错的断言：①`assert "2026-09-07" not in new_txt[pos:]`（日期本来就是降序，之后当然有更早的日期）；②`endswith("### 发布包更新…")`（归位改变了文件结尾，钉结尾是脆弱断言）；③`new_txt.count("## 2026-09-07") == 1`（**新增那节的正文里就提到了这个日期**，计数变成 2）。最终换成有意义的**多重集合断言**：`Counter(新文件行) - Counter(新增节的行) == Counter(原文件行)`，即「原文一行都没丢，只多了新增那节」——既强又不自我干扰。

**通用教训**：给「搬动/重排」类改动写断言时，别钉位置或结尾（它们本来就要变），要钉**内容守恒**（行多重集合相等）。

### 一条文档行限的经验

`docs/known-limits.md` 的索引型行限是 **60 字符/行**，而我把「为什么这样」一栏写成「与代码无关；判据只写在 `scripts/lib/gonoise.sh`，三个闸门脚本共用」= 76 字符，被预算检查抓出来。修法：把路径留全、把解释砍到最短（`| Go 工具链偶发读不到标准库 | 与代码无关；判据只在 scripts/lib/gonoise.sh |` = 55）。**行限约束的是「一行能扫完」，不是「说得多详细」**——详细解释的 home 是设计文档。
