# 外部资料 → Gleam 升级清单

Gleam 的演进有一条固定路径：**读外部资料 → 提炼判据 → 对照自己代码 → 产出清单 → 分批次落地**。
已经跑过三次：MiMo 文章（→ 设计文档 §4.6.2 成本治理 / §4.6.3 循环治理）、
Qoder Agent SDK 分享（→ §4.6.6 前缀缓存 / §4.6.7 场景模板 / §4.6.8 就绪体检）、
Harness Times 站点（→ `Harness 工程对照与升级清单.md`）。
本技能把这条路径固化，避免每次重新摸索。

## 一、抓取：先判断站点类型，别硬上 WebFetch

**判据**：WebFetch 只拿到 hero / 导航段 → 内容是客户端渲染的 SPA，WebFetch 拿不到正文。

```bash
# 1. 拿原始 HTML，确认框架与正文容器
curl -sL https://<host>/ -o _site.html && wc -c _site.html
grep -oE '(astro|__NEXT_DATA__|nuxt|vite)' _site.html | sort -u

# 2. 提取全部内链，先建全站地图再决定抓什么（不要盲目爬）
grep -oE 'href="[^"]+"' _site.html | sed 's/href="//;s/"//' | sort -u
```

- **Astro / 静态站**（本次 Harness Times 是 Astro v5.18.2）：正文在 `<article class="prose">`，
  用 Python 取**最大的那个 `<article>` 块**，正则剥掉 `script|style|svg|nav|aside` 再转纯文本。
- **微信公众号文章**（`mp.weixin.qq.com/s/...`）：不是 SPA，WebFetch 直接可用度也不高，
  走 `curl -sL -H 'User-Agent: Mozilla/5.0 ...'`（**不带 UA 可能拿到「环境异常」验证页**）。
  单篇 HTML 约 **3.5MB**（大量内联样式），正文容器是 `<div id="js_content">`——
  **`<article>` 出现 0 次**，所以「取最大 article 块」的启发式在微信上完全失效，别复用。
  实测口径（2026-09-21 复核）：`h.find('id="js_content"')` 命中位置约 568KB 处，
  从该处取 400KB 切片、剥 `script|style|svg` 与所有标签、解 `&nbsp;`/`&amp;`、
  `\s+` 压成单空格 → **8583 字**，干净可读。
  注意正文外层带 `style="visibility: hidden; opacity: 0;"`（渲染时由脚本放开），
  **不影响抽取**，别被它误导成"内容是空的"。
- 抓下来的 HTML 与 txt **放在仓库根目录的 `_<name>/` 临时目录**（前缀 `_` 表示临时），
  **收尾必须清理**——它们不属于项目产物。
  清理时**别一次 `rm -f a b c d e ...`**：本机实测多参数 `rm` 会被 SIGTERM 拦截
  （返回 `Exit Code: 1`），且删除是**逐个生效**的，看起来像"删了一半"。
  对策：用 `for f in ...; do rm -f "$f"; done`，每轮 ≤4 个，最后 `rmdir` 空目录。
- 抓取顺序按**与 Gleam 的相关度**排，不按站点目录顺序。Gleam 是 Agent Harness，
  相关的是「Harness 工程」「评测工程」；「知识引擎 / RAG」相关度低（Gleam 不是 RAG 系统），
  浏览确认后即可判低，不必逐字精读。

## 二、提炼：要判据，不要定义

外部资料的价值在**判据**，不在名词解释。逐章提炼时只保留三类东西：

1. **判据句**（「XX 的判据是 YY」）——例如「无进展检测 = 调用签名重复 **且** 结果哈希不变」
2. **数字**——阈值、比例、超时秒数（「阈值 3」「TTFB 30–60s」「保留池 20%」）
3. **反例**（「不要用调用次数，会误杀换关键词继续检索」）

**丢掉**：名词定义、历史沿革、作者感想、与 Gleam 无关的领域（如 RAG 的切分策略）。

把提炼结果写成一张 **A1…An 编号判据表**（按主题分组），它是后面逐条对照的工作底稿。
编号让「哪几条没做」可引用、可讨论。

## 三、对照：三路并行调研 + 关键结论逐行复核

代码库约 2 万行，**不要自己顺读**——用 Explore 子代理并行分片，每片问**具体问题**而不是「看看这块做了什么」。

有效分片方式（本次用的）：

| 分片 | 覆盖 | 问什么 |
|---|---|---|
| A · 循环与终止 | `internal/agent/` 主循环、`internal/eval/` | 主循环结构 / 终止条件几类 / 预算默认值 / 无进展检测依据与阈值 / partial 是否保留 / 有无 trace 与重放 |
| B · 工具与安全 | `internal/tools/`、`internal/harness/safety/`、`internal/llm/` | 契约字段清单 / 返回协议几态 / 有无错误分类 / 重试策略 / 有无幂等键 / 超时几级 / 闸门与审计 / 有无统一净化入口 |
| C · 上下文与评测 | `internal/agent/rules.go`、`internal/harness/memory/`、`internal/eval/` | 提示词拼接顺序 / 压缩触发与钉住区 / 记忆冲突与删除 / 多 Agent / 指标分母 / 评测分层与保留池 / 线上质量信号 |

给每个子代理的硬要求：

- **每条结论必须给「文件路径 + 函数/类型名 + 行号 + 关键代码片段」**（片段只贴关键几行）
- **能力不存在时要明确说「不存在」，并指出最接近的替代实现**
- 明确「只读调研，不要修改任何文件」

### ⚠ 关键结论必须自己逐行复核

子代理会给出很有说服力的摘要，**但摘要不等于事实**。凡是要写进结论、特别是要断言「这是 bug」的，
必须自己 `sed -n` 打开原文看一眼。本次复核抓到的例子：

- `shell.go` 非零退出吞错——**已部分修过**（「进程未能启动等非退出类错误（原实现会被静默吞掉）」），
  子代理的摘要没提这句注释，只看摘要会误判成「完全没处理」
- `clipboard.go` / `screenshot.go` 的 `PermissionReadOnly`——确认无误，是真漏
- `planner.go` 无注入防护——确认无误（稳定段逐行看过）

**判据**：写进清单的每一处「取证」，都要能在原文里指出那一行。

### ⚠ 还要单独查「声称 vs 实现」

逐行复核只保证「我引用的那一行没读错」，**不保证「项目承诺的行为真的被实现了」**。
外部资料的判据大多是关于"应该怎样"，所以对照时要把**项目自己的承诺**也当成一条判据去验：
README / 设计文档 / 代码注释里写的"我们会做 X"，回到代码里确认 X 真的生效。

本批（Jev 资料）两条 P0 都是这么挖出来的：

- `README.md:37` 写「干活的不能兼任验收……反思阶段由**独立环节**逐条判定」，
  实际 `agent.go:689-693` 是 `mainLLM := a.TierLLM(req.Role)` 喂给同一个 reflector（同源同档），
  且 `reflector.go:195-196` 只看 `Shorten(stringify(st.Output), 300)`——正是资料明确禁止的
  "仅依据主 Agent 的完成声明打分"。
- `agent.go:823-825` 的注释自己写着「后半句不能省——否则把 DoneThreshold 调低，或者模型自己说一句
  done，就能绕过逐条判定」，而 `agent.go:1225` 的 `acceptanceSatisfied` 在 `len(checks)==0` 时
  `return true`——**注释声明的意图被自己的 fail-open 兜底绕过了**。

**判据**：凡文档/注释里出现「必须 / 不能省 / 独立 / 强制」这类强承诺词，就去找对应实现，
把「承诺 → 实现落点 → 是否真生效」三件事写进取证。这比读外部资料更容易挖到真 bug，
因为**只有自己的代码知道自己承诺过什么**。

### ⚠ 先确认「是不是反方向」

外部资料给的最佳实践，落地前先问一句：**Gleam 是不是已经用另一种方式解决了？**
本批实例：资料里 `jev-skill-gate` 在解决"技能多了会爆上下文"，而 Gleam 的 skill
**根本不进提示词**（`planner.go` / `rules.go` 里 skill 命中数均为 0）——直接照搬会做出倒退的改动。
这类要写进「三、已经做对的（不要拆坏）」并说明**为什么是资产**。
反方向的另一面：同一个问题可能以**延迟版**形式存在（Gleam 不在提示词注入技能，但 `skill.list`
被调用时 `std.go:333-334` 全量倒进上下文）——**资产与缺口常常是同一个机制的两面**，两处都要写。

## 四、成文：清单要能让人拍板

产出物放**仓库根目录**（与 `CODE_REVIEW_REPORT.md` 同级），命名 `XXX 对照与升级清单.md`。
**不要**直接写进《Gleam 技术设计文档.md》——设计文档记的是**已决定的决策**，
清单是**待拍板的提案**。用户选定并落地后，才按 §4.6.x 追加进设计文档。

固定六节结构：

1. **摘要**——三句话说清：哪里领先 / 最大缺口在哪 / 哪几处该立刻修
2. **一、站点讲了什么**——A1…An 判据表（分主题）
3. **二、对照结果总览**——一张表：判据 / Gleam 现状 / 判定（✅ / ⚠ / ❌ / ➖ 不适用），末尾给统计
4. **三、已经做对的（不要拆坏）**——**这一节不能省**。外部资料常常比自己的实现更粗，
   照搬会拆掉资产。要写清「为什么是资产」+「升级时的注意点」
5. **四、差距清单**——按 P0…Pn 分批，每条给：取证 / 为什么是问题 / 改法 / 验收
6. **五、该拆的补丁** + **六、建议的落地顺序** + **明确不做（附理由）**

### 分批次的原则（不是按重要性，按「依赖关系」）

| 批 | 内容 | 为什么这个顺序 |
|---|---|---|
| P0 | **一致性缺口**——实现与自己声称的行为不一致 | 不是新特性，是修 bug；成本都在几十行内；先修它们，后面的观测才准 |
| P1 | **观测与口径**——错误分类、分段计量、trace、指标分母 | 「先让问题可见，再谈改」；**是第三批的前提**（没有归因分布，改哪层全靠猜） |
| P2/P3 | **动持久化格式**的改动——记忆、评测集 | 需要迁移方案，风险高一档 |
| P4/P5 | 长时程、沙箱 | 成本最高或与产品定位冲突 |

**「明确不做」必须写，并附理由**——否则以后有人看到外部资料讲了某件事，
会以为是自己漏了。理由通常是三类：与产品定位冲突（桌面单机 vs 完整沙箱）、
场景不成立（单任务 vs 多 Agent 上下文隔离）、本就不适用（行为型评测 vs 洞察型 judge）。

### 排序的可视化

用户要的是「按改动成本 × 影响面排序」，**用象限图而不是列表**（SVG，见 `show_widget`）：
横轴改动成本、纵轴影响面，四象限标「立刻做 / 排期做 / 顺手做 / 明确不做」。

**用「象限里的卡片」而不是「散点」**：成本/影响面是自己打的定性分，散点位置会暗示不存在的精度
（把影响面 0.55 的点画在中线上方，读者会以为它"偏高"）。改成四个象限里各堆一列固定宽度卡片、
**组内按影响面从上到下排**，既保住取舍信息，又不假装精确。落地细节：

- 四块象限矩形用 `var(--color-background-secondary)`，`明确不做` 那块用 `-tertiary` 让它后退；
  最该动的那块边框用 `var(--color-border-secondary)` 提亮一档。
- 象限角标用 pill 承担颜色（显式 50 级填充 + 800 级文字，如 `#FAEEDA`/`#633806`），
  这样明暗主题下都可读——**不要**让象限底色去扛颜色。
- 卡片内文字用 `var(--color-text-primary)`，前面加一个按象限着色的小圆点（400 级）；
  卡面 `var(--color-background-primary)` + 0.5px 边框。
- **本环境色板类名（`c-purple` 等）未实现，形状的 `fill` 必须显式写**，否则回落成黑色。
- 文本类名会覆盖 `fill` 属性（CSS 优先于 presentation attribute），要改色就用 `style="fill:..."`
  或在 `<style>` 里定义自己的类。
- 五张卡片塞进 195px 高的象限：卡高 26 + 间距 4 才放得下，先算清楚再定 `viewBox` 高度
  （`H = 最底元素 + 20`，且最底元素要落在 `H-40` 以内）。

## 五、减法（站点讲的「Harness 要能变薄」怎么落）

外部资料常有一条「好 Harness 要随模型变强而变薄」。**不要直接开拆**——拆补丁需要先有验证工具：

1. 先列**补丁候选表**：位置 / 为什么可能是补丁 / **拆的判据**
2. 拆的判据通常是「换到强档位后，某指标不下降」→ **依赖评测分层 + 保留池**
3. 所以**减法排在评测工程之后**，不能与它并行

本次审出的候选：工具菜单关键词筛选、`MaxSteps` 硬上限。
**不是补丁、不要拆**的：`extractJSON` 宽容解析（外部资料明确要求保留）、
各处 `Shorten` 截断（成本闸门）、`heuristicReflection` 本地兜底（可用性）。

## 七、落地批次（用户拍板后）：改 → 验 → 变异 → 同步

每个批次（P0/P1/…）的固定节奏：**实现 → 全量测试 → 评测基线对比并重新固定 → 变异验证 → 文档同步**。
前三步是常规工程，后两步的坑记录如下。

（第十一批修好了 e2e 脚手架的缓存策略之后，`go test ./...` 里 e2e 能正常跑，不再需要"e2e 单独跑"。
若又见到「构建超时: context deadline exceeded」，先看 `GOCACHE` 有没有被脚手架自建临时目录——
见第七节那条"测试红了先分三类"。）

### 变异验证脚本的三个坑（Python 写 `_mutate_pN.py`）

1. **bytes 字面量不能含非 ASCII 字面字符**——`b"...中文..."` 直接 SyntaxError
   （`\xe2\x80\x94` 这类转义可以、字面中文不行）。含中文的锚点统一写成
   `"....中文....".encode("utf-8")` 形式；别混用，混用最容易漏看。
2. **字符串字面量里嵌套引号要转义**——描述文字写 `"退回"只给分数""` 也是 SyntaxError，
   描述里改用单引号。
3. **锚点必须全文件唯一**——同一 case 结构常在兄弟函数里各出现一次
   （如 reflector 的 `buildDigest` 与 `buildStepDigest`）。脚本要断言 `count(old) == 1`，
   不唯一时用「带下一行注释」的更长锚点区分（注释通常只在其中一处出现）。

**P1 批次补充的四个坑**：

1. **`\xNN` 转义写进 str 字面量再 `.encode("utf-8")` = 双重编码 mojibake**——
   `\xe3` 在 str 里是码点 U+00E3（ã），编码后变 `\xc3\xa3`，永远匹配不上。
   规则：str 里只许真实字符，bytes 字面量里才许 `\x` 转义，二选一。
2. **锚点的缩进层级要核实，别数**——`cat -A` 或 bytes dump 看真实字节。
   本批两次 count=0 都是 tab 层级数错（3 层写成 4 层）。
3. **count=0 可能意味着「断言测的代码根本不存在」**——不只是锚点写错。
   实例：审批拒绝的结构性归类被静默丢编辑，测试靠启发式兜底全绿，
   直到变异脚本报 anchor count=0 才暴露。凡 count=0，先 grep 目标文件确认。
4. **断言能红的前提是「结构落点」与「启发式」不重叠**——审批拒绝文本自带
   "拒绝执行"，启发式永远兜得住，删掉结构定类测试照样绿。这种变异要改成
   「错误归类」（permission → business）才能被断言看见。

**P4/P5 批次补充的四个坑**：

1. **「抽共享实现」会连带 unused import**——把三处 `bufio.Scanner` 循环抽成共用
   `scanStream`、把 file 的 `within` 提升到 toolutil 后，`bufio`（三处）、`strings`（一处）
   立刻变成 unused。清理要用 Python `assert s.count('\t"bufio"\n') == 1` 精确删，
   删完立刻 `go build ./...`——unused import 是编译错误，这是最便宜的验证。
2. **跨语言路径变量别直接传**——Git Bash 的 `$TEMP` 传给 Windows Go 程序会变成 `\tmp`，
   报 `The system cannot find the file specified`。凡 `--data-dir` / `-o` 这类参数，
   先 `TMPD=$(cygpath -w "$TEMP")/xxx` 转换。这个坑第三批、第四批各踩一次。
3. **任务列表状态会陈旧**——收尾前发现 #51–#53 实际已完成但列表仍显示 pending
   （中途工具调用没回写）。**收尾第一步是按文件核实**（`ls` 关键新增文件 + `grep` 接线点），
   再据实回写任务状态，别信列表。
4. **CLI 打印时长要防负数**——造测试数据常用未来时间戳，`time.Since` 会出负值，
   显示成「等待 -6h39m57s」。统一 `if ago < 0 { ago = 0 }`。
5. **heredoc 会把 `\\n` 折叠成真换行**——用 `python - <<'PY'` 写变异脚本时，
   `b'...\\n...'` 到 Python 手里已是真换行，锚点 `count=0`。
   对策：`BS = chr(92)` 拼反斜杠，别在 heredoc 里写字面反斜杠。
   这是 **`count=0` 的第三种成因**：不是锚点写错、也不是代码不存在，
   而是**传参过程改了字节**。三种成因的排查顺序：先 grep 目标文件确认代码在不在 →
   再 `cat -A` 核真实缩进 → 最后怀疑传参。另外别用中文全角括号做锚点的一部分再手工数宽度。

**第八批（P0/P1 落地）补充的四个坑**：

1. **「逐条打印」还不够——重定向到文件时 Python 的 stdout 是块缓冲**。脚本跑着的时候
   `_mut_all_out.txt` 一直是 **0 字节**，看起来像"脚本根本没启动"，其实输出全卡在缓冲区里。
   必须 `python -u` 跑，或者 `sys.stdout.reconfigure(line_buffering=True)`。
   （`print(..., flush=True)` 也行，但九处都得记得加，不如 `-u` 一次搞定。）
2. **变异体必须"能编译"，否则只拿到编译红、验证不到测试**。实例：`rep.Repeatability = &rate`
   → `nil` 会让 `rate` 变成 declared and not used；`maxSteps = config.DefaultMaxSteps` → `12`
   会让 `config` 变成 unused import。两处都只得到 `FAIL ... [build failed]`。
   **编译红只能证明"这行是承重的"，不能证明"测试断言抓得住这个行为"**——而后者才是变异验证的目的。
   判据：输出里**必须出现 `--- FAIL`**；只有 `[build failed]` 不算捕获。
   写法：给变异体留一条"使用语句"（`_ = rate` / `_ = config.DefaultMaxSteps`），
   或把条件改成恒假但仍引用变量（`if hasChecks && false {`）。
3. **`consume(p)` 这类助手内部已含 `bak(p)` 时，调用方不要再套一层**。写成 `consume(bak(p))`
   会去找 `xxx.probe.bak.probe.bak`，`os.replace` 抛 `FileNotFoundError`——
   而且它发生在**恢复路径**上（`finally` 里），一崩就没人恢复源码了。
   规则：助手要么收"原始路径"、要么收"快照路径"，别让调用方猜；命名上区分开（`restore_of(p)` vs `drop_snapshot(bp)`）。
4. **收尾清理仍受「多参数 `rm` 被 SIGTERM 拦截」限制**（第四批记过，第八批又踩一次）：
   `rm -f a b c d` 会整条被杀、只生效前几个。用 `for f in ...; do rm -f "$f"; done`，
   每轮 ≤4 个，删完**再 `find` 回读一遍**确认空。

**P4-2a（验收确定性层）补充的两个坑**：

1. **变异脚本的恢复路径绝不能碰 `os.remove`**（第八批记过一次，这次换个形态又踩）。
   本环境的 safe-delete 垫片会把 `os.remove` 劫持成"移入回收站"，没有桌面会话时直接抛
   `SHFileOperationW 失败: 0x2`——而它发生在 `finally` 里，**一崩就没人恢复源码，整个验证带伤运行**。
   症状很有迷惑性：某几处变异莫名"未被捕获"，而且**两次运行结果还不一致**（同一处一次捕获、一次没捕获）。
   正确写法：**恢复一律用内存里的原字节**（`write_bytes(path, orig[path])`），快照只在脚本开头写一次、
   结尾由 shell 的 `for` 循环清理，**Python 全程不删任何文件**。
   连带一条：写文件要 `with open(...) as f: f.write(); f.flush(); os.fsync()`——否则 `go test` 可能
   读到旧内容，把"变异没生效"误报成"未被捕获"。
   判据：**结果不稳定就是脚本的问题，先别改测试**；连续两次跑出同一个数字之前，那个数字不算证据。
2. **「未被捕获」要先判是真阴性还是测试没覆盖**。一个变异不响，先查守卫是不是被别的守卫
   覆盖了——实例：`verifyArtifacts` 里「跳过未成功步骤」被后面「路径为空就跳过」覆盖
   （执行器只在 `err == nil` 时记 `Output`，失败步骤根本没有路径可判），属**真阴性**。
   两种处置：真冗余就删掉（不臃肿）；若它守的是一条**契约**（`StepResult` 允许「失败 + 有输出」
   的组合，工具完全可以 `return out, err`），就补一条直接构造该组合的测试，把它从装饰变成契约。
   **变异验证的价值正在这里：它区分「守卫在干活」与「守卫只是站在那儿」。**
3. **「未被捕获」的判据必须是「测试真的跑完且全绿（`rc == 0`）」，不能用"没看到 `--- FAIL`"**。
   本机 Go 工具链会间歇报 `package crypto/md5 is not in std (C:\Go\src\crypto\md5)`
   ——而那个目录**确实存在**（GOROOT=`C:\Go`，go1.23.4），属环境性偶发；此时 `rc=1`、
   既无 `--- FAIL` 也无 `build failed`，被脚本算成"未被捕获"，结论就变成了
   "守卫没被测试覆盖"——而真相是"这次测试根本没跑起来"。
   修法：`rc == 0 && 无 --- FAIL` 才算真阴性；`rc != 0 且无 --- FAIL` 判为**环境错误**，
   **自动重试**（3 次），仍不行就报「环境错误（不计入）」而不是算阴性。
   **阴性结论的判据是"测试成功跑完且全绿"，不是"没看到失败字样"。**

**P4-2b（独立验收者 + 格式合法）补充的三条**：

1. **「函数正确」不等于「被接进主循环」——改接线的地方要补一条接线断言。**
   `VerifyLLM` 怎么单测都对，但反思器原先吃的是 `mainLLM`；接上以后，只有一条
   "造两个假客户端、断言执行者那个**一条 reflect 调用都没有**"的测试才守得住这件事。
   手法：让执行者那个假客户端的反思脚本故意给低分（`score=10/replan`）、验收那个给高分，
   断言最终成功——**两个方向都能区分**，不是只看"验收被调过"。
   **接线断言本身也要变异验证**：把接线改回原样，它必须变红（本次实测会红）。
2. **「承诺」要落成「可核对的事实」。** 独立性这类东西，回退与换成功都会返回一个可用客户端，
   光看"有没有"看不出区别。所以额外给一个 `VerifyModel`（只算名字、**不建客户端**），
   就绪体检据此明说"独立验收生效"还是"与执行者同源"。
   一般化：**凡是"我们做了 X"的说法，都要有一个能被命令或测试打出来的事实支撑。**
3. **换不成的场景要如实回退，不许"随便挑一个顶上"。** 实例：`analyst` 这类角色自己就跑在
   验收档（`reasoning`）上 → 换不成。刻意**不**退而求其次去挑别的档或主模型：
   拿一个没有理由信任的弱模型去判强模型的产出，只会得到一个"看起来独立"的橡皮图章，
   **比同源自评更难发现**。把这条限制写进代码注释与就绪诊断，而不是靠注释糊过去。
   判据仍然回到那句：**宁可不判，不可错判。**

**确定性层的边界（P4-2a/P4-2b 定下的）**：只做**确定性**判定——存在性、类型、长度，
加上唯一一处读内容的例外「格式合法」（`.json` 能不能解析）。语义判断留给语义层。
格式这一层的取舍值得抄：只认扩展名（csv 不查，列数不齐也可能是合法数据）、
只查覆盖写（追加写可能只是贴一段）、放宽一档（JSONL 常被写成 `.json`，逐行合法也算通过）、
空内容不判、顺手容忍 BOM。**每一条都是在防假警报——假警报会让这道闸被当噪音关掉。**

**P4-2b 又踩的两个坑**：

1. **后台长脚本被中断，会把源码留在变异态——事后核对必须覆盖每一个锚点，不能只抽查两个。**
   变异脚本跑 11 处要几分钟，很容易超时被 SIGTERM 杀掉。那次它死在某处变异的测试里，
   `jsonBroken` 的空守卫**被留在删除态**；而我当时只核对了两个锚点（都正常）就放行。
   后果有二：后续所有验证都跑在"少了那个分支"的版本上；重跑脚本时那处变异报
   `anchor=0`，看起来像"锚点写错了"。
   **判据：核对还原状态时，把脚本碰过的每个锚点都数一遍**（`grep -cF` 逐个数）。
   顺带一条：**长脚本尽量一次跑完并留足时间，或拆成几批**，别让它半路被杀。
2. **本机 `grep` 的正则不可靠，判字符串一律用 `grep -F`。** 查
   `return m != "" && m != a.execModel(role)` 时，正则模式报 **0**、`-F` 模式报 **1**
   ——差一点得出"这行代码不在文件里"的错结论。这与早先记过的 `grep -c $'\r'` 假阳性同类：
   **这台机器上 `grep` 的结论要多问一次**（换 `-F`、换 `od -c`、或直接用 Python 读 bytes）。

**P5（交付侧口径）补充的两条**：

1. **SIGTERM 默认直接终止进程，`finally` 不会执行**——这是 P4-2b 那个坑的**根治办法**，
   而不是"留足时间、别被杀"（那是碰运气）。Python 不处理 SIGTERM，进程立刻死，
   `finally` 里的还原**根本跑不到**，源码就留在变异态。修法：脚本开头把信号转成异常，
   让 `finally` 有机会跑完：
   ```python
   import signal
   def _on_term(signum, frame):
       raise KeyboardInterrupt("收到 SIGTERM，走异常路径以触发还原")
   signal.signal(signal.SIGTERM, _on_term)
   signal.signal(signal.SIGINT, _on_term)
   ```
   再配一道**开跑前的锚点预检**（所有锚点 `count(old) == 1` 才开跑）：锚点写错时立刻失败，
   不用等跑到一半才发现、前面几分钟白等。
2. **判「变异有没有残留」不能用 `new in text`。** 收尾核对时我用 `if new in text: 报残留`
   去查，报了 3 处**假阳性**——因为 `new` 常常是 `old` 的**前缀或子串**：
   `res.FirstPass = p.firstRound` 是 `res.FirstPass = p.firstRound && res.Status == types.GoalSuccess`
   的前缀；`if prog != nil {` 在文件里本来就有另一处；两行的注释块被截成一行也仍是前缀。
   **真判据只有一个：原文锚点是否仍恰好命中 1 次**（`count(old) == 1`）。
   判"有没有被改坏"要看**原文在不在**，不是看**新文在不在**——后者对"包含关系"毫无抵抗力。

**「拆补丁」类任务的量测纪律**（第五批：拆工具菜单筛选时立的）：

减法项的判据常写成「换强档位后某指标不下降」，**天然依赖真实模型**。开工前先探针：
`gleam eval --depth plan --cases <1条>` 跑一下，`HTTP 401` 就是没凭证——
此时**不要假装做完了**，要把任务劈成「质量半边（需模型）」与「成本半边（离线可测）」，
把成本半边做扎实并如实报告哪半边没做。本机若也没有 ollama 等本地模型，就直说。

离线半边的量法（复用项目自带标尺，别另造）：构造**两个不同目标**的系统提示词，
用 `llm.StablePrefixLen(a, b)` 取最长公共前缀——那就是「与目标无关、可跨任务复用」、
真正能被前缀缓存吃掉的部分；阈值用 `llm.CacheFriendlyMinChars`。
再按缓存读价 d 折算盈亏平衡（`uncached + cached·d`），因为**「提示词更短」不等于「计费更低」**：
体积小的方案可能因为把易变段提前、截断了缓存前缀而更贵。

**拿到 key 之后：先量噪声基线，再谈处理效应**（第六批最贵的一课）：

1. **同配置重跑至少 2~3 次**，把「同一配置两次运行之间有多少用例不同」当成噪声基线。
   第六批实测：菜单×菜单 均值 3.00、全量×全量 均值 5.67，而**菜单×全量 只有 4.83**——
   处理效应落在两条噪声基线之间，**差异不可归因**。若只跑一轮 16 条就下结论，必然误判。
   **「不可归因」不等于「证明无差异」**——所以它**不能作为拆除依据**。第八批就靠这条推翻了
   原定的"拆工具菜单"：判据原文写的是"选择准确率不下降"，拿到的是"差异不可归因"，
   拿不可归因的证据去删一个用户可见的安全阀（设置页的 `max_tool_schemas`）是草率不是精简。
   正确顺序：**先补可重复性指标（`--repeat N`），再用重复采样实测判定**。
   凡是减法项的判据是"某指标不下降"，都要先问一句"我拿到的证据够不够支撑删除"。
2. **`temperature: 0` 不保证确定性**（A0 16/16、A0b 15/16）——provider 侧有 MoE 路由/批处理抖动。
   别指望靠降温省掉重复采样。
3. **判定「有没有稳定差异」的判据**：看某一用例的工具集在两组间**是否完全无重叠**。
   只要有重叠，就说明组内变异已覆盖组间差异。第六批 16 条用例**全部有重叠**。
4. **环境变量改不动模型时，先查覆盖层顺序**：`config.Load` 里 `applyEnv` 先跑，
   `buildRuntime` 随后加载 `DataDir/settings.yaml` 覆盖层 → **覆盖层赢**。
   绕法：`--data-dir <临时目录>` 让覆盖层文件不存在。另注意 Git Bash 的 `$TEMP` 要
   `cygpath -w` 转换（老坑）。
5. **判据里的约束可能不是真正的约束**：测「`MaxSteps` 上限是否死重」时发现，宽泛目标下
   先撞上的是**输出 token 预算**（`max_tokens: 4096` 下 JSON 被截断成「未闭合」、
   抬到 16000 就变成 8 步通过）。**上限 12 从未触发，但余量只有 2 步（观测最大 10）**——
   所以结论是「可抬不可废」，不是「可删」。凡是「某上限是否死重」的实验，
   都要顺手确认有没有**更早生效的硬约束**。
6. **稳定性指标自己也需要噪声基线**（第九批，最容易被忽略的一条）——`--repeat N` 报出的
   "可重复性"是**一个估计量、不是真值**，比较两个配置的稳定性时它的误差比结果指标还大。
   第九批实测：菜单 vs 全量，第 1 轮 69% vs 50%（差 19pp，看着"菜单更稳"），
   第 2 轮 **38% vs 44%（符号反了）**，合并后完全相同（5/16 对 5/16）。
   原因很清楚：**用例自身的稳定性是稳定的**（四个复杂用例在四格里全抖、三个简单用例三格全稳），
   会变的只是"这次抖几条"，而 16×3 下这个计数有 **±2~3 条**误差——足以把 3 条的差
   放大成 19pp 的"结论"。
   → **比较两个配置的稳定性，一轮 16×3 不够，至少两轮独立测量看方向是否一致。**
   → 反过来，"**可归因差异 0 条**"这个判据是稳的（两轮都是 0），可以直接用。
   → 顺带一个对项目很重要的事实：`deepseek-v4.1-flash`（temperature 0.3）的逐次一致性只有
   **31%~69%**，大多数用例单跑一次接近掷硬币——**通过率必须配合可重复性一起读**。
7. **减法项的判据若是"某指标不下降"，量完可能得出与假设相反的结论**（第九批）：
   菜单的成本收益（提示词小 24%）是**算术、两轮一模一样**，而质量差异测不出来
   → 不是"拆掉也没事"，而是**拆掉纯亏**。**"确定的小收益" + "测不出的质量改善" = 保留**，
   这比"不可归因所以保守不拆"是更强的结论。写结论时要把"测不出差异"与"有确定收益"分开说。

**改 fail-open 之前先看有没有测试把它锁成契约**（第十批）：同一个"核对失败就放行"的动作，
在工作模式里是**漏洞**（没有测试锁定，且效果是让整道验收闸失效 → 改代码），
在对话模式里是**设计**（`TestChatSelfCheck_FailureKeepsOldBehavior` 明确断言"失败时保持
成功/满分" → 改口径、补可见性，不推翻设计）。
判据：**先去看有没有测试把当前行为锁成契约**。有 → 尊重它；没有 → 再判断是漏洞还是设计。
反过来也成立：**发现行为是"有意的"之后，仍然要问"它有没有在自己的失败路径上复现它要消灭的问题"**
——对话自检就是一边宣称"不再无条件报满分"，一边在核对失败时静默给 100。

配套一条：**"放行"与"报满分"是两件事，可以只做前者**。对话自检核对失败时保持
`GoalSuccess`/`Score: 100` 是对的（回答已交付，不该因核对环节出问题就把它标成失败或低分），
但**不能让用户以为核对过**——把"没核对成"与"没什么可核对"拆成两种结局，只对前者发提示。
改分数这条捷径是错的：前端 `scoreRing()` 把 `<40` 渲染成红色的"完成度 0/100"，
那是在往反方向说谎。**凡是要改一个展示字段的值，先 grep 它在哪儿被渲染。**

**改默认值是一个"跨安装"的动作**（第九批）：改完 `Default()` 不算完——`SaveOverlay` 会把
**全部**字段写进 `DataDir/settings.yaml`（全量快照；MCP 空列表与 `tiers` 空表更是**故意要写**，
用于覆盖 `config.yaml` / 表达清空），加载侧又是"覆盖层赢"，所以**任何已经保存过设置的安装
都会把旧默认值钉死**。第九批改 `DefaultMaxSteps` 12→32 就撞上了：本机 `settings.yaml` 里的
`agent: max_steps: 12` 把新默认值压了回去。**凡改默认值，收尾时都要顺手查一遍已有安装的
`settings.yaml`。**（没有改成"只写非默认字段"：那需要一张例外清单——`tiers`/`mcp`/`workspace`
的零值都带"清空/覆盖"语义——清单本身比这个坑更脆。）

**交付前必做的「数字实测」**：文档/官网里凡是写死的数字（工具数、用例数、卡片数、
分组数、提示词字符数），**必须用命令实测后回填**，且回填后再 grep 回读一遍。
第四批实例：官网写「17 个内置工具」→ `gleam tools` 实测 23；卡片数 `grep -c` 实测 34、
分组 6；新分组卡片数一度记成 12，实测 11（awk 区间边界差一）。
这些数字用户会拿去核对，留着过期数字比不写更糟。

变异脚本的其他铁律（此前批次已验证）：全程二进制读写（文本模式会把 LF 翻成 CRLF，
Go 文件整份「还原 ≠ 原样」）；每处变异 finally 恢复原字节；跑完在受影响包上复跑一次测试确认还原干净。
**这条不限于变异脚本——任何用 Python 写仓库文件都算**：第十二批给 4 个测试文件批量补参数时又踩，
`open(p,'w')` 把 LF 翻成 CRLF，`gofmt -l` 当场报这 4 个文件。改完一律复核行尾 + `gofmt -l`。
（判行尾用 `od -c` 或 Python 读 bytes，**别用 `grep -c $'\r'`**，本机它会把 LF 文件也数成全 CRLF。）

**"测试红了"先分三类：代码回归 / 环境缺陷 / 脚手架缺陷**（第十一批）。e2e 5 条一直报
「构建超时: context deadline exceeded」，最初被当成"冷缓存偶发"，实际是**确定性**的脚手架缺陷：
`internal/e2e` 的 `buildBinary` 在 `GOCACHE` 未设置时**每次新建一个临时缓存目录** → 每次都是冷编译
→ 撞它内部 2 分钟预算。判据：**换一条命令重跑（这里是把 `GOCACHE` 指到热缓存），若结果从恒红
变恒绿，问题在脚手架不在代码。** 这类缺陷按"健全"优先修——**一个永远报红的测试比没有测试更糟，
它会训练人忽略红色，真回归也被一起忽略。** 另外注意 **测试内部的构建预算不是 `go test -timeout`**：
`-timeout 900s` 对那个 `buildCtx` 2 分钟毫无作用，别靠加 `-timeout` 来"修"它。
