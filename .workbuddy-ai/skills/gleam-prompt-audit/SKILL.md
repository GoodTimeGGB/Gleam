# Gleam 提示词审计

要讨论"提示词是不是太长、哪段该删"，先把它量出来。Gleam 的规划器提示词是
**代码里拼出来的**（`internal/agent/planner.go`），光读代码数不出字节数，得跑一次。

## 一、提示词在哪、分界在哪

- 构建函数：`internal/agent/planner.go` 的 `(*Planner).buildSystemPrompt(goal, cwd, recent, relevant, summary, feedback)`
- **稳定段**（跨请求逐字节相同，走服务端前缀缓存）：
  身份 → 输出契约（输出格式 + 规划规则 + 验收标准）→ 专家角色 →
  本角色验收重点 → 本场景产出格式 → 协作风格 → 编程模式准则（仅 code 模式）→
  能力菜单 → 定时/周期任务
- **分界线**：`p.toolSchemaSection(goal)` 之前都算稳定段；它之后是易变段
  （按目标筛出的工具 schema → 上下文/工作目录 → 早期摘要 → 相关长期记忆 → 最近对话 → 重规划反馈 → 输出提醒）
- **规则正文已经不在 `planner.go` 里了**：2026-09-20 起稳定段的规则全部搬进
  `internal/agent/rules.go` 的规则表（`stableRules`），每条规则有 ID / 落点（`Slot`）/
  适用范围（`Scope`）。`planner.go` 只负责把规则块按布局拼起来。
  **要改规则文案或让它只在某些场景生效，去 `rules.go`，不要在 `planner.go` 里加 if。**
  `planner.go` 里只剩下 `promptIdentity` 与 `styleInstruction`（协作风格是三选一，不是规则）。

## 二、测量手法（临时测试，跑完即删）

在 `internal/agent/` 放一个临时 `zz_measure_test.go`，复用现成 fixture：

```go
p := &Planner{Reg: bigRegistry(25), MaxToolSchemas: 12, Role: "analyst", TaskMode: "work", Style: "efficient"}
a := p.buildSystemPrompt("把上季度销售数据整理成表格并汇总", "D:/ws", nil, nil, "", "")
```

然后按小节标记切分 `a`，用 `strings.Index` 定位每个标记的**字节偏移**，
相邻标记相减即该段字节数。**跑完删掉，别提交进仓库**（`zz_` 前缀只是为了排序时显眼）。

## 三、三个必踩的坑

1. **`llm.StablePrefixLen` 返回的是字符数（rune），`strings.Index` 返回的是字节偏移。**
   混着比会得出"公共前缀在能力菜单中间被截断"这种**假结论**（我就这么被骗过一次）。
   要跟字节偏移比较，用 `stable, _, _ := llm.SplitCacheBoundary(a, b)` 再取 `len(stable)`。
   注：`llm.CacheFriendlyMinChars = 1200` 是**字符**阈值，与 `StablePrefixLen` 口径一致。

2. **规划器系统提示词里没有「用户目标」**——目标走独立 user message。
   所以拿两个不同目标去比系统提示词的公共前缀，结果**必然 100% 相同**，
   看起来像"缓存完美"，其实什么都没测到。要压出易变段，必须**同时变 cwd / 摘要 / 历史**。

3. **`bigRegistry` 造的工具描述全都一样**，按目标筛 schema 时评分打平、两次选择完全相同，
   所以它测不出易变段的差异。要测筛选差异，得让各工具描述彼此不同。

而本表三个总数（4885 / 5233 / 4514）一字未变。

## 五、改提示词时必须守的两条约束

1. **规则开关只能挂在「稳定维度」上**：模型档位 / 角色 / 任务模式。
   **绝不能挂在「本次任务」上**——那会让稳定段逐任务变化，前缀缓存全部失效。
   按档位整体切分规则集是可以的，缓存本来就是按档位分的。
2. **增删稳定段内容后，重跑 `TestPromptCache_*`**，并重新量一遍本表。
   稳定段变短会影响 `llm.CacheFriendlyMinChars`（1200 字符）这条门槛，
   `gleam doctor` 的第 7 项（模型调用缓存不可控）会跟着变。
3. **工具描述的头 60 字也在稳定段里**——`toolMenuSection` 用
   `firstLine(t.Description())` = `types.Shorten(desc, 60)` 把每个工具的**描述首行**列进能力菜单，
   而能力菜单是稳定段。所以：
   - 往工具描述里**追加**细节是安全的（超出 60 字的部分不进稳定段）；
   - 但**改动描述开头**会悄悄改掉稳定段，破坏前缀缓存。
   - 注意 `Shorten(s, 60)` 是「截 60 字 + 补一个 `…`」，**结果是 61 字**，别把上限写成 60。
   - 已有守卫：`TestScheduleDetailStaysOutOfMenu`（断言细节不混进菜单行）。

## 五之二、做减法的标准姿势：信息只能搬家，不能丢

从稳定段删掉的内容，要确认它**仍然能被模型看到**——通常是搬进对应工具的
`Description()` / `Schema()`（只在选中该工具时才加载，正是"目录在前、细节按需"）。

守卫写法：把「提示词段 + 工具描述 + 工具 schema」拼起来做**并集**断言，
而不是断言某句话在某个指定位置。这样以后再搬一次也不用改测试，
但只要有一句话在两处都消失就立刻红。参考 `TestScheduleGuidanceNotLost`。

另外要分清**可替代**与**不可替代**的内容：
`schedule.create` 的例子是——`when` 的 5 个示例、`name`/`goal` 必填，在工具 schema 里
本来就有（**纯重复，直接删**）；而「不要只在回复里答应」工具描述说不出（**必须留在提示词里**）。
先做这个区分，再决定删什么，不然容易把行为约束一起删掉。

## 五之三、规则表 `rules.go`：减法怎么改（2026-09-20 起）

规则全部在 `internal/agent/rules.go` 的 `stableRules` 里。结构：

```go
type Rule struct {
    ID    string   // 稳定标识，测试与变更记录用它
    Slot  string   // 落点：contract | code | schedule
    Title string   // 小节标题（相邻同标题的条目合并成一个 "## 小节"，多于一条自动编号）
    Items []string // 条目
    Scope Scope    // Modes / Tiers / Roles，空 = 不限
}
```

三条必须遵守的规矩（都有测试守着，破了会红）：

1. **范围只能落在稳定维度上**：任务模式 / 模型档位 / 角色。
   **绝不要**按"本次目标"开关规则——稳定段会逐任务变化，前缀缓存全碎。
   这条由签名兜住：`renderRules(slot, mode, tier, role)` 拿不到 `goal`。
2. **同一 ID 可以注册多条，先匹配到的生效**——变体在前、兜底在后。
   兜底版一旦排在变体前面，变体就永远轮不到（死代码，且不报错）。
3. **兜底兜的是档位，不是模式**。踩过的坑：`code.verify` 的兜底版只写了档位范围、
   漏了 `Modes: []string{"code"}`，于是**工作模式的提示词里凭空多出一条编程准则**，
   而规则表看起来毫无问题。加变体时把**每一个**维度都写清楚。

常用操作：

| 想做的事 | 怎么做 |
| :-- | :-- |
| 删一条规则 | 从 `stableRules` 里删掉；体积守卫会告诉你省了多少 |
| 只给某些场景用 | 填 `Scope`（如 `Scope{Modes: []string{"code"}}`） |
| 按模型档位换措辞 | 同一 ID 写两条：变体（`Scope{Tiers: capableTiers}`）在前、通用版在后 |
| 换掉一条规则 | 改 `Items`；**改完必须跑下面的逐字节比对** |
| 确认某场景用了哪几条 | `gleam rules --task-mode code --tier coding`（见五之四） |

**改规则前后必须做的逐字节比对**（这是资产化那次唯一抓到真 bug 的手段）：

```go
// internal/agent/ 下临时放个 zz_capture_test.go，导出若干 (角色, 模式, 档位) 组合的
// buildSystemPrompt 结果到 $TEMP，改动前存一份、改动后存一份，再逐字节比。
```

**判据**：纯重构（搬家/改名）必须 21356 字节完全一致；改文案时差异必须**只有你改的那几句**。
另外 `gleam eval` 的提示词合计也要对上（当前 82964 字符），两者互为交叉验证。

**按档位条件化的现状**（`code.verify`，编程模式第 3 条）：

- 生效档位为**空**（未配档位）或 `economy` → 保留原文「必须安排验证步骤」；
- 生效档位为 `coding` / `office` / `reasoning` → 「验一次就够，不要反复重跑」；
- 判据是**用户有没有为这一档单独配模型**（`Agent.EffectiveTier`），不是从档位名猜能力强弱
  ——档位名描述的是用途（编码/办公/推理），不是能力；
- **无论哪一版都必须提到"验证"**：变体去掉的是"反复"的推力，不是验证本身。
  有 `TestRules_VerifyNeverDisappears` 守着。

量测档位条件化的效果：

```bash
/tmp/gleam.exe eval --tier coding      # 模拟生效档位，只改提示词构建、不切换模型
```

注意：`--tier` 会改变提示词，所以**跨档位不能拿同一份基线比**（`Compare` 会直接拦下，
和跨深度同款）。当前实测：`--tier coding` 82987 vs 未模拟 82964，**差 23 字符**——
这是**行为改动不是体积改动**，别拿它当"省了多少钱"的论据。

## 五之四、规则集身份：改完规则要留下痕迹（2026-09-20 起）

一次产出的行为由**代码 / 模型 / 规则表**三者共同决定。代码有提交记录，模型有名字与用量，
规则表现在也有了身份——**排查回归时最常见的误判是"代码改坏了"，真相却是"规则改了一个字"**。

- `RuleSetVersion()`：**内容派生**的指纹（10 位十六进制），手写版本号会忘改，所以不手写。
  取自 ID / 槽位 / 标题 / 条目 / 适用范围 / 渲染顺序——`Scope` 也算在内：
  同一句话换个适用范围，行为就变了，不算同一版。
- `ActiveRuleIDs(mode, tier, role)`：这次**实际生效**的规则 ID，按提示词中的出现顺序。

**两者互补，别只看一个**：加一条只对 code 模式生效的规则 → work 模式 ID 列表一字不变、
但指纹变（表的内容动了）；改一句措辞 → ID 不变、指纹也变。

**已知边界：ID 列表区分不了变体**。`code.verify` 两个变体共用同一个 ID，所以
"用了 code.verify"不说明用了哪一版措辞——**措辞归因靠指纹**。这条边界是变异测试逼出来的：
把 `ActiveRuleIDs` 改成忽略档位，全部测试仍然绿（两个变体 ID 相同）。
测试绿不等于行为被守住了，动手前先问"这个断言到底看不看得见它"。

**改规则前后各跑一次**：

```bash
/tmp/gleam.exe rules                                    # 全表 + 指纹（离线：不读配置、不连模型）
/tmp/gleam.exe rules --task-mode code --tier coding     # 该场景生效 / 被挡掉的几条
/tmp/gleam.exe rules --task-mode work                   # 未生效栏会列出全部 code.* ——这就是"为什么没进提示词"
```

后两个视图里的「未生效」一栏最有用：它回答"为什么这条没进提示词"，
答案通常是被 `Scope` 挡了，而看代码不容易一眼看出。

**指纹变了不要去动门禁**：规则集变化在回归报告里只报一行（`规则集 xxx → yyy`），
**不卡门禁**——改规则是正常动作，卡它只会逼人摘掉 `--strict`，门禁整体失效。

**记录与渲染共用 `selectRules`**，这是底线：一份会撒谎的规则集记录比没有更糟。
以后再加任何"记录本次用了什么"的字段，先问它跟真实渲染是不是同一条路径，
并写一条双向一致性测试（记了的必须在提示词里、没记的必须不在）。

## 六、判断"该不该删"的正确姿势

Gleam 的稳定段是**被前缀缓存命中的**，所以删掉一段省下的 *token 费用*很有限。
真正的收益是**减少注意力稀释与指令冲突**——这**没法用"省了多少字节"论证，只能靠评测验证**。
所以：**先有评测集，再动减法**。别凭感觉删规则。

## 七、改完提示词/工具描述，跑 `gleam eval` 验一遍

评测集已经落地（`internal/eval/`），入口是 `gleam eval`。

```bash
go build -o /tmp/gleam.exe ./cmd/gleam

# 日常：select 深度，纯本地、零模型调用、离线可跑，秒级出结果
/tmp/gleam.exe eval

# 当门禁：仓库里带了基线，有回归就非零退出
/tmp/gleam.exe eval --baseline internal/eval/baseline-select.json --strict

# 改动后重新固定基线（确认通过率没退再存）
/tmp/gleam.exe eval --save internal/eval/baseline-select.json
```

三个深度：`select`（默认，只跑工具筛选，确定性）/ `plan`（跑到计划）/ `full`（完整目标，
会真的动工具，默认关进临时目录）。**没有 API Key 时只有 select 可跑**；plan/full 用
`--mock-llm` 只能验证管道通畅，验证不了质量。

### 7.1 断言口径：**不要**断言"工具在不在菜单里"

这是最容易踩的坑，第一版就这么写错了，16 条里 9 条红且大半红得莫名其妙。

`planner.go` 的 `selectTools` 末尾有一条**按注册顺序补齐**的兜底，菜单永远被填满
`MaxToolSchemas`（默认 12）个。所以"某工具在菜单里"既可能因为它相关，也可能只因为它注册得早——
**把工具说明改到丢光关键词，它仍可能被兜底塞回菜单，评测却全绿。**

正确口径是 `(*Planner).RelevantTools(goal)`：本地打分命中（得分 > 0）的那一层，补齐之前，
也不含 `RoleTools` / `ForceTools` / 字面命中（那些是模板与调用方的决定，不是"描述写没写清楚"的信号）。
再取**前 N 名**（`DefaultTopN = 5`，用例可 `top_n` 覆盖）：

- 窗口**外**的名次放行——本地打分是中文二元组 + 英文子串匹配，长尾全是偶然撞词，
  排 21 个里的第 11 名对行为毫无影响（模型只拿前若干个的 schema），拿长尾判误路由只会永远红；
- 失败详情要区分**"排到窗口外"（排序问题）**与**"完全没命中"（描述没写清楚）**，
  否则看报告的人还得回去手工复现。

### 7.2 本地兜底打分器的两条口径（2026-09-20 已修，写工具描述前先知道）

原先 `scoreToolNames` 把 `名称 + 完整描述` 一起打分，于是**描述里给模型看的举例与使用说明
也成了路由信号**。`gleam eval` 第一次跑就抓出四处误命中：

| 描述里的文字 | 撞上的目标 | 机制 |
| :-- | :-- | :-- |
| `不要自己拼 cron` | 你好，简单介绍一下你自己 | 「自己」这个二元组 |
| `goal 是到点真正要执行的事` | 给 utils.go 里的 parseDate 补充单元测试 | 英文词 `go` 作为**子串**命中 `goal` |
| 示例「每日下载目录整理」 | 把上季度销售数据整理成表格并汇总 | 「整理」这个二元组 |
| `（用户偏好、项目背景等）` | 检索我之前关于部署的偏好 | 与 `memory.search` 的「检索」同为 1 分平手，平手按工具名排序 → 保存工具排到前面 |

**现在的口径**（`internal/agent/planner.go`）：

1. **路由文本只取描述前 100 字**（`routingTextLimit`，见 `routingText(t)`）。
   容得下"什么时候用"那一句，排得掉紧随其后的参数说明与用法提醒。
   → **描述该写多长就写多长，路由只认前一段**；但**触发词必须写在前 100 字内**，
   否则该工具在相关目标上会选不到（`gleam eval` 的 `schedule-*` 用例就是守这个的）。
2. **英文/数字按整词匹配，且至少 3 个字符**（`minAlnumTerm`）。
   `go` 不再命中 `goal`；`go`/`in`/`is`/`id` 这类两字母词不进检索词表。
   中文仍是二元组子串匹配（没有分词器）。

写工具描述时的两条经验：
- **举例与"参数怎么填"放在第 100 字之后**，或者干脆留给 schema（`SchemaProp` 的示例）。
  举例放前面不仅污染路由，还会挤占真正相关工具的 schema 名额。
- **描述只讲"这是什么、什么时候用"，举例留给 schema。**
  `memory.save` 原来那句「（用户偏好、项目背景等）」与它 `tags` 的示例重复，
  去掉后描述变成「记住重要信息：写入长期记忆，跨会话可用」。

守卫在 `internal/agent/planner_routing_test.go`（6 条，用假工具与具体描述解耦）：
路由忽略描述尾部、英文整词匹配、两字母词被丢弃、截断边界、
**相关集 ≠ 菜单**（`reply` 在菜单里但不参与打分）、名称加权高于描述命中。

**实测影响**（逐项回退量的，16 条评测用例的系统提示词合计 85848 → 82964 字符）：

| 改动 | 提示词影响 | 修好的用例 |
| :-- | --: | :-- |
| 路由文本截断到前 100 字 | −1970 | chat-only、work-analyze-sales |
| 英文整词匹配 + 最小词长 3 | −685 | code-add-test |
| `memory.save` 描述去重 | −229 | memory-search |

**为什么"少误命中"能让提示词变短**：菜单模式的 schema 名额是固定的 12 个，
一个被误判相关的工具挤进去，就有一个真正相关的工具被挤出来——
而且被挤出去的那个反而更大。所以误路由的代价不只是"可能做错事"，
还有**提示词里塞了一堆用不上的 schema**。

### 7.3 加新用例的四条规矩

1. **必须有 `note`**：红的用例要能自己解释自己（有测试守着这条）。
2. **不能没有任何期望**：`Validate` 会直接拒绝——那种用例永远会通过，是评测最容易被架空的地方。
3. **只在 select 深度有意义的断言别硬塞**：`reply` 是被强制保留的收尾工具、**从不参与打分**，
   要求它"进前 N 名"是错的期望；步数、验收标准这类断言只在 `plan`/`full` 深度生效。
4. **查清但暂不修的，标 `known_issue`，别删用例。**
   标了的用例照常跑、照常打印失败详情，但不参与门禁；哪天通过了会以「已修复」出现，
   提醒你摘掉标记。**删掉会让问题悄悄回来；挂在门禁里会让评测常红、最后没人看。**
   注意它是**临时状态**：根因修好后记得摘标记（`note` 里写清"曾修 + 改法"，别只写"已知问题"）。

### 7.4 改完记得做的验证

- `go test ./...`（**别用管道接 grep**，会被沙箱 SIGTERM；改成 `> 文件 2>&1` 再 grep）
- 全绿后跑 `gleam eval --baseline ... --strict`
- 如果动的是"守卫"本身，做**变异验证**：故意改坏被测代码，确认对应守卫会红（还原后核对字节一致）
- **变异不响时先别急着加断言，先问"这个断言看不看得见它"**。踩过一次：把 `ActiveRuleIDs`
  改成忽略档位，测试全绿——因为变体共用同一个 ID，ID 列表压根看不出差别。
  这类"结构上就看不见"的差异，正确做法是写成显式的边界断言（把"看不出来"本身钉住），
  而不是堆一堆同样看不见的测试。
