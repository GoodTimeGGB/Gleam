### 步骤 panic 的边界：一次工具崩溃不该带走整批（批次 E）

- **来源**：Qoder Cloud Agents 的 **Batch** 篇。它把批量的验收标准压成四个词——可追踪、可恢复、可对账、可交付，其中一条是「超时、失败和重试不会污染其他任务」。这条判据正好落在 Gleam 唯一那个「批」上：`gleam eval`。
- **缺口**：`internal/agent/executor.go` 里每个步骤跑在自己的 goroutine 里，而**全仓没有任何 recover**（`grep -rn "recover()"` 只命中 `cmd/gleam/console_windows.go:17` 的控制台初始化）。工具实现里一次 nil deref / 越界就终止整个进程。
- **为什么在批上才是灾难**：`gleam eval --depth full` 跑 200 条用例时，第 5 条的工具 panic 会让**已经通过的用例、已经花掉的模型调用、整份报告一起消失**，重跑还要再花一次。在单条任务上它只是"崩了"。
- **修复点只能有一个，而且不能放在调用方**：panic 发生在**子 goroutine** 里，Go 的 recover 只在**同一个 goroutine 的 defer** 里有效——`eval.Runner`、`cmdGoal`、webui handler 各自加 recover 全都接不住。所以边界加在 `runStepGuarded`（`executor.go`）一处，四条执行路径（eval / goal / webui / 定时任务）一起受益。
- **三条设计约束**：①**转成已有的 `StepFailed`**，不新造状态——执行器早就把"步骤失败"建模成一等状态，没有理由让一次 panic 表现得比"这一步失败"更严重；②**收尾留在 guard 之外**——goroutine 里 panic 之后，defer 之外的剩余语句全部被跳过，所以 `close(state.finished[i])` / 落盘 / 计数 / 进度这四件事刻意留在外面（那里永远会执行），挪进去会让依赖这一步的下游**永远等不到放行**（症状是任务挂住，比崩掉更难查）；③**不静默吞掉**——步骤标成 `Failed`（任务不会被判 success），`ErrorKind` 单列 `types.ErrInternal`（"要改代码"与"换方案再试"是两个不同的动作，混进 `unknown` 会让一次工具缺陷看起来像一批业务失败），`Error` 带 `工具 panic:` 前缀与**截断到 7 行**的栈（带栈是因为 recover 之后 Go 不再打印任何东西，"哪一行炸的"就丢了；截断是因为它会进 `tasks/*.json` 与 `runs/*.jsonl`，完整栈几十行会把任务记录淹掉）。
- **测试 3 条 + 变异 6 处全响**：整批跑完 / 该步失败 / 错误含 panic 值 / 归因是 internal / 栈有界 / 同批另一步不受影响；下游必须被放行（用显式 20 秒超时把"挂住"变成一条可读的失败信息，而不是让 `go test` 的 10 分钟兜底把它变成一句看不出原因的 deadline）；panic 要**进得了归因分布**。变异：去掉 recover、标成成功、归因塞 unknown、栈不截断、丢掉 panic 值、panic 路径不释放下游——六处全响，最后一条跑了 21 秒才红，正是设计中的症状。

### 评测报告回答「这批花了多少」；归档任务不再被报成「不存在」（批次 F）

- **P1 · 评测用量**：`internal/eval/runner.go` 的 `runCaseOnce` 一直拿得到 `GoalResult`，却把 **`Usage` 丢了**——报告只有 `PromptChars`（**成本代理**：提示词多长），没有 token（**成本本体**：实际花了多少）。这不是新增原则，是补完已有的：`eval.go` 的注释早就写着「提示词成本与通过率必须记在同一行」。
  - **不复用 `types.TaskUsage`，另立 `eval.CaseUsage`**：前者带 `DurationMs`，而 `CaseResult` 已有 `DurationMS`——同一个报告里两个名字几乎一样、口径不同的耗时，读的人一定会拿错。转换点收敛在 `usageFromTask` 一处，将来加字段必须在那里显式决定一次，不会静默漂移。
  - **`--repeat N` 的每一遍都算**：重跑真的调了模型、真的花了钱；只报首遍会让 `--repeat 3` 看起来与 `--repeat 1` 一样贵——那是**账错了，不是省了**。通过率仍取首遍（口径可比），用量取全部遍数。
  - **nil 与 0 分开**：`select` 深度零模型调用，用量**缺席**（nil）而不是 0——一个 0 会被读成"计量了但没花钱"。`plan` 深度**会**调模型（规划那一次），但它的调用不经过 `RunGoal`、没有 taskID 登记，归集不到用例上，所以报告**明写**「用量：未计量（plan 深度的规划调用不经过 RunGoal）」——**这是缺口，不是 0**。补它需要给 `Agent` 开两个公开方法（登记 + 读取），为一个次级深度的成本核算扩 API 不划算，先记为限制。
- **P2 · 归档读回**：`internal/webui/handlers.go` 的 `handleGoalGet` **只读内存**（`s.tasks` 是纯内存表，进程重启即空，还有 `maxRetainedTasks = 200` 的淘汰上限），取不到就回 `404「任务不存在」`。而终态档案就躺在 `<DataDir>/tasks/<id>.json`，`gleam replay <id>` 读的正是它。于是**同一个事实、两个入口给出相反答案**：CLI 说有、Web UI 说 404——而 404 是一个明确、自信的答复，用户会据此认为记录丢了，然后重跑，**重复花钱**。
  - 改法是**最小的那一半**：内存 miss 时回落读单条归档；**不接管列表**（列表要不要显示历史、要不要分页是另一个决定，也会让 `pruneTasksLocked` 的语义变含糊）。这里只修"别撒谎"这一件事。
  - **回落读盘带来一个新攻击面**：`id` 来自 URL 且会被拼进文件路径，所以先挡 `..` 与路径分隔符——挡不住就等于把数据目录下的任意 JSON 变成一个可读接口（`settings.json` 里可能有密钥）。
  - 两处如实差异写进了 `archivedTask` 的注释免得被当成 bug：`GoalResult` 里**没有 `Mode` 字段**（模式不参与结果，只影响怎么跑），所以归档任务的 `mode` 为空；`Events` 是 SSE 流、进程退出即散，所以时间线是空的——但 `Result.Steps` 是完整的，**时间线空不等于过程丢了**。
  - **测试设计上踩的一个坑**：路径穿越那条的诱饵最初写成 `<dataDir>/settings.yaml`，而穿越路径 `tasks/../settings` 拼出来的是 `settings.json`——解析不到，于是接口照样回 404，**那条断言是空的**（改坏守卫也不会响）。改成 `.json` 后"守卫没挡住"才会真的读到一个文件；另外测试同时**直接调 `archivedTask`**，因为路由本身可能先挡掉一部分形态，只测 HTTP 的话守卫本身可能测不到。
- **测试 8 条 + 变异 8 处全响**（P1 五处：不拷 Usage / 只算首遍 / 不汇总进报告 / 漏抄 CachedTokens / 抄错字段；P2 三处：去掉归档回落 / 读不到也回 200 / 去掉路径穿越守卫）。

### max_concurrency 是单任务的，不是全局（批次 G）

- 来源的调度判据是"受容量、顺序、闲时时段约束"。Gleam 的调度器**没有任务级容量上限**（`scheduler.go` 对每个到期 job 直接 `go fire(j)`），而且 `max_concurrency` 是**单任务的**——`executor.go` 里 `sem := make(chan struct{}, conc)` 建在**每次计划执行**里，所以 N 个任务并发时实际是 **N×8**，不是 8。
- 加全局队列是架构变更、收益未验证（与 §4.6.24 里"不做完整断点续跑"是同一类判断），所以**不改代码**；但这个名字会被误读成全局，于是按负知识的规矩记进 `docs/known-limits.md` §一（同类先例：「场景模板的 tools 是提示不是白名单」）。
- 措辞从 61 字符压到 58 字符——那一版超了每行 ≤60 的预算 1 个字符，且把"为什么"（每次执行各建一个信号量）放进了理由列，比原稿更直接。

### 明确不做：通用批量提交接口与行级隔离（附理由）

- **通用批量提交接口**（JSONL 输入 / `POST /api/goals/batch`）：来源的场景是"业务系统把 10 万条任务写进 JSONL 交给平台"。Gleam 是单机单用户，用户就坐在键盘前，没有"从上游系统接收任务流"这回事；真正需要"批"的地方只有评测，而它已经有 `--cases` + 分层 + 基线。加一个通用批接口 = 为不存在的场景建一套架构（还要带上幂等、配额、对账）。
- **行级隔离（坏一行跳过、其余继续）—— 这条方向相反。** 来源的"行"是**数据**（客服会话、合同），坏一行是脏数据，跳过是对的。Gleam 的"批"是**用例集**：受版本控制的代码资产，坏一条是**测试集自身的 bug**。静默跳过会让评测**悄悄少跑一条而通过率看起来没变**，正是 `cases.go` 注释里防的那件事（"没有任何期望的用例永远会通过……评测最容易被这样悄悄架空"）。所以 `Validate` 保持"遇第一条即 return"。**判据：问一句它说的那个「一行」，在我的语境里是数据还是代码？** 是数据 → 跳过对；是代码/配置 → 必须整批拒绝，否则就是把 bug 静默化。
- 其余：闲时调度 / 错峰折扣（单机没有在线业务要避让、也没有计费对象）、`output.jsonl` / `error.jsonl` 分文件（`--json` 已给出完整的机器可读报告，再分两个文件是同一份数据的第二种形状，会立刻产生"两处各写一遍然后漂移"的问题）、单批 10000 项上限（用例集是人工维护的几十条）、自动断点续跑（`pending.go` 已记为"收益未验证"的刻意不做）、`identity_id` / 多租户 / Template 引用（上一份清单已判不做）。

### 四类状态：各自住在哪、活多久、谁能改（批次 D）

- **此前的缺口不是"没有文档"，而是"没有一处能一眼答完"**：配置 / 会话 / 记忆 / 任务这四类各自的落盘位置、生命周期、谁能改，事实其实都在——README 的架构图（那是**代码**布局，不是**数据**布局：`internal/harness/memory/` 是包名，不是文件位置）、设计文档十几个小节里的零散交代、以及若干处 `filepath.Join`。于是用户问"我的记忆存在哪""删了 `memory/` 会不会把会话也删了"时，答案要靠翻源码；agent 更糟——它会**一遍遍重新 grep**。典型的知识不在它该在的地方：事实存在，入口不存在。
- **路径清单的 owner 是代码，不是文档**：`cmd/gleam/state.go` 的 `stateEntries` 是全部落盘位置的唯一清单（18 条，带类别 / 路径 / 一行说明）。设计文档 §4.6.26 **刻意不重复列路径**——重复列一定会漂移，而漂移方向通常是文档更旧（改代码的人不会想起来同步文档）；那里只写四类的语义与理由。
- **`gleam doctor` 增加「状态落盘」一段**：按四类打印每条路径的现状（目录报「N 个文件 · 体量」、文件报体量、不在就报 `[无]`），外加每类一句「谁能改」。
- **这一段是报告不是判定**：①九项与来源里的九个坑**一一对应**（`readiness.go` 的注释与 `readiness_test.go` 的顺序断言都钉着），不能塞成第十项；②更要紧的是**缺目录是常态**——没用过记忆就没有 `memory/`，没跑过定时任务就没有 `schedules.json`，做成判定会产生一批假不合格，然后用户加个开关把整个 `--strict` 废掉（正是 `strictErr` 注释里防的那件事）。所以不影响退出码，`--json` 也不带它（它是给人看的地图，不是判定；CI 要的是结论）。
- **落地时发现的第一件事：目录名与语义类别不一一对应。** `memory/context.json` 住在 `memory/` 目录下，但它是**会话**状态（滚动上下文与压缩状态），不是跨会话积累。清单按语义把它归到「会话」并点出这个错位——不点出来的话，读者会按目录名归类，然后得出"删了 `memory/`，会话也一起没了"，而长期记忆与会话上下文其实是两套生命周期。
- **落地时发现的第二件事：来源的四类框不住 Gleam 的一类。** 云上多租户里"能力"由平台提供、用户不持有技能文件；Gleam 的技能与片段是用户自己攒的，既不是配置（不决定怎么跑）、也不是记忆（不是"发生过什么"）。硬塞进四类里，读者会以为它们与长期记忆同寿、同一种删法。所以单列第五类「资产」，并写明它为什么在四类之外。
- **数据目录之外的条目如实标注**：配置主文件（`configs/config.yaml`）不在数据目录里——它由 `--config` 指定，默认取**当前目录**下的这个相对路径（`main.go:172`）。清单里标 `Outside` 并按当前目录解析，换个目录跑就显示 `[无]`——这是**如实反映**（那时确实没加载任何配置文件，只剩默认值 + 环境变量），把它伪装成"一定在数据目录里"才是误导。
- **测试（`cmd/gleam/state_test.go` 7 条）**：表的形状（四类齐且在「资产」之前、路径相对且不含 `..`、类别已声明、每类至少一条、无重复路径）、渲染、缺路径安静报 `[无]`、目录**递归**计数、体量格式化、已知成员不许被删。
- **其中一条是这批的核心**：`TestStateEntries_CoverWhatRuntimeCreates`——**真装配一套 runtime、真跑一个任务、再把装配不会碰到的几处显式触发，然后 walk 数据目录顶层，把盘上真实出现的条目与表逐一对账**。这是"从盘上验回来"，不是"断言函数被调用过"——对一张清单来说后者毫无意义。清单最容易出的错不是"写错一条"，而是**代码新加了一处落盘、表没跟上**；那时报告会漏报一个目录，而漏报的形态是"看起来数据目录里就这些东西"，比不报更坏。这条测试自己还有一道前提断言：先确认盘上真的出现了 `memory/` `skills/` `tasks/` `conversations/` `spaces/` 五个目录，否则对账会**空对空地通过**——那种"以错误的理由通过"比直接失败更坏。
- **负例控制（两个）**：①删掉 `runs` 那一行 → 两条红，且报的正是该报的话（覆盖对账说「数据目录里出现了 "runs"，但 stateEntries 里没有它」，已知成员说「表里缺 "runs"」）；②把 `countTree` 改成不递归 → 递归计数红，症状正是那个误导性输出「0 个文件 · 0 B」，而 `tool-output/<taskID>/<stepID>.txt` 恰恰是最需要知道体量的那个（它是缓存，裁剪失效时第一个涨起来的就是它）。
- **顺带一个观察**：写这一批时 `go test ./cmd/gleam/` 又一次命中 `package crypto/rand is not in std (C:\Go\src\crypto\rand)`——签名与上次记录的一模一样，且这次落在 `go test` 上（不是 `go run`）。第三次独立命中，进一步印证"那是工具链环境噪声，不是某条命令的特性"。

### 对照清单的落地进度表头（文档漂移清扫）

- **起因**：做批次 D 时打开「判断层与评测口径对照与升级清单」，表头写着 P2-2「未落地」——而它上一批就落地了（§4.6.25）。顺手把四份清单扫了一遍，发现这是**一类**问题，不是一处。
- **这类漂移为什么坏**：四份 `*对照与升级清单.md` 是**某一天的取证快照**（写「`ExecutedPlan` 是死代码」「`web.fetch` 无 SSRF 防护」「`skill.list` 全量返回」，写下的当天都准确），然后被逐条修掉——而清单**不会**自己更新。矛盾的方向永远是**清单更旧**（改代码的人不会想起来同步清单）。而 `docs/known-limits.md` 存在的理由正是「agent 读到这里就不会反复提同样的建议」：一份说「这里没有 SSRF 防护」的清单，会让下一个 agent 去**修一个已经修好的洞**——重复开工正是这几份清单开头反复强调要避免的浪费。
- **修了六处**：①判断层清单表头——P2-2 移入已落地（§4.6.25），并补上原表头**漏列的两项**（P0-2 验收同源同档 → §4.6.18 + §4.6.19；P1-3 数据出网留痕 → §4.6.16），未落地只剩 P4-1；②Harness 清单**根本没有落地进度表头**，而它的 §六 四批（P0 / P1+P3-1 / P2+P3-2/3/4 / P4+P5）**全部已落地**（§4.6.12–§4.6.15）——整个 §六 读起来像待办清单，补表头 + 四批各标已落地；③AI Coding 清单补落地进度（批次 A → §4.6.22、批次 B → §4.6.23，其余在 §五 末尾标为明确不做）；④Qoder 清单补落地进度（**已全部收口**：P0 → §4.6.24、P1 取证结论不做、P2 → §4.6.26）；⑤`docs/known-limits.md` 头部的「三份对照清单」→ **四份**（这是**活指针**，不能停在旧计数）；⑥设计文档 §4.6.23 同一处「三份」→「四份」——但保留后半句「此前这些散落在三份清单」，那是**历史**，改了反而失真。
- **立的约定（写进设计文档 §4.6.23）**：①每份清单的表头必须有「落地进度」行——哪些条目已落地、各自对应设计文档哪一节、哪些是明确不做、**还剩什么没落地以及被什么阻塞**；②**正文的判定表不随落地回改**（它是报告原文，改了就失去"当时怎么看"的价值），表头负责把它标注成快照并指向设计文档看现状。
- **为什么不加机械检查**：「每个清单文件里有落地进度段」正则一行就能判，但它**防不住真正的漂移**——真正的失效是"表头说的和设计文档实际的不一致"，那需要读懂语义。加这种检查只会给出"已经守卫了"的错觉，而按本仓库自己的判据，**一个不能真的失败的闸门比没有闸门更坏**。所以靠约定 + 落地时回来更新，并把这条理由一并写下来，免得后人"顺手补一个检查"。
- **顺带确认 P4-1 的阻塞前提仍成立**：环境变量 `GLEAM_API_KEY` / `GLEAM_LLM_BASE_URL` / `GLEAM_LLM_MODEL` 与 `~/.gleam/credentials.json` 全无（`settings.yaml` 里也没有 key 字段），所以「判断分层」仍无法做实测——阈值必须用 Gleam 自己的评测集校准，不能拍一个数。状态记在 `docs/known-limits.md` §三「还没到条件」。

### 新增文档引用门禁：悬空的 § 指针是静默失效（第 1 层扩展）

- **起因**：做上一节的漂移清扫时顺手发现另一种坏法——正文写着「见 §4.6.26」，而那一节还没写、或者改了号。Markdown 没有链接检查器管 `§` 这种自造指针，于是**读者跟着指针走到空处不会报错，只会以为"文档里没写"**；写的人也不知道自己指错了。这与 broken link 同类，只是没人管。
- **它与「落地进度段」那条恰好相反，所以该做成闸门**：上一条判的是"表头说的和事实一致吗"（要读懂语义，防不住真正的漂移，做了只会给"已守卫"的错觉）；这一条判的是"指针指向的东西在不在"——**可以真的失败、且失败即有缺陷**。分界就一条：**能不能真的失败，且失败是不是即缺陷**。
- **`scripts/check-doc-refs.py`（新增）**：从设计文档抓 `^### (4\.6\.\d+)` 的小节号集合，遍历所有 `.md`（跳过 `.git` / `node_modules` / `dist` / `.workbuddy-ai` / `pack`）找 `§4.6.N` 引用，悬空就逐条打印 `文件:行号 §小节号` 并非零退出。两个细节：①**解析不到任何小节时也非零退出**——设计文档的结构变了而检查还在报"通过"，是最坏的结果（检查本身失效了）；②`§4.6.N` 这种**泛指**写法不算引用（它说的是"这一片"，不是某一节）。
- **归在第 1 层，不新开一层**：它本来就是"文本层的格式约定"——gofmt 管**代码文本**、它管**文档文本**，都便宜（各只一两次进程创建）、都不需要编译，按成本序该一起最早撞墙。而且**层数一变，"六层"这个说法在 `AGENTS.md` / `README` / 设计文档 / 技能里全要跟着改**（先问归属，再谈实现）。第 1 层由 `fmt_check` 改名扩展为 `text_layer`，`step` 名字改为「格式与引用（gofmt + §ref）」；解释器解析（`python3` / `python` / `py`）提到脚本顶部复用，**找不到 python 时算这一层没过**而不是静默跳过——静默跳过的检查等于没有检查。
- **负例控制**：把某份清单里一处引用改成不存在的小节号 → **第 1 层 3 秒内失败**、点明 `.\Qoder Cloud Agents 对照与升级清单.md:9`、`PIPESTATUS[0]=1` 立即停止；还原后全仓 99 处引用全部有效。同层的 gofmt 与它共用一次 `step`，任一条失败即整层失败——**这一层没有"部分通过"**。
- **一个自我约束**：描述负例控制时**不能写真造的小节号当例子**，否则检查会把这段说明本身判成悬空引用。检查器分不清"举例"与"真引用"，这是对的——写文档时避开即可。
- **同步的三处描述**：设计文档 §4.6.23 的六层表第 1 行改为「格式与引用」并补上这一段理由；`README` 的闸门行与自测节同步；`AGENTS.md` 的命令表行改为「格式与引用 | `gofmt -l ./internal ./pkg ./cmd`；`scripts/check-doc-refs.py`」（仍在 1950 字符预算内）。

### 环境噪声不是「一次调用」，是一段窗口：重试策略改成「最多 3 次 + 间隔」

- **证伪**：`verify.sh` 又一次红在第 4 层——首次跑 32 秒失败，紧接着的**重试也失败**，而且两次命中的是**不同的** std 包（`internal/stringslite` / `internal/poll` / `internal/syscall/windows`）。原来的假设是"噪声属于一次调用，立刻重跑就好"，实测不成立：它是一段几十秒的**窗口**，窗口里任何一次 `go` 调用都可能红。而当时做的正是"重跑一次"——按本仓库自己的判据，偶发失败要当**闸门可信度**问题修，不是重跑一次。
- **改法**：`scripts/lib/gonoise.sh` 的 `go_retry` 由「重试一次」改成「最多 3 次尝试 + 中间等 3 秒」（`GLEAM_GO_FLAKE_ATTEMPTS` / `GLEAM_GO_FLAKE_BACKOFF` 可覆盖）。**仍然只吃那一个签名**，所以"多试几次"只可能把假红变绿、不可能把真红变绿（真实失败根本不带这个签名，因此**一次都不会重试**）。不做无限重试的两个理由：①环境持续坏下去时闸门要如实红，不能靠重试把问题拖过去；②每次尝试都是完整跑一层（第 4 层 30–80 秒），次数越多、假红时等得越久。这两个数是**旋钮，不是判据**。
- **探针从三段扩到四段**（`scripts/lib/gonoise_probe.sh`）：①噪声一次后成功 → RC=0、调用 2 次；②真实失败 → RC=1、**只调 1 次**、且不被误认成噪声；③**噪声两次后成功 → RC=0、调用 3 次**（新增，这条才证明"能熬过窗口"）；④噪声一直存在 → RC=1、调用 3 次（有上限）。探针自己把等待旋钮压到 0，第 0 步仍是一秒量级。
- **四段探针立刻抓到了东西**：改之前是"噪声两次仍失败、期望调用 2 次"，改成三次尝试后那条会立刻红——策略一变、探针就响，这正是它存在的理由。

### 修掉一条时序脆弱的假红测试；并纠正「探针 <1s」这个错数字

- **现象**：全量 `go test ./...` 里 `internal/tools/shell` 红了——`TestShell_ExecExitCode` 报「非零退出码不应返回 error: 命令超时（10s）」，而**单跑该包 3.8 秒就过**。跑的是 `cmd /c exit 3` 这种一句话命令。
- **根因**：这条测试用 `New(10 * time.Second)`，10 秒只是**兜底**，与被测行为无关（它断言的是「退出码怎么报」）。而本机进程创建极慢——实测 `TestShell_OutcomeReportsNonZeroExit` 单跑就要 10.51 秒（它跑三条命令，每条约 3.5 秒）。于是并发跑时 `cmd /c exit 3` 越过 10 秒，测试报「超时」。**一个偶发假红的闸门很快就会被忽略**，与本仓库此前修掉的两条环境耦合假红测试（`TestPlatformBrowserMatrix` / `TestExecutor_SkipsRepeatedFailedCall`）同源。
- **改法**：三条与耗时无关的测试（`ExecEcho` / `ExecExitCode` / `OutcomeReportsNonZeroExit`）改用 `execTimeout = 60s` 常量，注释写明理由。**没有少测任何东西**：超时行为由 `TestShell_ExecTimeout` 覆盖，它显式传 `timeout_sec: 1`，改完仍是 1.23 秒通过（这就是负例控制——超时路径照旧生效且仍是秒级）。
- **顺带纠正一个自己写错的数字：探针不是"秒级"。** 早期文档里写「第 0 步自检 `<1s`、所以放在最前面（最便宜的检查最先撞墙）」——**两处都不对**。实测：`verify.sh` 里六层合计 658 秒、总 803 秒，**差额约 145 秒就是探针**。根因是**进程创建本身贵**：实测 40 次 `$(cat …)` = 107 秒，约 **2.7 秒/次**，而探针全是进程创建。
- **所以它排在最前面不是因为便宜，是因为它是前置条件**：重试逻辑坏了，后面每一层的结论都不可信——先证明尺子，再量东西。已改的四处表述：`scripts/verify.sh` 的注释、`scripts/lib/gonoise.sh` 的注释、设计文档 §4.6.23 的六层说明与探针段、`docs/known-limits.md` 新增一条（本机进程创建约 2.7 秒/次）。这条也顺带解释了这个仓库里其它"看起来应该很快"的脚本为什么慢（`smoke.sh` 443 秒里绝大多数是进程创建）。
- **验证**：`bash scripts/verify.sh` 六层全过、803 秒、退出码 0（第 4 层 68 秒，不再假红）。

### 后台任务的结果必须送达：通知策略 + 四个宿主接线（批次 C）

- **此前的缺口**：`bindSchedulerFire` 里定时任务跑完的返回值被直接丢弃（`rt.agent.RunGoal(...)` 的返回值没人接，旁边留着一行 `_ = notifier`）。用户关掉窗口之后，**没有任何东西会告诉他这个任务跑完了、跑成了还是失败了**。定时任务的整个价值就是「不用盯着」——而缺了这个，用户恰恰必须盯着；更坏的是**失败也静默**：一个每天 9 点的巡检连续失败一周，用户会以为一切正常。
- **通知要有策略，不是一律打扰**：`scheduler.Job` 增加 `Notify`，三值 `always` / `on_failure` / `never`，**默认 `on_failure`**（成功静默、只报异常）。判断收敛成 `Job.ShouldNotify(succeeded)` 一个方法——散在调用点判一定会漂移，而漂移方向通常是「某个调用点忘了判」，于是失败被静默掉。判据只有一份：**只有 `GoalSuccess` 才算成功**，`partial` 与 `cancelled` 都要通知（一个每天跑、每次都只做一半的任务，用户最需要被告知）。存量脏值按默认走，别让一个脏字段把失败通知静默掉。
- **事件出口与进度分开**：`agent.Notifier` 增加 `OnTaskDone(types.TaskDoneEvent)`。进度是「正在发生」，丢了就丢了；完成是「已经发生且必须被记住」。`TaskDoneEvent` 自带 `Origin` 与 `Succeeded()` / `StateText()` / `Title()` / `Line()`，三个宿主**共用一份措辞**，不各写一遍 switch（那种分叉最终表现为「某个入口的说法和别处不一样」）。
- **系统通知只有一份实现**：`desktop/notify.go` 的平台分支导出为 `Notify(title, message)`，工具与调度器共用，避免两处各写一份然后漂移。新增 `GLEAM_NO_SYS_NOTIFY`：自动化环境能关掉真弹窗，但**关掉不是静默丢弃**——待发内容打到 stderr，否则「通知发了没有」无从断言。
- **接线断言（第五次）**：单测 `ShouldNotify` 的表格只能证明判据对，证明不了它真的被调用了——而本仓库栽过四次的正是这一类。做法是把 `runGoalFor` 与 `sysNotify` 抽成可注入的变量，断言**两条出口**（系统通知 + 事件推送）在该响时都响、该静默时都不响；另加一条走 `bindSchedulerFire` + `TriggerNow` 的路径断言，**不信任「闭包里写了调用」**。
- **惰性读 notifier**：`webui` 命令里 `bindSchedulerFire` 在 `webui.NewServer` **之前**调用，绑定时 `rt.agent.Notifier` 还是 nil。必须在 fire 闭包**内部**读，测试把「绑定之后才换宿主」钉成断言，捕获式写法会立刻红。
- **落地时改掉的第二处（不在原计划里）**：`webui.OnTaskDone` 原来写的是「如果这个任务在 `s.tasks` 里就落盘」，而 `s.tasks` 只由 `POST /api/goals` 填充——定时任务不是从那里提交的，**这个 if 恒为假**，看起来写了持久化、实际只剩广播，用户几小时后打开窗口时 SSE 早就断了。这是「判据对但线没接」的另一种形态：**判断没错，前提假设错了**。改法：表里没有就按结果补登记，再落事件，并补 `pruneTasksLocked`。对应断言也必须换形状——从读接口验回来（推事件后走 `GET /api/goals/{id}`，读不到就是没送达）。
- **配套 API 面**：`ScheduleCreateWithNotify` **先校验策略再创建**，不留「任务建好了但策略没上」的半成品；新增 `POST /api/schedules/{name}/notify` 与 JSON-RPC `schedule/notify`（策略是跑起来之后才会想改的东西，要求删掉重建就会让用户选择忍受噪音）；`jobToScheduleView` 印**生效值**而不是原始字段（空串表示「用默认」，但界面要回答「这个任务跑完会不会通知我」），存量脏值如实印出、不悄悄改成默认。
- **负例控制（五个）**：①绑定时捕获 notifier → 接线断言红；②`ShouldNotify` 短路 → 策略表红；③视图印原始字段 → agent + webui 双红；④webui 不补登记 → 两个用例红（读接口 404）；⑤`fire` 路径不送达 → 冒烟 2 项红、`RC=1`。冒烟从 37 项涨到 **45 项**。

### 截断是「有损」不是「丢失」：超长工具输出的落盘缓存（P2-2）

- **此前的缺口**：工具输出注入下游前按「头 3/5 + 尾 2/5」截断（`MaxOutputRunes`，默认 6000 字）。截断本身没问题（上下文有限），但被丢掉的中段可能正是关键——一份两万字日志里的第 1 万行。原来的兜底是提示语里的「请缩小读取范围，或用 file.read 精确取用」，而那要求模型**先意识到自己缺了什么**，可它只看到首尾，恰恰意识不到中间有什么。**一条它想不起来的后路，等于没有后路。**
- **改法**：超限时把完整原文写到 `<DataDir>/tool-output/<taskID>/<stepID>.txt`，注入内容改成「头 + 尾 + **完整内容见 `<path>`**（临时文件，任务结束后可能被清理）」。
- **这是缓存不是归档（A23）**：按 `spillMaxTasks = 200` 按 mtime 裁剪，所以提示语里必须写明「临时文件」——否则模型会把它当持久产物引用，而那个文件几轮之后就不在了。裁剪挂在 `Execute` 收尾而不是任务收尾：任务收尾有三条路（正常 / 取消 / 技能），挂三条里迟早漏一条，而漏掉的那条会一直涨。清理失败一律忽略——一个「为了省磁盘把任务弄挂」的清理逻辑，比不清理更坏。
- **两条边界，因为失效方式不同**：①`safeSeg` 白名单净化（只留字母数字与 `-_.`，去掉首尾点，兜底 `_`）——`step.ID` 直接来自模型输出的计划 JSON，而计划校验只查了「非空」「不重复」（`planner.go:582`），**没做路径安全**，所以 `"id": "../../../x"` 能一路走到落盘，而这是**写**；②`toolutil.ResolveInRoots` 与工具读写走同一套校验（两套一定会漂移，而漂移方向通常是「新加的那条更松」）。负例控制时把第 1 道关掉，**第 2 道独立兜住了越界**——这就是两道都要留的意义。
- **落地时抓到的三个问题（都是测试逼出来的）**：①落盘名跟着「引用方」而不是「内容来源」走，一步引用两个来源时会**互相覆盖**，两个路径指向同一段内容——比不给路径更坏；②提示语（含一条可能很长的路径）会把预算**撑破**，假上限比没有上限更坏（调用方按它分配上下文，却在某批任务上悄悄超出，表现为「偶发」的溢出）→ 改成先算提示语再按剩余预算分配首尾，剩余不足 80 字时退回纯截断；③落盘失败必须说出来并给退路，装作成功会让模型反复重试同一个引用，而真正的原因（没配数据目录 / 磁盘满 / 权限）一次都没被说出来。
- **小预算不落盘**：`budget < 160` 时纯截断。提示语含路径要占几十上百字，预算太小时会把正文挤没；而「落了盘但提示语里放不下路径」等于没落。
- **负例控制（三个）**：①`safeSeg` 不净化 → 性质断言红（且第 2 道防线独立兜住越界）；②落盘名跟引用方走 → 两个来源落进同一文件，红；③预算不扣提示语长度 → 实际 766 字 vs 预算 500，红。
- **断言形状**：`safeSeg` 的测试以**性质**为主（不含分隔符、不是相对路径段、非空、**幂等**），而不是逐字比对——安全依赖的是这几条性质，逐字比对只会在实现微调时变成维护负担。

### 补漏：孤儿孙进程把 Wait 拖到包超时（shell.exec）

- **症状**：`go test ./...` 偶发失败——跑到 `internal/tools/shell` 卡满 300s 包超时，而单跑该包 10s 通过。
- **根因不是"某条命令慢"，是三个条件叠加**：①`Stdout`/`Stderr` 是 `bytes.Buffer`（不是 `*os.File`）时，`os/exec` 会另起 goroutine 把管道内容拷进 buffer，而 `Wait` **要等这些 goroutine 结束**；②管道写端只要还有**任何**进程持有，拷贝就永远不返回；③`exec.CommandContext` 在 Windows 上只杀**直接子进程**，外层 shell 起的孙进程会存活并继续持有继承来的管道句柄。于是"命令超时"这条正常路径在某些时序下变成"整个测试包挂到超时"。
- **修法**：`cmd.WaitDelay = 5s`（Go 1.20+）——进程退出后等管道关闭的上限，到点让 `Wait` 返回 `exec.ErrWaitDelay`。
- **为什么要为一次偶发失败动代码，而不是"重跑一次"**：一个偶发失败的闸门很快就会被忽略，而忽略之后它连"哪一条失败了"都不再提供。这跟 `verify.sh` 建立时抓出的三个问题（`set -e` 豁免、trap 污染退出码、`go run` 不稳）是同一类：**闸门的可信度就是它的全部价值**。
- **回归测试**：造一条"自己立刻结束、但留下活 30 秒的孙进程"的命令，断言耗时远小于 30 秒（实测 5.6s）。负例控制时把 `WaitDelay` 关掉 → 耗时 31.4s 且红。
- **顺带钉住一条不变量**：`ErrWaitDelay` 意味着 stdout/stderr 很可能只拷到一半，把它当完整输出用就是**静默截断**（读的人会以为命令只输出了这些，然后照着残缺输出下结论）。所以结果里带 `output_incomplete: true` 与一句说明，并补一条反向控制——正常命令**不能**被标记为不完整（永远亮着的告警等于没有告警）。

### 环境噪声的判据只写一份 + 闸门自检（补漏）

- **为什么还要再动一次**：上一批把「环境噪声重试」加进了 `verify.sh`，但**加完当天第 5 层又红了一次**——红在 `smoke.sh` 自己的 `go build`（同一签名 `is not in std (`）。三个闸门脚本各写一遍重试逻辑，迟早只在一处加、另两处漏；而漏掉的那处会继续偶发变红，然后整个闸门被忽略。「一个事实一个 owner」在这里的具体含义就是：**噪声的判据只写一次**。
- **抽出共用实现**：新增 `scripts/lib/gonoise.sh`（`GO_FLAKE_RE` + `go_retry <说明> <命令…>`），`verify.sh` / `smoke.sh` / `smoke-replay.sh` 各自 `source` 它；`verify.sh` 原来内联的 `go_step` 定义块删掉，四处调用（第 2/3/4 层与第 6 层的构建）改走共用实现。
- **踩到的坑：`set -e` 下的裸赋值会让重试逻辑一次都跑不到。** 第一版写成 `out=$(cmd); rc=$?`——赋值语句的退出码就是命令替换的退出码，**在带 `set -e` 的调用方里这一行直接退出脚本**。症状极具误导性：脚本在某一行静默结束，看起来像构建失败。调用方有没有 `set -e` 并不一致（`verify.sh` 没有、`smoke-replay.sh` 有），所以共用函数必须按有 `set -e` 的情况写：`out=$(...) && rc=0 || rc=$?`（`&&`/`||` 列表里 `set -e` 不生效）。
- **把闸门自检做成第 0 步（不占层号）**：重试逻辑本身也要被证明，而且要**在闸门里自动跑**，不能靠人记着去验。新增 `scripts/lib/gonoise_probe.sh`（当时写的是「`<1s`、不碰 Go 工具链」——**`<1s` 这个数字是错的**，实测是分钟级；场景后来也从三个扩到四个。两处都已在下文 2026-09-23「修掉一条时序脆弱的假红测试」那节纠正），三个场景：①噪声一次后成功 → RC=0、命令调 **2** 次、**且必须打印**（静默重试等于把抖动藏起来）；②真实失败（无签名）→ RC=1、命令**只调 1 次**（确定性失败不该被重试掩盖）；③噪声两次 → RC=1、调 2 次（不无限重试）。`verify.sh` 在函数定义之后、第 1 层之前调它，失败即 exit。**"不重试"那一场景比"重试"那一场景更重要**——只验重试成功，等于只证明了"失败会被吞掉"这条路径是通的。

### 审计的四种用法：同一份记录，四种问法（批次 A）

- **此前的两个缺口**：① 用法只有一种——`gleam replay` 只能把记录排给人看；② **前置不成立**——任务记录是**跑完之后写一次的终态快照**，进程若在运行中退出（关窗口、重启、强杀）那次运行**什么都没有**，没有记录就没有回放、没有归因，连"跑到哪一步了"都答不上来；而 `--rerun` 会**真实调用工具**，一个 20 步的任务在第 17 步失败，从头重跑等于把前 16 步的副作用（写文件、发请求、下单）再做一遍。
- **四种用法**：回放（排给人看）/ 重跑（`--rerun`，原样再执行一遍并逐项对比）/ 恢复（`--from <stepID>`，该步之前**沿用当时结果、不重新执行**，从该步往下跑）/ 分叉（`--from <stepID> --tool/--args`，同一前提换一种走法）/ 比较（`--diff <A> <B>`）。
- **运行中落盘**（`internal/agent/runlog.go`）：执行器新增 `Sink`，每步结束后回调一次，落成 `<DataDir>/runs/<taskID>.jsonl`。**JSONL 而不是 JSON 数组**——追加必须是 O(1) 且不依赖读回旧内容，边跑边重写整个数组既慢、又会在崩溃时留下半个文件把前面写好的部分一起毁掉。**半行 JSON 跳过而不是整份拒绝**——一份"缺最后一行"的日志仍然能回答"跑到哪一步为止"。**正常结束就删**——任务记录写成功后运行日志就是冗余的，于是 `runs/` 里留下的**只有那些没跑完的运行**，正好是唯一需要它的那批；不删则目录无界增长，而"每个任务都留一份"带来的不是可追溯性，是没人看的噪音。
- **不安全的 taskID 宁可不记，也不"净化后照写"**：净化会把 `a/b` 与 `a_b` 映射到同一个文件，两次不同的运行写进同一份日志——读的人会以为看到的是完整的一次运行。**宁可不记，也不要记错。**
- **文件不存在不算错误**：日志正常结束就删，所以不存在是绝大多数任务的**预期**状态；把它变成错误，等于让每个调用点都得先绕开一次预期中的失败，而真正该被看见的读取错误反而淹没在同样的 `err` 里。
- **`DiscardRunLog` 必须在写盘成功之后**：反过来，写盘失败会把运行中唯一的凭据也一起丢掉。
- **恢复：沿用不是复用**。`Carried` 与 `Deduped` 必须分开——Deduped 是同一次运行内的去重（这一步跑过，结果被复用），Carried 是这一步**这次根本没跑**。回放要回答的第一个问题就是"这一步到底执行了没有"，而两种"没真跑"的原因完全不同：**一个是省调用，一个是省副作用**；印成一个词，读的人就无法判断这次有没有产生副作用。
- **预置必须早于所有 goroutine**：顺序错了，依赖沿用步骤的下游会去等一个永远不关的完成信号——不是"偶尔失败"，是死等，且只在特定并发交错下暴露。
- **沿用的步骤也要进运行日志**：漏掉它们，一次中途退出的恢复在日志里会看起来"少了前几步"，读的人分不清是沿用了还是丢了；而且终态记录与从日志重建的视图会给出不同的「沿用」计数。
- **缺一条历史结果就拒绝，不能"顺手跑一遍"**：那会把恢复悄悄变成重跑，而重跑有副作用——用户以为只是接着跑，实际上把前面做过的又做了一遍。拒绝时要给出出路（换起点或 `--rerun`）。
- **沿用下来的失败步骤照旧连累下游被跳过，那正是当时的前提，不是恢复失败**：不提醒，用户会以为 `--from` 坏了，然后改用 `--rerun` 把副作用又跑一遍——正好是恢复想避免的事。
- **沿用步数必须印出来**：不印，"这次成功 3 步"会被读成"这次跑了 3 步"，而实际上可能只有 1 步是这次跑的。
- **回放产物落 `replays/`，不进 `tasks/`**：`tasks/` 是质量统计（完成率、用户重试率、首次验收通过率）的**分母来源**，把回放混进去，指标就被复盘动作本身污染了——用户重放一次历史任务，统计里就多出一个"用户提交过的任务"。回放记录是**执行结果**不是任务判定（没有提示词分段、规则集与交付口径），所以渲染也刻意分开。
- **计数只有一份实现**：`countSteps` 的判据与执行器汇总**逐字一致**，最容易分叉的一项是「跑完了但业务上失败」（`Status=succeeded` 而 `Outcome=failed`）——按 Status 算会把它洗成成功。除单测外还有一条**跨实现对照**：真跑一次执行器，拿它的五项汇总与 `countSteps` 逐项对照。同理比较只有一份 `renderDiff`——两处各写一份，迟早会对同一个变化给出不同判断。
- **接线断言（第四次）**：回放记录是**跑完才写**的，所以运行日志的接线写在调用点的话单测照样全绿，而每次回放都不留任何运行中的凭据。因此这根线接在 `rerunExecutor`（组装执行器的地方），让"回放接上了运行日志"本身可被测试钉住。
- **测试**：新增 `internal/agent/runlog_test.go` 10 条、`internal/agent/executor_carried_test.go` 6 条（含**直接数工具调用次数**证明沿用不执行、**5 秒超时**暴露死等）、`cmd/gleam/replay_audit_test.go` 11 条、`cmd/gleam/replay_count_crosscheck_test.go` 1 条（跨实现对照）。
- **变异验证**：20 处全部会响（无一存活、无一因编译失败而"假捕获"），专门覆盖这一批的"静默失效"——不标注沿用、沿用数不进汇总、不放行下游（死等）、沿用步不进日志、沿用步又被真跑一遍、通道重复 close、日志写入变空操作、不安全名字被净化、缺文件当成错误、半行让整份失败、Discard 变空操作、"跑完但业务失败"按 Status 算、丢掉沿用计数、沿用标记不印、对比不印沿用行、提醒被删、回放落进 `tasks/`、同名记录随便挑一个、缺记录时顺手跑一遍、回放不接运行日志。变异脚本已收进 `scripts/mutation/`（**不再跑完即删**）。

- **冒烟脚本踩的三个环境坑**：① **断言顺序必须先正后反**——先证明"命令跑起来了、第三步真的执行了"，再证明"前两步没被重做"；反过来写，"文件没被创建"会在命令压根没跑起来时也成立，**用错误的理由通过比直接失败更坏**。② 传给 Windows 二进制的路径必须经 `cygpath -m` 转换，且任务记录里要写**绝对**路径——cygpath 对相对路径不补全，于是"绝对路径"其实是相对的，被工具再按工作区解析一次（路径拼两遍 `ws/ws/c.txt`），症状看起来像"文件不存在"，很容易被误判成权限问题。③ 本机的删除操作会经过一层安全删除策略，`rm -rf` / `rmdir` / `find -delete` 都可能被挂起等待确认，所以脚本**不清理临时目录**，改用系统临时目录由操作系统回收——每次 `mktemp` 都是新目录，重复运行天然干净。

### 任务绑定配置快照：让"当时用什么跑的"成为事实（P2-1）

- **问题**：事后留痕回答不了"是什么"。`RuleSetVersion` 只在产出时事后留痕、不绑定任务；一个跑五分钟的任务中途改了模型或档位，前半段和后半段用的就不是同一套配置——而结果里只有一个事后算出的规则指纹，**"是配置变了"和"模型发挥不稳"在数据里长得一模一样**。
- **取快照的唯一正确时机是任务启动时**：收尾时再取，记下的会是一个**从未完整生效过**的配置（后半段用的新值被当成了全程的值）。`RunGoal` 在进循环之前取一次，循环只负责把结果写出去。
- **只记影响行为的关键项，不记全量**：全量快照会把 API Key 明文写进 `tasks/<id>.json`；而且改一个无关字段也算"配置变了"，反而看不出真正影响结果的那几项。路径类字段（工作区、数据目录）同样不记——它们属于"这次在哪跑"，不属于"用什么跑"。
- **`Tiers` 必须深拷贝**：不拷贝则快照与活配置共享同一个 map，用户改一次档位就把**所有历史快照**一起改掉——而快照存在的全部意义就是不跟着变。
- **`ConfigSnapshot` 与 `RuleSet` 是同一类东西的两个半边**：规则集回答"提示词是哪一版"，快照回答"模型与阈值是哪一套"。缺任何一边，历史结果之间都不可比。
- **`replay --rerun` 用快照，不再用当前配置**：复现实验的前提是**只动一个变量**；拿当前配置重跑，比出来的差异分不清是"环境变了"还是"配置变了"。
- **回退必须保留，但必须被说出来**：本字段落地之前产出的任务文件里没有 `config_snapshot`，直接拒绝重跑会让所有历史任务失去重跑能力（那比"参数不精确"更差）。所以回退存在，且重跑前印一行来源——**"以为在复现、其实变量变了两个"是最坏的复盘姿势**。
- **复盘输出两处细节**：没有快照时如实说"无"并点明后果（不印，读的人会把"没记录"当成"没改过配置"）；**0 表示"不限"的预算不能印成 0**（"输出预算 0 字符"会被读成零预算，与真实语义正好相反）；档位要排序（map 遍历顺序随机，同一份快照每次印得不一样会被误读成"配置变了"）。

**测试与变异验证。** 新增 `internal/config/snapshot_test.go` 5 条、`internal/agent/snapshot_test.go` 2 条、`cmd/gleam/replay_test.go` 补 6 条。**15 处变异全部会响**：快照推迟到收尾再取、取了不写进结果、`Tiers` 不深拷贝、去掉 nil 守卫、快照里塞进 API Key、json tag 写成 `-`、漏拷 `DedupeCalls`、漏拷 `MaxSteps`、组装时无视快照、解析函数永远回退活配置、来源说明恒报"取自快照"、档位不排序、把"不限"印成 0、复盘不印快照行、没有快照时不说后果。其中两处遇环境错误，**自动重试后才捕获**。

**端到端冒烟（不是单测）。** `replay --rerun` 的调用点在 cobra 命令里，所以造两个任务文件实跑：带快照的得到 `参数取自任务启动时的快照（本次只动"环境"这一个变量）`；旧任务（无快照）得到 `参数回退当前配置（该任务没有快照）——差异里混着配置变化，不能全归给环境`。**两条路都要能跑，而且都要说清自己走的是哪一条。**

**接线断言。** 判据算对了不等于接上了：`resolveRerunParams` 写对、组装执行器时却传 `nil` 或活配置，单元测试照样全绿，而每一次重跑都会拿今天的配置去比昨天的结果。所以组装那一步抽成 `rerunExecutor`，让"用快照"这根线本身可被测试钉住——与独立验收者的 `VerifyLLM`、交付侧口径的成长记录接线是同一个坑的第三次。

### 交付侧一次性：首次验收通过率与返工轮数（P5）

- **问题**：成功率看不见"返工"。一个重做三轮才成的任务和一个一次做对的任务，在数据里完全一样：`status=success`，分数可能还更高（反思器看的是最终产物）。已有的 `StepResult.Retried` 是**步骤级**的（这一步重试了几次），回答不了"整个目标返工了几轮"——而后者才是成本与可信度的差别所在。
- **两个字段，两个不同的问题**：`GoalResult.FirstPass`（第一轮尝试就走完流程并通过完成判定，端到端**一次就合格**）与 `GoalResult.Reworks`（反思判未达标后**真正重新执行**的轮数，返工**花了多少轮**）。一个任务返工 5 轮与 5 个任务各返工 1 轮，累计轮数一样、首次通过率完全不同，所以两个都要。
- **"计划校验失败导致的重规划"不算返工，但会让 `FirstPass` 落成 false**：计划没过校验时**一步都没执行**，谈不上"重做"——计进返工会让这个指标随"计划写得好不好"漂移，而不是随交付质量漂移。但"首次尝试"里包含"计划第一次就可用"这件事，所以那次尝试仍不算走完。
- **循环内部的事实不让外面猜**：新增 `goalProgress`，由循环写（`attempts` / `reworks` / `firstRound`）、由 `RunGoal` 读并 `stamp` 进结果。"第几轮才成""返工了几次"从结果**反推不出来**——重试三次才成与一次做对，最后的 status/score 一模一样。
- **`stamp` 两条守卫**：① 只在进过循环时写（对话模式没有"轮"，无条件写会把对话管线给出的结论覆盖成零值）；② 要求最终状态是成功（完成判定通过之后 `applyAcceptanceVerdict` 仍可能校正成"部分完成"，那不是一次就合格）。
- **分母是这批最容易写错的地方**：`FirstPassRate` 与 `RetryRate` / `AbortRate` **不共用一个分母**——后两者按"完成 + 中断"，前者**只算记过这个口径的完成任务**（对话模式没有"产物"可核，历史条目也从没记过）。所以成长记录里单记一个 `Delivery` 布尔，而不是靠"`FirstPass` 是不是零值"去猜：零值既可能是"没通过"，也可能是"根本没这个口径"。**分母不可信的比率比没有比率更糟**——它会让人以为自己看到的是质量，其实看到的是记账方式。`ReworksTotal` 则**含中断任务中断前已发生的返工**：用户放弃之前烧掉的那几轮同样花了钱。
- **一处刻意不做**：工作模式规划屡败、回落直聊的任务留在分母里（`Delivery=true`、`FirstPass=false`）。它确实是一次失败的交付——把最差的从分母里摘出去，是在把比率改成好看的样子。
- **CLI 两处，都为"三种情形要能区分"**：`gleam doctor` 用户信号块加两行（沿用样本量门槛，交付口径的分母写在行内、不借上一句的"完成 + 中断"）；`gleam replay` 单任务复盘加一行，**一次通过 / 返工 N 轮 / 没走到验收三种情形都要印得出来**——只印一种，另两种就混进来看不见了，尤其不能把第三种印成"返工 0 轮（一次通过）"，那是在替一次没核对过的交付邀功。顺带把 doctor 那段抽成 `userSignalReport(growth.Stats) string`：段里有两个不同分母，而**分母写错在终端上看起来一模一样**，只有断言文本才能发现。

**测试与变异验证。** 新增 `internal/agent/delivery_test.go` 9 条、`internal/harness/growth/delivery_test.go` 3 条、`cmd/gleam` 下 doctor 3 条 + replay 1 条（口径见设计文档 §4.6.20）。**16 处变异全部会响**：不判第几轮、循环不报轮数、返工不计数、`stamp` 去掉范围守卫 / 去掉状态守卫、对话任务也标交付口径、结果算对了但不记下来（两个字段各一处）、分母算上所有完成任务、丢掉中断前的返工、不判分母为零、不卡样本量、分母为零也报、三种渲染各改坏一处。

**两处 CLI 是冒烟验证的，不是单测。** `doctor` 那段抽成函数之后分母可断言了，但"抽出来的结果有没有真的被打印"只有端到端跑一次才知道（调用点在 cobra 命令里，抽不动）：造 6 条完成记录 + 1 条中断，实跑得到 `首次验收通过率 50%（3/6，仅工作模式）`、`累计返工 4 轮（含中断前已发生的）`；`replay` 用三个任务文件分别得到"返工 2 轮（非一次通过）"/"返工 0 轮（一次通过）"/**不印**。

**接线断言是这批最该记住的一条。** 口径算对了不等于**记下来了**：`stamp` 正确、`growth.Stats` 汇总正确，但中间"写进成长记录"少接一根线，统计的分母就永远是空的——而所有单元测试照样全绿。所以必须端到端跑一遍、去读真正落盘的那条记录。这与 P4-2b 的 `VerifyLLM` 是同一个坑，**同一个坑第二次栽，说明"新写一个判定"和"把它接上线"在这套代码里始终是两件事**。

**变异脚本本身也补了一处。** SIGTERM 默认直接终止进程，`finally` **不会执行** → 源码留在变异态（P4-2b 就栽在这）。这次给脚本注册了 SIGTERM/SIGINT 处理器、转成异常走 `finally` 还原，并加了开跑前的**锚点预检**（命中数不为 1 就别开跑，免得跑到一半才发现锚点写错、前面白等）。

### 独立验收者：验收换档位、格式合法归代码（P4-2b）

- **问题**：P4-2a 把"自述"换成了"实测"，但那只解决一半——**干活的模型仍在给自己打分**。原先 `reflector := &Reflector{LLM: mainLLM}`，注释还明写着"规划、反思、对话都走这个客户端"，于是"独立验收"只体现在**独立调用 + 独立上下文**上：同一个模型干完活又给自己打分，它的盲区会同时出现在"干活"和"验收"两侧，自评偏差没有任何东西去抵消。
- **改法**：验收走一个**不同档位**的模型，默认点名 `reasoning`（`DefaultVerifyTier`）。判据只有一条，而且落在**模型 ID 不同**上、不是"档位名不同"——两个档位名指向同一个模型并不构成独立，照旧回退。抽出 `tierLLM(tier)`（按档位名取客户端），`TierLLM(role)` 成为它"先由角色解析出档位"的包装，免得两处各写一份回退与缓存。
- **换不成要如实回退，不许随便挑一个顶上**：刻意**不**退而求其次去挑 economy/coding 档或主模型——验收是判断活，拿一个没有理由信任的弱模型去判强模型的产出，只会得到一个"看起来独立"的橡皮图章，**比同源自评更难发现**。已知限制：`analyst` 这类角色自己就声明 `reasoning` 档，执行者与候选验收模型是同一个 → 换不成、走回退（内置 7 个角色里 5 个能换成）。这条限制写进代码注释与就绪诊断，不靠注释糊过去。
- **回退不是错误，但不能假装独立**：新增 `VerifyModel`（只算名字、**不建客户端**），就绪体检据此明说"独立验收生效"还是"与执行者同源"。**"独立性"因此是一个可核对的事实，而不是注释里的一句期望。**
- **格式合法**：确定性层原先只做"文件系统上就能确认的事"，补上唯一一处读内容的例外——`.json` 能不能解析。**只看"在、长度对"发现不了写进去的是一份坏掉的 JSON。** 取舍全在防假警报：只认扩展名（csv 不查，列数不齐也可能是合法数据）、只查覆盖写（追加写可能只是往尾部贴一段）、放宽一档（JSONL 常被写成 `.json`，逐行合法也算通过）、空内容不判、顺手容忍 BOM。
- **顺带两处清理**：一是 `mainLLM` 在接上 `VerifyLLM` 后已无人使用（`BuildPlanner` 内部自己解析档位），删掉并把注释改成"反思是例外"；二是 `applyAcceptanceVerdict` 里那句收尾文案从"代码实测没找到说好的产物"改成"代码实测对不上"——产物可能是**在**的，只是坏的，原话在格式失败时就不准了。

**成本与回滚要说实话。** `reflect` 默认每个 attempt 只跑一次（`ReflectEachStep=false`、`MaxReplans=2`），所以最多多出 3 次调用；把 `reasoning` 档指向贵模型时会实实在在花在验收上。**回滚方式就是删掉那一档**——档位是"可以挑"不是"必须挑"。另外这是**行为改动，不是可量化的提升**：仓库唯一的基线是 `baseline-select.json`，而 `select` 深度零模型调用、不经过反思器，所以这次改动动不到基线；要验证收益得在配了真实模型的环境里看返工次数与首次验收通过率。

**测试与变异验证。** 新增 `internal/agent/verify_test.go` 8 条，`artifact_test.go` 补 8 条（口径见设计文档 §4.6.19）。**11 处变异全部会响**。其中一条是**接线断言**：造两个假客户端，执行者那个的反思脚本故意给低分（`score=10/replan`）、验收那个给高分，断言最终成功、且**执行者客户端上一条 reflect 调用都没有**——这条断言本身也做了变异验证，把接线改回 `TierLLM` 它当场变红。

**一处"多余的守卫"是意外收获。** `jsonBroken` 里原先那句显式空内容守卫（`if len(bytes.TrimSpace(b)) == 0 { return false, "" }`）**不是一个守卫**：空文件与纯空白文件在逐行循环里本来就会被全部跳过，最终同样返回"没写坏"——把整轮验证跑在"没有它"的版本上，空文件用例照样绿（单独复跑也绿）。于是删掉这个分支，理由写进注释。**这与 P4-2a 那处"真阴性、但它守的是契约、所以补测试"正好相反：那一处该补，这一处该删——判据是"它守的东西还成不成立"。**

### 验收补「确定性层」：把产物核对从模型自述里拿回来（P4-2a）

- **问题**：反思器看到的每一步只有**截断 300 字的工具自述**，于是"说写了其实没写""写到别的路径去了""只写进去一半"它看不出来——它拿到的文字说成功，就只能按成功判。这是"干活的自己给自己打分"的另一种形态：不是分数自评，而是**事实自述**。
- **顺带发现同形状的第二个洞**：`statusOfExec` 只看步骤计数（全成功即判 `GoalSuccess`），而 `acceptanceSatisfied` 在**没有验收标准时直接返回 true**。两者叠加——一个没有验收标准的任务，只要每步都报成功，哪怕说好的文件根本不在，也会以「已完成」收尾。与 P0-1 同一个形状：**在事实层面错报，却没有任何一层去核对事实**。
- **做法**：新增 `internal/agent/artifact.go`，对"声称产出了文件"的步骤用代码做事后核对（`file.write` 存在且长度一致、`file.mkdir` 是目录、`file.move` 源消失且目标存在、`file.delete` 已不存在）。事实有两个去处：**喂给语义层**（作为 `## 产物核对（代码实测，不是步骤自述）` 段沉在 digest 末尾，附一句"自述成功不等于产物在"）与**当硬闸门**（`Evaluate` 一票否决 + 完成判定 `completionReached` 独立判 + `applyAcceptanceVerdict` 校正状态，**三处都堵**）。
- **三条取舍**：**按路径收敛、后写覆盖先写**（同一路径写两次、写完又删都是正常流程；逐条判会把"被覆盖"误报成"产物丢失"，而假警报会让这道闸很快被当成噪音关掉）；**长度校验最值钱**（路径对、文件在、只写进去一半，只看"存在"发现不了）；**宁可不判不可错判**（不认识的工具、拿不到路径的步骤一律跳过，未成功的步骤不进入核对）。
- **闸门不看有没有验收标准**：它判的是代码实测到的现实，与"承诺过什么"无关。也不能只靠压 verdict——完成判定第一句是 `verdict=="done" || score>=阈值`，压成 replan 后**分数达标的半边仍会放行**，所以必须独立判一次。
- **不改分数**：只改结论（verdict / 状态），不造数字——`Score` 的口径是"验收标准的通过比例"，塞一个合成条目进去会把口径弄脏。（这是 §4.6.5.1「放行与报满分是两件事」的镜像：那里是"不能静默给满分"，这里是"不能凭空给低分"。）
- **P4-2 的另一半未做**：资料建议"给核对者工具去实际读取产物"，这里改走"由代码读、把事实交过去"（零额外模型调用、不可幻觉、与 A3 一致）；仍欠的是**换用与执行者不同档位**的核对模型，以及"格式合法"这类更深的确定性判定。

**测试与变异验证。** 新增 `internal/agent/artifact_test.go` 15 条（口径见设计文档 §4.6.18）。**8 处变异全部会响**：去掉长度校验、同一路径保留首次期望、`failedArtifacts` 恒空、去掉 `wantAbsent` 校验、不跳过未成功步骤、`Evaluate` 去掉一票否决、`completionReached` 去掉产物那一句、`applyAcceptanceVerdict` 去掉产物分支。其中"不跳过未成功步骤"**最初没被抓住**，查下来是**真阴性**（执行器只在 `err == nil` 时记 `Output`，失败步骤根本没有路径可判），但它守的是一条契约，补了一条直接构造「失败 + 有输出」组合的测试把它从装饰变成契约。

**变异脚本新坑（这次很坑）**：脚本的恢复路径用了 `os.remove` 删快照，而本环境的 safe-delete 垫片会把它劫持成"移入回收站"，无桌面会话时抛 `SHFileOperationW 失败: 0x2`——崩在 `finally` 里，**整个验证带伤运行**。症状极具迷惑性：某几处变异莫名"未被捕获"，**两次运行结果还不一致**，很容易被误判成"守卫不承重"从而去改代码。修法：**恢复一律用内存里的原字节**（不读快照、不删任何文件），快照只在开头写一次、结尾用 shell 的 `for` 循环清理；写文件一律 `with + flush + fsync` 并**回读确认变异已落盘**。修好后连跑两次都是 8/8。判据：**结果不稳定就是脚本的问题，先别改测试。**

### e2e 测试脚手架的缓存策略：从"必然报红"改成"能跑"

- **问题**：`internal/e2e` 的 `buildBinary` 在 `GOCACHE` 未设置时会**每次新建一个临时缓存目录**，于是每次运行都是冷编译。本机冷编译超过它自己那个 2 分钟预算，`TestE2E_GoalCommand` 等 5 个用例全部以「构建超时: context deadline exceeded」失败——**只要没显式导出 `GOCACHE`，整套 e2e 就是必然报红**。一个永远报红的测试比没有测试更糟：它会训练人把 e2e 的红色当背景噪声，真回归也会一起被忽略。
- **修法**：`GOCACHE` 未设置时回退到 `go env GOCACHE`（标准缓存），不再自建临时目录；显式设置的 `GOCACHE` 仍然优先。缓存只影响构建产物、不影响测试结论，复用默认缓存与所有 Go 项目的默认行为一致。构建预算 2 分钟 → 5 分钟：它只是"编译卡死"的兜底，不是性能指标，预算太紧会把"机器慢"误报成"测试失败"；超时信息里补了预热缓存的办法。
- **验证（对照）**：修复前 `unset GOCACHE && go test ./...` → e2e 5 条全部构建超时、exit=1、耗时 2m39s；修复后同一条命令 → **26 个包全 ok、exit=0、耗时 32s**。
- **顺带清理**：本文件此前每批前插时都带了一次 H1 标题与 `## 日期`，累积出 3 个重复标题与 3 个同日分节，已合并为 1 个标题 + 1 个 `## 2026-09-21`。

### 代码格式统一：全仓通过 gofmt（顺带清掉 7 个文件头的 UTF-8 BOM）

- **问题**：收尾时跑 `gofmt -l internal/ pkg/ cmd/`，**28 个文件不合格**。差异是真实的缩进对齐漂移（不是行尾符问题），另有 7 个文件（`desktop/clipboard.go`、`clipboard_other.go`、`clipboard_windows.go`、`notify.go`、`screenshot.go`、`snippets.go`、`harness/growth/growth.go`）**文件头带 UTF-8 BOM**——BOM 正是它们被 gofmt 点名的原因。一个连 `gofmt -l` 都过不了的仓库，等于把标准格式检查这道最便宜的门禁关掉了。

### 对话自检的失败路径不再静默（补漏）

- **问题**：对话模式在核对**跑了但没跑成**时（辅助模型调用失败、输出读不出来）静默保留 `Score: 100`——"干活的自己报满分"正是这个功能要消灭的东西，却在自己的失败路径上复现了一遍。根因是"不值得核对"（开关关、闲聊）与"核对了但没成功"两种结局被压成了同一个 `ok=false`。
- **修法**：拆成三种结局 `chatCheckSkipped` / `chatCheckDone` / `chatCheckUnusable`，只有最后一种会发一条"对话自检未能完成，本次回答未经核对"的提示。**状态与分数保持原样**——这不是手软：前端把 `<40` 渲染成红色的"完成度 0/100"，把分数改成 0 等于往反方向说谎（回答可能很好，只是没核对过）。能做的只有"让没核对过这件事本身可见"。
- **为什么不像工作模式那样落"部分完成"**：差别不在"有没有放行"，而在**有没有先前的承诺**。工作模式的验收标准是规划器**动手前**定下的，核对不了就不该声称完成（§4.6.5 三道闸门因此把"判定缺失"判为不通过）；对话模式的标准是核对者**事后**提炼的，核对器一挂就等于标准从未存在——此时放行与"没有验收标准就放行"是同一条规则。**同一个 fail-open 动作，在有承诺的地方是漏洞，在没有承诺的地方是常识。**
- **顺带复核了 P0-1 的波及面**：工作模式（`Verdict:"replan"` 与 `Score:0` 在同一个门里只判一次，不会双重触发；终态由 `finalize` 首行的 `applyAcceptanceVerdict` 在写成长统计**之前**校正）、技能路径（`plan.Acceptance` 恒空）、对话模式（新分支不可达）三条路径全部干净。

**测试与变异验证。** 新增 2 条（`chatCheckUnusable` 必须提示且不改状态与分数、闲聊必须安静），改写 2 条（"没提炼出标准"归 skipped、"输出不可解析"归 unusable——原先两者只断言 `ok=false`，现在断言各自的结局）。**4 处变异全部会响**：去掉 `chatCheckUnusable` 分支、解析失败归成 skipped、调用失败归成 skipped、警告条件改成 skipped（对闲聊喊虚警）。还原后复跑全绿。

### 减法实验判定与配置陷阱：能力菜单保留、覆盖层钉死默认值

- **能力菜单实测判定为「保留」**：此前列在"明确不做"，理由只是"差异不可归因"（处理效应 4.83 落在噪声基线 3.00/5.67 之间）。补上 `gleam eval --repeat N` 之后，按当时定下的顺序做了**两轮独立对照**（唯一变量 `max_tool_schemas` 12 vs 0，16 条用例，`--depth plan --repeat 3`；`max_tokens` 抬到 16000 以消掉"JSON 被截断"这个已知混淆项）。结果：**可归因差异两轮都是 0 条**——在两臂都稳的范围内，工具集、步数、通过与否完全一致；通过率 16/16 对 16/16（第 2 轮全量掉了一条 `chat-only`：纯对话目标在全量 schema 下被误导去选工具，但 n=1 不足以当结论）；合并稳定性 5/16 对 5/16。成本侧则**有确定收益**：提示词 83,482 字 vs 109,246 字，**小 24%**，且两轮一模一样（算术而非统计）。结论与原先的假设相反——不是"拆掉也没事"，而是**拆掉纯亏**：拿一个确定的 24% 提示词收益，去换一个测不出来的质量改善。
- **顺带发现：可重复性指标自己也需要噪声基线**。第 1 轮菜单 69% vs 全量 50%（差 19pp）看着像"菜单更稳"，第 2 轮变成 38% vs 44%——**符号反了**，合并后完全相同。逐条看能看出原因：**用例自身的稳定性是稳定的**（`file-write` / `file-list` / `work-analyze-sales` / `code-add-test` 四格全抖，`schedule-weekday-report` / `schedule-list` / `web-fetch` 三格全稳），会变的只是"这次抖几条"，而 16×3 下这个计数有 ±2~3 条误差，足以把 3 条的差放大成 19pp 的"结论"。**要比较两个配置的稳定性，一轮 16×3 不够，至少要两轮独立测量看方向是否一致。**
- **一个更值得记住的事实**：`deepseek-v4.1-flash`（temperature 0.3）的逐次一致性只有 **31%~69%**——大多数评测用例单跑一次的结果接近掷硬币。**通过率必须配合可重复性一起读**，否则会把噪声当结论。这正是补 `--repeat N` 的意义。
- **配置覆盖层会把默认值钉死（坑）**：改 `DefaultMaxSteps` 12→32 后本机**没有生效**——`~/.gleam/settings.yaml` 里有一句 `agent: max_steps: 12`。`SaveOverlay` 是**全量快照**（不管用户有没有动过某个字段都写进去；MCP 空列表与 `tiers` 空表更是故意要写，用于覆盖 `config.yaml` / 表达"清空"），加载侧又是"覆盖层赢"，于是**一旦在设置页保存过，所有默认值就被钉死在那份文件里，之后改任何默认值对这台安装都不再生效**。没有改成"只写非默认字段"：那需要一张例外清单（`tiers` / `mcp` / `workspace` 的零值都带"清空/覆盖"语义，不能省），清单本身比这个坑更脆。改为把坑写进 `SaveOverlay` 的注释，并立一条操作纪律：**改默认值之后，顺手确认已有安装的 `settings.yaml` 有没有把旧值写进去。**
- **注释里的过时数字**：`config.go` 里能力菜单的注释写"当前内置 21 个"，`gleam tools` 实测是 **23** 个，已回填。

**实测数字（可复现）。** 两个数据目录只差 `agent.max_tool_schemas`（12 / 0），两边各跑 `gleam eval --depth plan --repeat 3 --json`，共两轮。完整口径与表格见设计文档 §4.6.17。

### P0/P1 批次：验收闸门补漏、评测可重复性、数据出网留痕

- **验收闸门在反思器故障时被整体绕过（P0-1，真 bug）**：串起来看是一条完整的假成功路径——反思器调用失败 → `heuristicReflection` 给 `done/85` → `acceptanceSatisfied` 因 `checks` 为空而放行 → 一个定义了 4 条验收标准的任务，在**一条都没被核对过**的情况下以「85 分 · 已完成」收尾。原先那句"判定缺失时放行"是有意写的（理由是不想让反思器偶发失败把任务卡死），但代价是整道闸失效。三处同时收口：`acceptanceSatisfied` 区分"没有验收标准"（放行）与"有标准却没判定"（**不通过**）；`heuristicReflection` 在有验收标准时不再给 `done`，改判 `replan` 并把分数给 **0**（本文件自己的规则是"有验收标准时分数一律由 checks 算"，给 85 既违背规则又恰好越过 `DoneThreshold`，等于留了第二条路）；`applyAcceptanceVerdict` 增加"有标准却没判定"分支，落「部分完成 · 验收未能核对」。"不要卡死"的诉求改由状态层满足，而不是靠放行。
- **评测补「可重复性」维度（P1-1）**：`gleam eval --repeat N`。这个缺口是上一批减法实验真实咬出来的——同一配置重跑 16 条用例，噪声基线 3.00/5.67 条工具集不同，而处理效应只有 4.83，**噪声比效应还大、结论不可归因**，而当时没有任何工具能事先看出这件事。指纹只收三个确定性字段（通过与否、步数、工具集合），工具集合**排序后比较**（顺序不算差异），**不收分数与耗时**（mock 下恒等、本来就会抖，收进来只会制造假不稳定）。**通过率仍取首次运行**，否则 `--repeat 1` 与 `--repeat 3` 不可比、历史基线全部失效。一致率用指针而不是 `float64`，好区分"没度量"与"度量了但一致率为 0"。不稳的用例会打印"重跑 N 遍得到几种结果、每种几次"，直接指出抖的是哪一部分。口径写死在输出里：**通过率回答"对不对"，可重复性回答"稳不稳"，两个数不能互相替代**。
- **审计补「数据出网」事件（P1-3）**：此前全仓检索 `egress|outbound` 的 24 处命中**全是 `regression` 误匹配**——"本地优先"这句话回答不了"什么数据出了本机"。现在模型调用与 `web.fetch` 每次发包都留一条（`gleam pending --audit --egress` 可只看这类）。**只记主机名与字节量，绝不记内容**：`Gate.RecordEgress` 把这条边界写在签名上（调用方手里根本没有正文可传），把请求正文写进 `audit.jsonl` 等于把风险从"网络"搬到"磁盘上的日志"。两条细节：GLM 客户端自走 HTTP，所以三条出网路径（非流式、流式、GLM `do()`）都要记账，否则对话模式是一条无痕出网路径；`web.fetch` 的留痕放在 SSRF 校验**之后**——被拦下的请求根本没出网，那是 `denied` 不是 `egress`，混在一起审计就会把"发给了谁"变成"想发给谁"。过滤时先把全部读回来再筛，避免稀疏的出网记录被别的留痕整个盖掉（查不出问题的审计比没有审计更危险）。
- **`MaxSteps` 12 → 32，并消除重复定义**：146 次观测里模型自然收敛到的最大步数是 10，原值 12 **从未真正触发过**，余量只有 2 步。同时把兜底值收敛到 `config.DefaultMaxSteps` 一处——原先 `config.go` 与 `planner.go` 各写死一个 12，改一处忘一处就成了两份边界。顺带确认：真正的硬约束往往不是它，宽泛目标下先撞上的是输出 token 预算。
- **文档口径对齐（P0-2）**：README 与设计文档把工作模式的"独立验收"限定为「独立调用 + 独立上下文（不看生成推理）」，并如实写出两条限制——**与执行者同档模型、只看截断的执行摘要、不重读产物**。所以这道闸能挡住"嘴上说 done"和"漏判"，挡不住"摘要看着对、产物其实错"；文件型目标的硬核对属于后续要补的确定性验收层，不该指望语言模型代劳。
- **明确不做：工具菜单暂不拆**：实测处理效应 4.83 落在噪声基线 3.00/5.67 **之间**，属"差异不可归因"而非"证明无差异"。用不可归因的证据去删一个用户可见的安全阀（设置页的 `max_tool_schemas`）不叫不臃肿；且内置工具已有 23 个、越过资料所述"约 20 个活跃工具表现下降"的门槛，删除面还牵到 web 设置页、成本看板的 `tool_pick` 归因与约 30 处测试。**正确顺序是先有可重复性指标，再用重复采样实测判定。**

**测试与变异验证。** 新增/改写 15 条测试：`acceptance_test.go` 3 条 + 1 条端到端回归（注入必定失败的反思器 LLM，断言终态不是 success、分数不是 85、说明含"未能核对"）、`planner_test.go` 1 条（兜底上限与 `config.DefaultMaxSteps` 同源）、`repeat_test.go` 5 条、`egress_test.go` 9 条（llm / web / safety 各 3）。**9 处变异全部会响**。全量测试绿，e2e 5 条单独跑通过。

**一条过程教训。** 变异脚本被强杀时 `finally` 不执行，会把已变异的源码留在工作区，而第二次运行只会报"锚点 count=0"，完全看不出是"上次没还原"。对策：变异前写 `<file>.mutbak` 快照、启动时若发现残留快照先恢复、结果**逐条打印**而不是攒到最后。另外本环境 Python 的 safe-delete 垫片会把 `os.remove` 劫持成"移入回收站"并在无桌面会话时失败——恢复路径上禁用删除，改用重命名。

### P4/P5 批次：三级超时、审批落盘、shell 边界与凭证隔离、全量审计

- **流式三级超时（P4-1）**：只设 http.Client 的总超时抓不住「每 60 秒吐一个字」——默认 60 秒下，一个每 30 秒吐 1 字的响应会被判成功，体验却是卡死。流式路径单独计时：首字节 30s（连接建了却不吐字）+ 块间 15s（吐着吐着停了），命中即中断、错误文本带「超时」自动归为可重试类。实现是共享的 scanStream（读取放 goroutine，主循环 select 计时器与行通道；每收一块重置计时，先停表再重置避免旧到期信号被误读）——原先三个 provider 各写一遍 bufio 循环，看门狗要做三遍且会走样。
- **等待审批状态落盘（P4-2，只做一半）**：进程若在等待审批期间退出（关窗口、升级重启），那条任务就没人知道它停在哪、要批什么。审批进行中写 DataDir/pending_approvals.json、有结果即摘除；`gleam pending` 列出、`--clear` 清理。不做完整断点续跑（桌面单机场景下收益未验证）。
- **shell 边界复用与凭证隔离（P5-1，只做两条）**：cwd 此前直接用用户参数，现在走与文件工具同一份实现（within/resolve 提升到 toolutil）——两条路径各写一份边界就会出现「文件工具挡住了、shell 绕过去了」的缝；未配置根目录时一律拒绝（失败朝安全方向失败）。子进程环境剔除 *_API_KEY/*_TOKEN/*_SECRET/PASSWORD/CREDENTIAL 等凭证变量——模型能读回命令输出，凭证进了子进程就等于进了上下文；保留其余全部变量（是"拿开凭证"，不是"清空环境"）。明确不做容器/seccomp（与本地优先定位冲突）。
- **全量审计落盘（P5-2）**：原先只有内存环 200 条（重启即失忆）且自动放行不记。现在 Record 追加写 DataDir/audit.jsonl（JSONL 追加而非重写——审计的价值在于"发生过什么"），自动放行的**副作用动作**也留痕（action=auto），只读不记（没有副作用，记下来只是噪音）；`gleam pending --audit` 重启后仍可复盘。
- **验证**：新增 22 条测试（流式看门狗 5、shell 边界与凭证 5、toolutil 边界语义 1、safety 审计与等待 8、executor 接线 3）；**7 处变异全部会响**（TTFB 看门狗失效、块间看门狗失效、cwd 校验被绕过、凭证不再剔除、审计不落盘、等待记录不清除、自动放行不留痕）；全量 26 包绿 + e2e 5 条通过；评测 16/16 通过，提示词 83482 字符（+14 = shell.exec 的 cwd 说明变长，预期）。

### P2/P3 批次：钉住区、记忆卫生、评测分层、badcase 回流、重试率/中断率

- **压缩钉住区（P2-1）**：滚动摘要会被截断覆盖，用户早期定下的约束（"以后都用中文标题"）可能悄悄消失。`Manager` 钉住区：压缩不动、注入排易变段最前、按加入顺序渲染**绝不重排**（重排同时打碎缓存前缀与约束顺序）。来源两条：`Pin()` 显式钉 + 用户消息约束词启发式（记住/约定/以后/必须…）——多钉一条只多 200 字，漏钉的代价是约束被磨掉。摘要注入带「累计省略 N 轮 / 约 M 字」：不说清丢了多少，读者分不清全貌与残余。P2-2 按清单判定只做一半：按轮数触发是可接受的近似，"阶段边界固化"对应任务收尾的 Compress（已存在）。
- **记忆去重 / 软删 / 阈值（P2-3）**：写入前余弦判重（≥0.92 更新原条目而非新增——同一目标跑 10 次不再产生 10 条互相挤占的记录）；`Item` 加 `Deleted`/`Source`，`SoftDelete` 只打标记、检索一律跳过（误删可挽回）；检索统一过滤 0.15 之下的长尾噪音。四类冲突完整版按清单判定暂不做。新字段全 `omitempty`，旧记忆文件零迁移可读。
- **memory.delete 工具（P2-4）**：模型此前能写能查不能删。新增按 id 软删工具，权限 `PermissionUserApproved`——删除用户数据不能让模型静默决定；存储能力走可选接口断言，不破坏只实现读写查的适配器。
- **评测分层与保留池（P3-2）**：`Case` 加 `Layer`，16 条内置用例打标（10 smoke / 3 regression / 3 holdout）；`gleam eval --layer smoke` 跑零模型调用的确定性冒烟层。**保留池**照跑计入聚合但不显示单条结果——被盯着调的样本会过拟合，没被盯着的样本绿了才算泛化。
- **badcase 回流（P3-3）**：`gleam eval --emit-case <taskID>` 把失败任务转用例草稿：goal、实际工具、trace 填好，期望留占位人工补。note 强制先回答站点 H4 的第一问——「换更强模型会不会消失？」会消失是研究问题不进回归集。

### P1 观测与口径：归因分布、分段计量、Trace 重放、attempt 明细、指标分母

- **问题一（只有失败率，没有归因）**：`StepResult.Error` 是自由文本，参数错、权限不足、超时、上游故障混在一个失败率里——失败率回答"坏了多少"，没人回答"该先修哪层"。新增 `ErrorKind` 八类：结构已知的错误在落点直接定类（审批拒绝=permission、引用替换失败=param、超时=timeout），自由文本走关键词启发式，归不了类的如实记 unknown。`GoalResult.FailureBreakdown` 随产出携带，`gleam goal` 失败时打归因行——**一条用例绿不代表过程干净**，被重规划救回来的失败也留在分布里。
- **问题二（上下文膨胀无从定位）**：只有提示词总字符数，没有分段。`buildSystemPromptMeasured` 按四成分计量（指令/能力/知识/状态），随产出落盘，输出与原版逐字节一致（有测试守着）。体检第 9 项加满载状态占比实测，判据双重：**占比 > 60% 且总量 > 20000 字节**——只看占比会在小注册表上误报；注入上限抽成与提示词组装共用的常量，上限被调大时占比检测自动跟着走。
- **问题三（复现写了两年没实现）**：`ExecutedPlan` 被赋值但无任何消费者。现在随 `tasks/<id>.json` 落盘（`gleam goal` CLI 也归档了，原先只有 serve 落盘）；trace_id 由"目标+模式+角色+模型"派生（刻意不含时间戳——同输入同模型自动聚类，失败聚类不需要额外索引）；新增 **`gleam replay <taskID>`**：默认只读回放，`--rerun` 原计划真实重跑并输出状态/步数/重试/耗时四项对比与逐步差异——重跑会真实调用工具，必须显式指定。
- **问题四（侥幸做成不可见）**："一次就对"与"重试三次才对"在通过率里长得一样。`StepResult.Attempt` + `Retried`，`GoalResult.RetryOK()` 汇总"重试后才成功"的步骤数，eval 报告与 goal CLI 都带这一行——后者是隐患位置。
- **问题五（分母陷阱 + 激励硬猜）**：评测只有全样本分母，没有"不可解"档。`Case.Unsolvable` 只在 full 深度生效，判据刻意宽松：状态不是 success 即算识别（"怎么拒绝"可以多样，"硬猜成功"只有一种形态）；识别成功计入 Handled（**不进 Passed**——混进通过率等于激励硬猜），识别失败计入 Failed；`Report.Attempted` = Total - Unsolvable，`gleam eval` 报出口径行与不可解处理率。本条同时吃掉 MiMo 文章遗留的 P2 指标口径项。

### P0 一致性缺口 5 项：三态结果、注入防护、桌面权限、重规划反馈、SSRF

- **问题一（数据源头）**：`err == nil` 不等于"做成了"。`shell.exec` 非零退出、`file.search` 超时都把原因塞进 payload 后返回 nil，执行器判成功、反思器看不见、整个任务被判 success——完成率失真的根因在数据源头，不在统计口径。
- **三态与状态机正交**：新增业务层 `StepOutcome`（ok / empty / failed），与执行层 `StepStatus` 分开。工具可选实现 `OutcomeReporter`（`Outcome(args, out)`），执行器在 err==nil 后再问一次"到底做成了没有"；没实现的工具一律按 ok 计，纯增量不破坏既有工具。空结果单独计数（不是错误，但必须与"有结果"区分，否则模型会空转重试）；note 抬到 `StepResult.Error`，否则原因只留在 payload 里，反思器与用户都看不见。
- **去重缓存连结果性质一起存**：`cachedCall{out, outcome, note}` 三字段一起存、一起还原——"空"恰恰是模型最容易反复重试的一态，丢语义的代价最大。
- **问题二（注入最省力的出口）**：工具返回的内容（文件正文、网页、命令输出、记忆、引用里的文件名）是数据不是指令。这条约定对所有模式成立，所以放规划器契约段稳定规则 `safety.untrusted`（208 字节）而不是在工具说明里各处复制——说明只在使用对应工具时出现，而注入可以来自任何工具的返回；放契约段还自动进规则集指纹与缓存前缀，改它是一次可被记录、可被回归的改动。
- **问题三（权限粒度）**：`Permission()` 不接受参数，一个混装两种副作用等级的工具声明哪一种都是错的。剪贴板拆成 `desktop.clipboard.read`（readonly，自动放行）与 `desktop.clipboard.write`（user_approved，过审批闸门）；`desktop.screenshot` 从只读改为需审批（截屏会把 PNG 落到磁盘），并实现 `PathAware` 把落盘路径交给门控，未指定路径时返回 nil 由门控要求人工确认而不是默认放行。
- **问题四（重规划盲飞）**：重规划 feedback 此前只有"完成度 X/100。问题：……"，规划器拿不到上次哪一步失败、为什么失败，只能原样重来。现在附上 `buildStepDigest` 的精简步骤摘要（工具/状态/错误前 200 字，刻意不贴输出正文），并明确指示"针对它们改，不要原样重来"。
- **问题五（SSRF）**：`web.fetch` 是自动放行的只读工具，也是提示词注入最省力的出口。默认拒绝本机/内网地址：DNS 解析后逐 IP 判定（loopback / private / link-local / multicast / unspecified 全拦），覆盖 169.254.169.254 云元数据端点；**重定向逐跳校验**（`CheckRedirect` 限 5 跳、每跳重新过 guardURL）——只挡入口不挡跳转等于没挡。`safety.allow_private_web` 显式放宽而非一刀切："读本机 dev server / 内网 wiki"是本地优先桌面 Agent 的正常需求，默认值 false。
- **测试**：新增 14 条（`internal/agent/outcome_test.go` 6 条，含重规划反馈接线断言——读第二次 plan 的 System 确认步骤结果真的进了 feedback；`desktop/permission_test.go` 3 条，含闸门端到端；`web_test.go` 3 条；`shell_test.go` 1 条；`rules_test.go` 1 条）。**9 处变异全部会响**（计数逻辑、去重缓存、反思器摘要、规则正文、两个权限声明、重规划接线、SSRF 拦截、shell Outcome），0 漏报。回归基线已重新固定（`rule_set: 860d8397bf`），16 条评测用例全绿；提示词合计净减 504 字符（规则段 +80，工具段因剪贴板拆分改变关键词选中的工具组合而 -584），属预期。

### 新增规则集身份：记录这次产出用了哪版提示词

- **问题**：一次产出的行为由代码 / 模型 / 规则表三者共同决定。代码有提交记录，模型有名字与用量记录，规则表此前什么都没有——排查回归时最常见的误判是"代码改坏了"，真相却可能是"规则改了一个字"。规则越资产化、改起来越容易，归因就越重要。
- **版本指纹从内容派生，不手写版本号**：手写版本号会忘改，而"这次用的是哪版"只在内容真变了时才有意义。`RuleSetVersion()` 取 ID / 槽位 / 标题 / 条目 / 适用范围 / 渲染顺序算短哈希（10 位十六进制）。内容不变则指纹不变，前后两次产出可比；少算任何一处，都会造出"规则改了、指纹没变"的假象。
- **指纹与生效规则 ID 互补**：加一条只对 code 模式生效的规则——work 模式的 ID 列表一字不变、但指纹变（表的内容动了）；改一句措辞——ID 不变、指纹也变。指纹回答"是不是同一份"，ID 列表回答"用了哪几条"，缺一不可。
- **已知边界：ID 列表区分不了变体**：`code.verify` 的软化版与兜底版共用同一个 ID，所以"用了 code.verify"不说明用了哪一版措辞——措辞层面的归因靠指纹。这条边界是变异测试逼出来的：把 `ActiveRuleIDs` 改成忽略档位，全部测试仍然绿（两个变体的 ID 相同）。测试绿不等于行为被守住了，得先问"它到底看不看得见"；现在写成显式断言钉住，将来谁想靠 ID 列表区分变体措辞会先红。
- **四个落点**：产出结果 `GoalResult.RuleSet` / `Rules`（对话模式**留空**——它直连模型、不经规划，一条规则都没用上，记成"用了契约段三条"是撒谎，会让翻日志的人往错方向排查）；成长日志 `Entry.RuleSet`（落盘、可跨进程回查：换规则之后要能回答"这批历史任务是哪一版跑出来的"，否则历史平均分与成功率只是不可比的混合体）；评测报告 `Report.RuleSet` 进基线、`Diff.RuleSetFrom/To` 报变化；`gleam rules` 离线回查。
- **规则集变化只报，不卡门禁**：改规则是正常动作，因为它让门禁变红只会逼人把 `--strict` 摘掉，门禁整体失效——那个代价比漏报大得多。但回归报告里必须看得见：**有回归时第一条该怀疑的是规则改了，不是代码改坏了。**
- **新增 `gleam rules` 命令**：默认列全表（落点 / 条目数 / 字符数 / 适用范围 / 版本指纹），带 `--task-mode` / `--tier` / `--role` 时列该场景**实际生效**与**被挡掉**的规则 ID——"未生效"那一栏是这个命令最有用的部分，它回答"为什么这条没进提示词"（答案通常是被 Scope 挡了，看代码不容易一眼看出）。`--json` 结构化输出。命令**刻意不装配运行时**：规则表是编译期常量，读它不该要求配置、模型、数据目录都就位——排障时往往正是这些坏了才要回头查规则。用 `--task-mode` 而不是 `--mode`：后者在 `gleam goal` 里是执行模式（auto / plan_first / interactive），同名不同义最容易在复制命令行时踩雷。
- **测试**：`internal/agent` 新增 9 条、`internal/eval` 3 条、`internal/harness/growth` 2 条、`cmd/gleam` 4 条。最关键是**记录与渲染的双向一致性**：记在生效列表里的，正文必须出现在提示词里；没记进去的（含同一 ID 未被选中的变体），正文必须不出现——一份会撒谎的规则集记录比没有更糟。**11 个变异全部会响。**

### 新增规则资产化与按档位条件化：让提示词减法可操作

- **规则进表**：稳定段规则从散落的字符串常量搬进 `internal/agent/rules.go`。每条规则有 ID、落点（contract / code / schedule）与适用范围（任务模式 / 模型档位 / 角色）。一共几条、各自何时生效，一处看得全；"减法"从"改代码"变成"改 Scope"。
- **范围只能落在稳定维度上**：规则开关一旦挂到"本次目标"这类逐任务变化的条件上，稳定段就不再稳定、前缀缓存全碎。这条由签名兜住——渲染函数拿不到目标，想按目标开关也开关不了。
- **同一 ID 可注册多个变体，先匹配到的生效**（变体在前、兜底在后）。这就是条件化：同一件事弱模型看一版、强模型看另一版，调用方不必知道任何 if。
- **按档位条件化的第一处落点**：编程模式第 3 条「涉及代码修改后必须安排验证步骤」。档位未配置、或档位是 economy（内置注释写明"低难度、大批量"）时保留原文；档位是 coding / office / reasoning 时换成「代码改动后运行一次验证并检查输出即可；同一条命令不要反复重跑，也不要为同一件事重复验证」。
- **判据是"用户有没有为这一档单独配模型"，不是从档位名猜能力强弱**：档位名描述的是用途（编码强 / 办公写作强 / 推理强），不是能力。所以规划器拿到的是「实际生效档位」而不是角色「声明」的档位——声明只说明这个场景建议用哪一档，没配时角色照样跑在主模型上，拿声明档位切规则会切出"跑着主模型、却按强模型的口径删规则"的错配。
- **变体没有把验证删掉**，只是去掉了"反复"的推力：Gleam 里没有别的机制保证代码改完会被验证，这条底线不能丢。有测试守着"任何档位下第 3 条都必须提到验证"。
- **资产化的第一要求是不改一个字**：重构前后五个 (角色, 模式) 组合的系统提示词**逐字节一致**（21356 字节），`gleam eval` 的提示词合计 82964 字符不变。这一步当场抓出一个真 bug——`code.verify` 的兜底版只写了档位范围、漏了模式范围，导致工作模式的提示词里凭空多出一条编程准则，而规则表看起来毫无问题。
- **`gleam eval` 新增 `--tier`**：模拟生效档位，只改提示词构建、不切换模型客户端。存在的理由是档位条件化要"用户配了档位"才生效，评测默认跑不到那条路径。量测结果：`--tier coding` 提示词合计 82987，未模拟 82964，**差 23 字符**。它同样改变提示词，所以跨档位对比被直接拦下（与跨深度同款），而不是把措辞差异报成一片回归。
- **效果要说实话**：这是**行为改动，不是体积改动**，体积基本持平。收益是"少推着强模型反复验证"，属于行为，`select` 深度量不到（它只跑工具筛选，与措辞无关）；要验证得在配了真实模型的环境里跑 `--depth plan`，看计划里有没有出现重复的验证步骤。在拿到那个证据之前，它是一个**有明确判据、可一行回滚（把 `Scope.Tiers` 清空）的假设**，不是已证实的优化。
- **测试**：`internal/agent` 新增 12 条（规则表自身合法、范围里的名字必须是已知维度取值以防拼错静默失效、变体必须由窄到宽排列、渲染确定性、编程准则不得漏进工作模式、定时段始终生效、稳定段规则体积上限、档位条件化的行为契约、验证底线不消失、`EffectiveTier` 四种回退与 `TierLLM` 一一对应、mock 下不上报档位、规则范围不得依赖目标），`internal/eval` 新增 2 条。六个变异全部会响：兜底版去掉模式限定、变体与兜底互换顺序、economy 也算能力档、档位名拼错、生效档位退回声明档位、删掉验收标准规则。

### 修掉本地打分器根因：路由只认描述开头一段，英文词按整词匹配

- **背景**：`gleam eval` 第一次跑就抓出四处误命中，同一个根因——
  `scoreToolNames` 把 `名称 + 完整描述` 一起打分，于是**描述里给模型看的举例与使用说明
  也成了路由信号**：

  | 描述里的文字 | 撞上的目标 | 机制 |
  | :-- | :-- | :-- |
  | `不要自己拼 cron` | 你好，简单介绍一下你自己 | 「自己」这个二元组 |
  | `goal 是到点真正要执行的事` | 给 utils.go 里的 parseDate 补充单元测试 | 英文词 `go` 作为**子串**命中 `goal` |
  | 示例「每日下载目录整理」 | 把上季度销售数据整理成表格并汇总 | 「整理」这个二元组 |
  | `（用户偏好、项目背景等）` | 检索我之前关于部署的偏好 | 与 `memory.search` 的「检索」同为 1 分平手，平手按工具名排序 → 保存工具排到前面 |

- **改法一：路由文本只取描述前 100 字**（`routingTextLimit`）。
  工具描述里混着两类文字：讲"这是什么、什么时候用"的，和讲"参数怎么填、注意什么"的。
  后者是写给**已经选中该工具**的模型看的，不是路由信号。
  100 这个数的依据：要容下"什么时候用"那一句（`schedule.create` 的
  「当用户说“每天/每周/每月/工作日/周末/每隔多久/到点提醒我…」在第 89 字结束），
  又要排除紧随其后的参数说明与用法提醒（第 120 字起）。
  **描述该写多长就写多长，路由只认前一段。**

- **改法二：英文/数字按整词匹配，且至少 3 个字符**（`minAlnumTerm`）。
  子串匹配会让 `go` 命中 `goal`；而 `go`/`in`/`is`/`id` 这类两字母词到处都是，
  当检索词只会制造噪音。中文仍是二元组子串匹配（没有分词器）。

- **改法三：去掉 `memory.save` 描述里与 schema 重复的内容举例**。
  原描述「把重要信息存入长期记忆（用户偏好、项目背景等），跨会话可用」，
  括号里的内容举例与它 schema 里 `tags` 的示例（`["偏好"]`）重复；
  改成「记住重要信息：写入长期记忆，跨会话可用」——描述只讲"是什么"，
  举例留给 schema（与提示词减法同一原则）。

- **收益不只是"少误命中"**：干净的路由顺带让提示词变短了——
  16 条评测用例的系统提示词合计从 **85848 → 82964** 字符（-3.4%）。
  归因是**逐项回退实测**出来的（把改动逐个撤掉、看数字怎么动）：
  路由文本截断 **-1970**、英文整词匹配与最小词长 **-685**、`memory.save` 描述去重 **-229**，
  三项合计正好 2884。大头来自 `schedule.create`：它的 schema 最大（6 个参数），
  以前被误判相关、挤进了十来条无关目标的菜单。**误路由不只是"可能做错事"，
  它还在挤占真正相关工具的 schema 名额。**

- **结果**：`gleam eval` 从 12 通过 / 0 未过 / **4 已知问题** → **16 通过 / 0 未过**，
  四条 `known_issue` 标记全部摘掉（评测会把"标着已知问题却通过了"的用例
  单列成「已修复」提醒摘标记，机制按设计工作）。

- **新增 6 条单测钉住口径**（用假工具，与具体描述解耦）：
  路由忽略描述尾部的用法提醒（正反对照，避免"永远选不到"式的假绿）、
  英文按整词匹配（`goal` 不命中 `goals`）、两字母词不进检索词表、
  截断边界（超限要截且带省略号、不超限不画蛇添足）、
  **相关集 ≠ 菜单**（`reply` 在菜单里但不参与打分）、名称命中权重高于描述命中。
  **5 条变异验证全部会响**：路由文本退回整段描述 / 英文退回子串匹配 /
  最小长度退回 2 / `RelevantTools` 实现成 `SelectTools` / 去掉名称加权——
  各自触发对应守卫判红，还原后 `internal/agent` 全绿。

- **文档**：设计文档 §4.6.3 补「兜底打分器的两条口径」、§4.6.9 补修复结论。
### 新增回归评测 `gleam eval`：给提示词改动装一道闸

- **为什么现在做**：上一刀减法（定时段 734 → 207 字节）靠的是"核对后发现与工具描述重复"
  这个人工判断。但**稳定段被服务端前缀缓存折扣过，减法的收益本来就不在省钱，而在减少
  注意力稀释与指令冲突——这件事没法用"省了多少字节"论证，只能靠评测回答"删了会不会变差"。**
  没有评测就继续删规则，是赌博不是工程。

- **不依赖模型裁判**：绝大多数要守的是结构性契约（工具路由、步数、有没有给验收标准），
  这些都能确定性断言。让模型来打分会让评测本身不可复现，也就失去了"回归"的意义。

- **三个深度**：`select`（默认，只跑工具筛选，本地关键词打分，零模型调用、确定性、可离线进 CI）、
  `plan`（跑到计划）、`full`（完整目标，会真的动工具——除非显式指定 `--workspace`/`--data-dir`，
  否则关进临时目录并在结束后删掉）。

- **门禁**：`--save` 存基线、`--baseline` 报回归、`--strict` 有回归时非零退出。
  仓库里带了 `internal/eval/baseline-select.json`，开箱即可当门禁：
  `gleam eval --baseline internal/eval/baseline-select.json --strict`。

- **走了一段弯路，值得记下来**：第一版断言写的是"工具在不在菜单里"，结果 16 条里 9 条红。
  查下来是口径错了——`selectTools` 末尾有一条**按注册顺序补齐**的兜底，菜单永远被填满 12 个，
  于是"在菜单里"既可能因为它相关，也可能只因为它注册得早。**把工具说明改到丢光关键词，
  它仍可能被兜底塞回菜单，评测却全绿。** 改成断言「本地打分相关集的前 N 名」后才有意义，
  并区分"排到窗口外"（排序问题）与"完全没命中"（描述没写清楚）。

- **抓出四件真问题，同一个根因**：`scoreToolNames` 把 `名称 + 完整描述` 一起打分，
  于是**描述里给模型看的举例与使用说明也成了路由信号**——
  - `schedule.create` 描述里的「不要自己拼 cron」→「自己」命中了闲聊目标「你好，简单介绍一下你自己」；
  - 同段的 `goal 是到点真正要执行的事` → 英文词 `go` 作为**子串**命中了 `goal`，
    于是「给 utils.go 里的 parseDate 函数补充单元测试」也把它排到第 1；
  - 示例「每日下载目录整理」→「整理」命中了「把上季度销售数据整理成表格并汇总」；
  - `memory.save` 的「（用户偏好、项目背景等）」与 `memory.search` 的「检索」**同为 1 分平手**，
    而平手按工具名排序，于是保存工具排到了检索工具前面。

  后两条的举例文字**正是上一刀减法搬进工具描述的**——减法本身没让路由变差，
  但它顺手在兜底打分器里留下了副作用，而这种副作用读代码、读提示词都发现不了。

- **已知问题机制**：根因已查清，修法（打分只取"身份行"而非整段手册；英文词按词边界而非子串匹配）
  会改变运行期菜单构成，属于独立改动。因此四条用例先标 `known_issue`：照常跑、照常打印失败详情，
  但不参与门禁；哪天通过了会以「已修复」出现，提醒摘掉标记。**比删掉用例诚实——删掉会让问题悄悄回来。**

- **16 条单元测试 + 变异验证**：深度门控（select 不判计划类断言，否则评测变噪音）、
  前 N 名窗口、"排到窗口外"与"没命中"可区分、窗口只对 select 生效、
  `Validate` 拒绝"没有任何期望的用例"（那种用例永远会通过，是评测最容易被架空的地方）、
  内置用例集合法且每条都有说明、基线往返、回归/修好/移除/跨深度拒绝/已知问题不参与回归、
  归集规则。四个变异（摘掉窗口、摘掉深度门控、摘掉"没有期望"校验、`Compare` 不跳过已知问题）
  各自触发对应守卫判红，还原后全绿。
  另做一次端到端变异：把 `schedule.create` 描述改到丢光定时关键词后重建，
  `--baseline --strict` 退出码 0 → 1，精确报出两条定时回归，还原后字节一致。

- **文档**：设计文档新增 §4.6.9；README 特性表、目录树、快速开始同步。
### 提示词减法第一刀：定时段 734 → 207 字节

- **背景**：规划器的 `## 定时/周期任务` 段位于**稳定段**，每轮规划都要带上，
  实测 734 字节（占整个提示词 14%）。但核对后发现它**大部分与 `schedule.create`
  自己的 description / schema 重复**——同样的 5 个 `when` 示例在那两处各写了一遍，
  `required: [name, goal]` 也早就声明过。

- **改法**：稳定段只留「什么时候该用」与「别只答应不做」两句（734 → **207 字节**，省 72%）；
  参数写法、时间示例、创建后如何确认，全部交给工具自己的说明（选中该工具时才加载）。
  这就是「目录在前、细节按需」——Gleam 对工具 schema 早就这么做了，这次把同一原则用到规则文本上。

- **不可替代的那一句**：「不要只在回复里答应」必须留在提示词里。
  工具描述能说清"这工具干什么"，说不出"别只口头答应"。

- **效果**：analyst/work 5412 → **4885** 字节；coder/code 5760 → **5233**；general/work 5041 → **4514**。

- **新增 4 条守卫，并做变异验证确认真会响**（故意删掉「不要只在回复里答应」→ 3 条同时红；

  - `TestScheduleSectionIsCompact`：上限 300 字节，超了就是有人把细节写回了稳定段；
  - `TestScheduleGuidanceNotLost`：断言「提示词段 + 工具描述 + 工具 schema」的**并集**
    仍覆盖全部关键信息——信息只能搬家，不能丢；
  - `TestScheduleDetailStaysOutOfMenu`：工具描述的**头 60 字会经能力菜单进入稳定段**
    （`firstLine` → `Shorten(s,60)`，注意结果是 61 字），细节必须落在 60 字之后；
  - `TestScheduleSectionStaysInStablePrefix`：压缩不能把它挤出公共前缀。

- **回归**：28 个包 + e2e 全绿（e2e 单独跑、热 GOCACHE，18s）。

     让断言只测「顺序契约」本身，并补上「Edge 全部排在 Chrome 之前」这条真正的契约。
  2. `TestExecutor_SkipsRepeatedFailedCall`：s1 与 s2 之间没有依赖，
     执行器并发起跑（MaxConcurrency 为 0 时取默认 8），谁先抢到 single-flight 由调度决定。
     原先断言"被去重的一定是 s2"，只在 s1 抢到时成立，机器一忙就假红。
     改成顺序无关断言：两次完全相同的调用，**恰好一次真执行、一次去重跳过**。
     连跑 20 次验证稳定。

- **回归**：28 个包（不含 e2e）+ e2e 5 个用例全绿；
  全量并行时 `internal/agent` / `internal/server` 会因资源竞争出现时间敏感型假失败，
  分批或单独跑即稳定通过。

### 就绪体检：把「自建九坑」做成可执行自检

来源：同一篇分享的结论——"几个坑叠在一起，结果就是 demo 做了很多，稳定进入生产的 Agent 很少"。
九个坑本身好懂，但静态清单看一遍就忘、没法随版本回归、也没法在自己这套系统上验证踩没踩。
所以不做第二份清单，改成**一次可执行体检**：每项都从真实运行状态取证据，给三档结论 + 补齐建议。

- **九项与证据来源**
  - Runtime 重复建设 ← 工具注册表 / 子系统装配 / 工具 schema 完整度（裸工具会让模型猜参数）
  - 只会聊不会交付 ← 工具权限分布 / 验收门禁 / 结构化结果
  - 模型与能力锁定 ← 厂商目录 / 协议集合 / llm.tiers 档位表
  - 权限与审计割裂 ← 门控覆盖数 / 门面视图条数 / 审计留痕 / **审批通道**
  - 最佳实践不可复制 ← 场景模板五要素完整度 / 技能数与复用次数 / 可安装生态
  - 体验与业务脱节 ← 角色数 / 工作区 / 微光空间 / 历史会话
  - 缓存不可控 ← **实测**提示词公共前缀 + 用量归集里的缓存命中
  - 缺少健康迭代架构 ← 成长日志（任务数 / 平均分 / 连续活跃 / 等级）
  - 可扩展架构与压缩记忆 ← 记忆条数 / 短期窗口 / 压缩开关与节省量 / 扩展点计数

- **第 7 项必须实测**：布局对不对光看代码看不出来，得真构建两份提示词比一比。
  样本刻意同时变**目标**和**工作目录**——只变目标的话，若有人把工作目录挪到提示词前部，
  两份样本工作目录相同、公共前缀照样穿过去，检查就漏了。

- **修正过一个错判**：最初只看「公共前缀占比」，真实环境（21 个内置工具）下稳定段 2448 字符、
  布局完全正确，却因按目标筛出的 schema 尾巴长、占比只有 46% 被判「待改进」。
  占比低不等于布局坏。改成三级判定，顺序有意为之：
  1) 布局对不对（稳定段标志小节是否全落在公共前缀内；不对 = 不合格，这才是"不可控"的根因）
  2) 稳定段够不够大（达到 CacheFriendlyMinChars；不够 = 待改进）
  3) 占比高不高（达到 25%；偏低 = 待改进）
  抽成纯函数 `cacheStatus(layoutOK, stable, ratio)` 并单独测优先级，把这条判断固定下来。

- **三条设计约束**：只读（不改配置 / 不发模型请求 / 不写文件，有超时保护断言）；
  无数据不装懂（没历史数据就说"暂无法评估"，缓存字段没返回就说"未报告"，不伪造绿勾，也不编 0% 命中率）；
  结论指向动作（每项非通过都带 fix，CLI 末尾单独收口成"待处理"）。

- **三个入口同一个实现**：`Agent.Readiness()` ← 界面「就绪体检」/ `gleam doctor [--json]` / `GET /api/readiness`
  - CLI 版最初硬传 `NopNotifier`，第 4 项永远报"未接入审批通道"——体检结论必须反映真实运行环境，
    改成与控制台 `gleam goal` 一致的真实审批通道，并支持 `--config/--workspace/--data-dir/--mock-llm`

- **测试**：后端 16 条 + WebUI 4 条（含前端接线完整性——路由通了但界面没入口最容易悄悄上线）

- **真机结果**（当前仓库状态）：6 通过 / 3 待改进 / 0 不合格 —— needs_work
  - 待改进：未配模型档位、未沉淀技能、还没有任务历史（都是真实且可动的）
  - 第 7 项：稳定段 2448 字符落在公共前缀内（占较短提示词 46%）

### 提示词前缀缓存 + 场景模板（受 Qoder Agent SDK 分享启发）

文章主旨：把驱动产品的 Agent Harness 以 SDK 形式开放。其中两条可迁移的判断——自建九坑里的**缓存率上不去**，以及**把不同场景的差异沉淀为 Agent Template，而不是为每个场景修改底层 Runtime**。对照落地两件事：

- **P0 提示词前缀缓存友好化（省钱，且真实可量化）**
  - 原理：服务端前缀缓存（KV cache 复用）要求**逐字节相同的最长公共前缀**，命中部分按折扣计价；一个夹在中间的工作目录就能废掉它后面的全部内容
  - 原布局的问题：最长的静态块（输出格式 + 规划规则 + 验收指南）排在最后，工具 schema 段却在最前且随目标变化——第一个易变段出现在第一百字左右，公共前缀几乎为零
  - 重排为「稳定段在前、易变段在后」：身份 → 输出格式 + 规则 + 验收指南 → 角色知识 → 验收重点 → 场景产出格式 → 风格 → 编程准则 → 能力菜单 → 定时任务；随后才是筛出的 schema、工作目录、摘要、记忆、历史、重规划反馈
  - 关键拆分：把**能力菜单**（只依赖注册表，稳定）与**完整 schema**（按目标筛选，易变）分开，不再把稳定内容拖进易变区
  - 输出格式要求前移后，末尾另压一行 `## 输出提醒`——它排在易变段之后，不损缓存前缀，却把"只输出 JSON"这条最容易违反的约束推回生成点
  - 反思器同此布局（`reflectorSystemPrompt`）
  - 度量工具：`llm.StablePrefixLen` / `SplitCacheBoundary`（按字符切分，不切断多字节字符）

- **P0 缓存命中量化（把布局优化变成可验证的数字）**
  - 四套协议分别解析：OpenAI/GLM `prompt_tokens_details.cached_tokens`、DeepSeek `prompt_cache_hit_tokens`、Anthropic `cache_read_input_tokens`、Responses `input_tokens_details.cached_tokens`
  - **流式也拿真 usage**：规划走流式，不主动要就永远只能估算，而估算值里没有"缓存"这一项，命中率永远显示不出来。因此流式带 `stream_options.include_usage`；该字段是 OpenAI 扩展，个别厂商会直接 400 → **被拒一次自动退回重试并记住不再发**（不能为拿准数字把主链路弄挂）
  - **Anthropic 显式挂断点**：其前缀缓存是 opt-in 的，不标 `cache_control` 就完全不缓存。系统提示词估算 > 1024 token 时转内容块数组并挂 `{type:"ephemeral"}`
  - 口径对齐：Anthropic 的 `input_tokens` 不含缓存部分，总输入按 `input_tokens + cache_read + cache_creation` 计，与 OpenAI 的 `prompt_tokens`（含 cached）一致；命中量只取 `cache_read`
  - `TaskUsage` 增 `CachedTokens` / `CachedCalls`，任务卡悬浮显示缓存命中率与命中 token 数
  - **沉默比撒谎好**：厂商不返回该字段时不显示任何百分比——"命中率 0%"会被误读成布局有问题，而实际只是无从得知

- **P1 场景模板：角色升级为完整模板（`ExpertRole`）**
  - 五字段各管一件事：`SystemPrompt`（人设）/ `AcceptanceFocus`（什么算做到）/ `OutputFormat`（产出长什么样）/ `Tools`（场景核心工具）/ `ModelTier`（该场景用哪档模型）
  - `Tools` → `Planner.RoleTools`：菜单模式下强制附完整 schema，且排在按目标快筛的结果**之前**（快筛是"猜"，模板是"这个场景靠它吃饭"）；与 `ForceTools`（上次用过的）分开存、提示词里分开说，因为理由不同
  - `OutputFormat` → 注入规划器提示词稳定段。"写份报告"在分析师那里是表 + 口径，在项目经理那里是"谁、什么时候、交付什么"
  - `ModelTier` → `llm.tiers` 档位表（档位名 → 模型 ID）+ `Agent.TierLLM`，内置 economy / coding / office / reasoning 四个档位名。**三层回退**：角色未声明 / 档位未配置 / 档位即主模型，都安全回退——档位是"可以挑"不是"必须挑"
  - 同一场景内规划、反思、对话用同一客户端；`mock` 会话下档位失效，避免离线自测打真实网络
  - 边界：模板作用于工作/编程模式（规划管线）；对话模式只取模型档位——把"优先用 file.*"这类规划导向约束塞进直答路径只会互相打架
  - 设置页新增「模型档位」文本框（一行一条「档位: 模型」）

- **测试与验证**
  - 新增 `internal/agent/promptcache_test.go`(6)、`internal/agent/roles_template_test.go`(9)、`internal/agent/usage_cache_test.go`(3)、`internal/llm/promptcache_test.go`(11)、`internal/config`(3)、`internal/webui`(2)
  - 布局契约做成了可执行断言：换目标后公共前缀仍覆盖各稳定块且长度达标；易变内容无论怎么变都不得侵入；提示词必须以身份段开头；末尾保留输出提醒；随任务历史变化的 schema 段不得混进稳定段
  - 模板最容易出的错是**工具名拼错一个字母**（不报错，只是"保证附上 schema"静默失效）→ 测试用真实工具构造器拼注册表逐个校验
  - 全量回归 28 包全绿；e2e 5/5 绿

- **踩坑（复用）**
  - 本仓库**全部是 LF 行尾**（此前记录的"CRLF"是误判）。用 `gofmt -w` 可能连带改掉行尾，**改完要核一遍**：`python -c "raw=open(f,'rb').read(); print(raw.count(b'\r\n'))"`
  - `gofmt -l` 在改动字段对齐后会报警：新增结构体字段/常量会改变对齐列。核格式时先 `tr -d '\r'` 归一化再看
  - `NewGLM(..., timeout time.Duration)` 最后一个是 `time.Duration`，传字面量 `5` 等于 5 纳秒，测试会以 "context deadline exceeded" 失败
  - 前缀缓存的公共前缀**包含段落标题**：两个提示词都有 `## 上下文` 时，标题本身在公共前缀里，只有标题下的取值不同。断言要针对取值，不要针对标题

### 验收标准：干活的不能兼任验收（第二轮追加）

文章把「生成者给自己打分」列为最隐蔽的坑之一——让干活的兼任验收，分数永远偏高。落地三步：

- **规划阶段定标准**：`Planner` 输出的 JSON 新增 `acceptance`（2–4 条可核对条目），`normalizeAcceptance` 去空白/去重/截断/限条数（`maxAcceptance = 4`）；拿不到不算错误，退回原整体评分
- **反思阶段逐条判定**：`Reflector.Acceptance` 非空时，提示词切换为「逐条判定、`criterion` 用原文、`note` 要具体到能照着改」，输出 `checks` 数组，并明确告知「分数由系统计算，你不需要给分」
- **分数由系统算**：`scoreFromChecks` 按通过比例给分（全过 100 / 一半 50 / 全不过 0），模型硬塞 `"score":100` 也会被覆盖；`alignChecks` 把判定对齐回标准列表，**漏判按未通过计**，多出的丢弃
- **三道闸门（判定不能被绕过）**
  - verdict 说 `done` 但判定没全过 → 降级为 `replan`：verdict 与 checks 出自同一模型，矛盾时以更结构化的 checks 为准
  - 循环的完成判定补上 `acceptanceSatisfied`：调低 `DoneThreshold` 或模型自称 done 都绕不过逐条判定；判定缺失时放行，避免反思器偶发失败把任务卡在循环里
  - 验收标准**定下就不再改**：重规划没重申则沿用，重申但内容变了也不采纳——它是给用户的承诺，不该由没做到的一方在重试时改写
- **状态校正**：`applyAcceptanceVerdict` 在 `finalize` 开头统一校正——部分通过判 `partial`、一条没过判 `failed`，未达标条目写进错误说明；只纠正被误判为成功的结论，已判失败/取消的不翻案。成长统计与记忆沉淀因此看到的是真实状态
- 数据链路：`types.Plan.Acceptance` → `types.Reflection.Checks` → `GoalResult.Acceptance/Checks`；任务卡渲染验收清单（对勾 / 叉 / 点）与「验收清单 N/M 项通过」
- 无额外 LLM 调用——验收搭在既有反思调用里，只换提示词与输出结构

### 领域化验收重点（第二轮追加）

通用验收指南只能教"怎么写可判定的标准"（好例/差例），给不出"这个领域该盯哪几件事"。而尺度随领域变：数据的"完成"是能对账，代码的"完成"是能验证，文案的"完成"是能直接交付。

- `ExpertRole` 新增 `AcceptanceFocus` 字段，7 个内置角色各补一条：数据分析师（数字可追溯/口径/异常值）、开发工程师（最小改动/可执行验证/错误分支）、内容创作者（可直接交付/结构完整/受众字数）、项目经理（谁-何时-交付什么/风险有应对/不写"尽快"）、研究员（来源可查/区分事实与推测/给反面证据）、运维专家（可回滚/验证命令与预期输出/影响范围）、通用助手（无占位符/逐项覆盖）
- 注入位置：通用验收指南**之后**（先讲原则再讲本领域重点），不挤占原有角色知识段
- 未指定角色时也生效（走通用助手），不再退回"做得不错"这类没法判的标准

**明确不做"验收标准库"。** 原本设想把历次标准按意图存下来复用，但前提不成立：验收标准**本来就不花额外调用**——工作模式里它是规划器同一次 JSON 输出里的字段，对话模式里是核对器同一次输出的一部分。复用省不下调用，只省几个 token；而代价是拿过期/错配的尺子去量（"写公众号文章"的标准若写着"不少于 1500 字"，这次要的是短推文），且无反馈信号时标准会冻结在首次任务的水准。已在设计文档写明取舍。

### 对话模式独立自检（第二轮追加）

工作模式有了逐条验收后，对话模式的"无条件报满分"就成了最刺眼的不一致——`runChatPath` 里写死 `Score: 100`，连自评都省了。补一次独立核对：

- **`internal/agent/chatcheck.go`（新增）**：`chatSelfCheck` 由辅助模型做一次调用，只读用户目标与最终回答（不给它看生成时的推理），先从目标提炼 1–3 条可核对标准，再逐条判定
- 结果写回 `GoalResult.Acceptance` / `Checks`；`applyChatCheck` 用 `scoreFromChecks` 算分、`applyAcceptanceVerdict` 校正状态——只过一半就如实判 `partial` 并说明差在哪
- **四条纪律**：只走辅助模型（未配 `fast_model` 静默不生效）；短目标（<10 字）且短回答（<160 字）视为闲聊跳过；调用失败/解析不了/没提炼出标准一律放行；只纠正被误判为**成功**的结论
- 与工作模式的差别已在文档写明：对话模式的标准是**事后**提炼，弱于工作模式的"动手前定承诺"，但"核对者不是生成者"这条约束是满足的
