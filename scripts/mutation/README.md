# 变异验证（负例控制）

**这里回答的问题不是「测试通过了吗」，而是「测试真的挡得住吗」。**
把每一处判据逐个改坏，确认至少有一条断言会响。全绿的测试套件不能证明这件事——
它只证明「在没人动过代码的前提下，代码是对的」。

对应判据：每条可机械判断的规则，配一条 exit non-zero 的命令（`AGENTS.md` 命令表），
**并且**做一次负例控制（本目录）。

## 怎么跑

**清单在本文件，不在别处。** 每批一个脚本，`AGENTS.md` 只指到这个目录：

| 批次 | 管什么判据 |
| :--- | :--- |
| `batch-a-audit.py` | 批次 A「审计四用法」：沿用语义、运行日志、计数与告警口径、回放与续跑 |
| `batch-b-wiring.py` | 批次 F4/F7/F8 的接线：密钥主机绑定、终态归档落盘（含「归档不受通知策略支配」）、重启后的任务列表 |
| `batch-c-inventory.py` | 闸门自己：README 端点表与 `internal/webui` 注册的路由是否双向一致（`scripts/check-api-docs.py`） |
| `batch-d-feedback.py` | 批次 F10「反馈与建议」的判断：脱敏时机、现场字段范围、投递失败的状态、图片识别、空描述 |
| `batch-e-rail-lifecycle.py` | 批次 F11 的读数与寿命：现场栏那一格的数字从哪来（`/api/info` 与门面两处源头）、取消能否真的叫醒停在审批上的那一轮、取消的原因写成什么 |
| `batch-f-composer-meta.py` | 批次 F12 的接线与补丁语义：水位百分比的算法（容量保护、钳 100、多算一轮）与两处出口（`Stats` / `ContextView`）、只发一个 `model` 键的设置补丁不许清掉辅助模型与档位表 |

| `batch-j-cue-owner.py` | 批次 F17「候补目标」的三条口径：线索清单与派生分支与`人话牌子`三处少一处（界面上不报错，只是那一类永远不出现 / 裸奔成 `half_done`）、提议层伸了手（`CueView` 里调 `RunGoal`——"只提议不执行"天生测不到，它描述的正是没有发生的事）、卡片理由退回 markdown；派生分支还在却不吐行与「别再提」按错指纹（都归 Go：闸门只读源码，判不出"今天到底浮没浮出一张卡"）；前端换掉截断提示的 id。**第 9 条打的是闸门自己**：把清单改成 `append(...)` 拼出来（合法 Go 写法）后，正则读不出 `cueSignals`，必须判红而不是判绿。这道闸门**还**带 `--self-test`（6 份坏文本 + 2 份干扰文本：注释里提函数名、注释里用 `**`） |

还有一类判据的负例控制**内建在检查脚本自己身上**，不占批次号：

- `python scripts/check-app-startup.py --self-test`——app.js 的启动段必须是最后一段。
- `python scripts/check-py-utf8.py --self-test`——会印中文的 `check-*.py` 必须自修 stdout 编码。
- `python scripts/check-dom-anchors.py --self-test`——JS 指向的 id 必须存在、现场栏 / 输入区 / 预览面板 / 台账 / 候补目标那批锚点（`rail-*` / `ro-*` / `cp-*` / `bp-*` / `cx-*` / `cu-*`）必须有人接、app.js 里定义的函数必须有人调用（七份坏文本：正向一条、锚点反向五条、函数反向一条，逐条验会被拦住）。

它们不碰 Go 代码，套不进本目录的「改坏 → 编译 → 跑测试」骨架，所以自己带坏文本；
后一条还顺手拿真文件的 stdout 解一次 UTF-8，防止"判据点头、输出仍是乱码"。
`verify.sh` 第 1 层每次都以 `--self-test` 形式调用它们。

```bash
python scripts/mutation/batch-a-audit.py            # 整批
python scripts/mutation/batch-a-audit.py 1-5        # 只跑第 1~5 个（分段，见下）
python scripts/mutation/batch-a-audit.py carried    # 只跑名字含 carried 的
```

**分段跑不是可选项。** 整批十几分钟，而后台执行会被沙箱拦在 Go 构建缓存上；
一次被拦下的命令**看起来就像「测试失败」**，于是变异被记成「已捕获」。
那是比跑不动更坏的结果：它给出一个假的满分。宁可分段、每段都在前台跑完。

## 判定口径

| 结果 | 含义 |
| :--- | :--- |
| **捕获** | 目标命令返回非零——断言挡住了这个错误。这是要的 |
| **存活** | 所有目标命令都通过——这个错误能悄悄溜过去。**必须补断言** |
| **无效** | 变异导致编译失败——它证明不了任何事。**必须修改法** |
| **跳过** | 锚点预检失败——脚本已过期，改法没被应用。**必须更新锚点** |

只要有存活 / 无效 / 跳过，退出码就是 1。**「无效」必须单独计数**：
把它混进「捕获」，捕获率会被悄悄抬高。

## 四种假满分（都被踩过，别再踩）

1. **命令里出现 `|`。** 在 Windows 上走 `cmd.exe`，而 cmd 不认单引号——
   `go test -run 'A|B'` 里的 `|` 被当成管道，命令压根没跑起来，
   而「命令失败」被记成「捕获」。**目标命令一律不含 `|`。**
2. **变异没能编译。** 「捕获」的理由是语法错误，不是断言有效。
   骨架会按 `BUILD_FAIL_MARKERS` 单列成「无效」。
3. **环境噪声当成测试报错。** 本机 Go 工具链偶发把标准库报成
   `package X is not in std`，也会出现莫名的 SIGTERM。骨架按 `ENV_MARKERS`
   识别并重试（`MAX_ENV_RETRIES`），不把噪声算成捕获。
4. **进程被强杀，仓库停在改了一半的状态。** 内存备份救不了 SIGKILL。
   骨架把备份同时写到磁盘，**启动时先还原上次没跑干净的文件**，
   再做全量预检（每个锚点必须恰好出现一次）。起点不干净就拒绝运行。

另外两条：死等类变异（例如「不放行下游」）会让 `go test` 挂到默认的 10 分钟超时，
**目标命令必须带 `-timeout`**；改动前先确认锚点**恰好出现一次**，匹配到两处时
变异会被应用到错误的位置。

## 有一类判据在这里测不了

**"写盘要早于把终态告诉外界"**（webui 任务归档）没有负例控制：把顺序倒回去，
没有任何断言会响——它挡的是"广播之后进程被杀"，而这在一个进程内复现不出来。
能测到的只是"有没有归档"，那是另一条变异的事。

处理方式不是硬凑一条永远存活的变异放进批次表（那只会让人怀疑捕获率），而是：
判定留在 `internal/webui/handlers.go` 的注释里说明理由，本目录记下"这条不测、为什么不测"。
**负例控制的边界就是可测性的边界，越界的部分要明说。**

同类还有「反馈先落本地归档、再谈远端投递」：整块挪到投递之后，相关测试仍全绿。
理由写在 `batch-d-feedback.py` 的开头，这里只留指针。

同一批里也可能**一条测不出**：批次 G 去掉了还原路径的 workspace 边界（`ResolveInRoots`），
十条断言一条都不响——因为"必须在本次清单里"那道闸在它后面兜着，而清单只可能记着
workspace 内的路径。那一道的意义是纵深（清单被手工塞进脏数据时它还在），不是当前可测的判据。
理由写在 `batch-g-changes.py` 的开头。

## 加一批

复制 `batch-a-audit.py`，改 `MUTATIONS` 即可，公共骨架在 `_harness.py`。**加完回到上面的清单补一行**——清单漏一批，后来人就只跑第一批，拿到一个假的满分：

```python
{
    "name": "沿用步骤不进运行日志",
    "file": "internal/agent/executor.go",
    # 锚点 old 在文件里必须**恰好出现一次**
    "edits": [("\t\te.record(taskID, state.results[i])\n", "")],
    "targets": [("agent", "go test ./internal/agent/ -count=1 -timeout 90s")],
}
```

每个变异都要写一句注释说明**为什么这处失效是静默的**。
写不出来，说明它不该在这里——它应该是 `verify.sh` 六层里的一条普通检查。

## 它不在 `verify.sh` 里（但锚点在）

变异验证是**每批一次**的证明，不是每次改动都跑的门禁（十几分钟起步）。
六层闸门管「这次改动没弄坏东西」，本目录管「闸门本身有没有用」。

**便宜的那一半已经进了第 1 层**：`python scripts/check-mutation-anchors.py --self-test .`
逐个导入批次、确认每条锚点在目标文件里恰好出现一次（判据转调 `_harness.preflight`，
不写第二遍）。为什么非进闸门不可——批次 A 真失效过一次：锚点指的那行代码早被收进
`replayFile()`，预检报 0 次、整批拒绝运行，20 条负例控制一条都没跑，而六层全绿。
没人会在每次重构后想起来重跑批次，所以"锚点还在不在"这件事不能靠人记。
